Плагин можно проверить, не открывая окна: ядро не импортирует Electron, а тест-кит поднимает его вместе с хостами в процессе теста. Пакет называется `@cyborg-harness/testing`, ставится как dev-зависимость и опирается на `@cyborg-harness/core`, не копируя его код.

```bash
npm install --save-dev @cyborg-harness/testing
```

:::caution[Пакеты ещё не опубликованы]
Пакеты `@cyborg-harness/*` и команда `cyborg-plugin` ещё не в реестре. `@cyborg-harness/contracts` готов к выпуску ([P-01](https://github.com/dex-it/cyborg-harness/issues/29): собирается, упаковывается и ставится в пустой проект из tarball), его выпуск - [P-10](https://github.com/dex-it/cyborg-harness/issues/11); остальное публикуется задачами [P-02](https://github.com/dex-it/cyborg-harness/issues/34), [P-05](https://github.com/dex-it/cyborg-harness/issues/39), [P-09](https://github.com/dex-it/cyborg-harness/issues/9). Пакеты scope `@cyborg` на npmjs.com к проекту не относятся. До выпуска работайте из репозитория (`npm ci`, `npm start`).
:::

Тесты запускаются встроенным `node --test`: Node 24 снимает типы с `.ts` сам, сборка для теста не нужна.

## Что даёт тест-кит

| Что | Зачем |
|---|---|
| `startKernel({ plugins, os })` | Собирает манифесты и точки входа ваших плагинов, запускает загрузку на хостах внутри процесса теста и возвращает ядро |
| Ожидание записей журнала | Дождаться `activated`, `denied`, `switched-off`, не гадая со временем |
| Выгрузка через `Symbol.asyncDispose` | Конструкция `await using` снимает ядро и все хосты в конце теста |
| `fakePty()` | Поддельный pty: проверить запуск терминала без процессов |
| Поддельные секреты и память разделов | Хранилище секретов и слои `config` и `state` в памяти |
| Каталог-песочница | Временный каталог с `realpath`: на macOS временный каталог - симлинк, и без этого пути не совпали бы с областями |
| `agentContractSuite(provider)` | Общий набор проверок поставщика `cyborg.agent` |

Объекты `os` в `startKernel` подменяют окружение ОС: так плагин с правом `pty` работает без настоящих процессов, а плагин с секретами - без хранилища системы.

## Что проверить в тесте плагина

1. **Плагин активен.** После запуска ядра в журнале есть `activated` для вашего `id`, а `rejected`, `invalid` и `failed` нет.
2. **Команда отвечает.** Вызов зарегистрированной команды возвращает ожидаемое, а вызов с неверными аргументами даёт `Invalid`.
3. **Контракт работает через границу.** Потребитель получает `Remote<T>`: вызовите метод и проверьте результат. Если метод возвращает функцию или `Map`, тест упадёт с `NotCloneable`, как упал бы в окне.
4. **Раздел `config` проходит схему.** Значения по умолчанию валидны, а `migrate` приводит старый слой к новой версии.
5. **Права достаточны и не шире нужного.** Обращение к пути вне области даёт `PermissionDenied`, а в журнале появляется `denied`; в тесте штатной работы записей `denied` быть не должно.

## Тест поставщика агента

Поставщик контракта `cyborg.agent` проходит тот же набор, что и встроенные `agent-claude-code` и `agent-shell`. Набор проверяет:

- факты поставщика и то, что ответы клонируются;
- запуск через потребителя по его праву `pty`: описание из `launch` годится как вход `ctx.os.pty.spawn`;
- код выхода 127 переводится в `notFound`;
- `history` отвечает пустым списком там, где `capabilities.history` ложно;
- в журнале нет записей `denied`.

Для контрактов `cyborg.secret-source` и `cyborg.project-settings` в пакете лежат каркасы наборов с перечнем обязательных проверок.

## Собственный набор для своего контракта

Если вы объявили контракт `acme.*`, который будут реализовывать другие, выпустите вместе с пакетом объявлений функцию-набор, как `agentContractSuite`: она принимает поставщика и вызывает его через потребителя на `startKernel`. Так сторонний поставщик проверяет себя теми же тестами, что и ваш.

## Статическая проверка

Дисциплина «главная часть импортирует только `@cyborg-harness/contracts` и свои модули» проверяется не тестом, а командой:

```bash
npx cyborg-plugin check .
```

Она читает манифест, сверяет `engines.cyborg` с версией API, проверяет, что модули видов и файлы схем существуют, прогоняет правило импортов по всем `.ts` и `.js` и печатает права словами. Из кода тот же результат даёт `checkPlugin(dir, options)`, но структурой. Код возврата 0 - нарушений нет, 1 - есть. Подключите `check` и `build` в CI вашего плагина.

:::caution[Чего тест-кит не проверяет]
- Вид в браузере: `<iframe>`, CSP, клавиши с фокусом внутри фрейма. Для этого есть дымовой тест окна в стенде.
- Изоляцию доступа: в тестах хосты работают внутри процесса, а статическая проверка не видит динамические вызовы вроде `globalThis.process`.
- Поведение настоящих программ из `process` и `pty`.
:::
