У плагина два места для данных. **Config** - намеренные настройки, **state** - память машины. Каждый плагин видит только свой раздел; ошибка в разделе ломает только его владельца.

## Config и state

| | Config | State |
|---|---|---|
| Что | намеренные настройки | память машины: активный проект, ширины, раскрытые узлы, расстановка |
| Где | файл воркспейса и файл пользователя | каталог приложения, ключ по воркспейсу |
| API | `ctx.config` - только свой раздел | `ctx.state` - только свой раздел |
| Редактирует | человек и плагин | плагин |

Config делится на слои **user** и **workspace**: верхний слой перекрывает нижний. Значения, которые расширяют права (хост `config:<поле>` в `net`), ядро берёт только из слоя user: файл воркспейса мог прийти из чужого репозитория ([границы доверия](/concepts/trust/)). Значения секретов не лежат ни там, ни там.

```jsonc
{
  "cyborg": 2,
  "plugins": { "enabled": ["sessions", "files", "trackers"] },
  "settings": {
    "trackers": { "byProject": { "p1": { "github": true } } }
  }
}
```

Разделы плагинов лежат в `settings`, ядро знает только своё: `plugins.enabled`, `plugins.hosts`, `plugins.uiGroups`, `plugins.keybindings`.

## Схемы и версии

Манифест объявляет версию и схему раздела:

```jsonc
"config": { "schema": "./config.schema.json", "version": 3 },
"state":  { "schema": "./state.schema.json",  "version": 1 }
```

Ядро проверяет раздел по схеме до активации и при каждой правке файла извне. Схема - подмножество JSON Schema: `type`, `properties`, `required`, `additionalProperties`, `items`, `enum`, `const`, границы чисел, длины строк и списков, `pattern`, `uniqueItems`. Аннотации (`title`, `description`, `default`) пропускаются, а остальные ключи, например `$ref` и `oneOf`, - ошибка схемы: автор не должен считать проверенным то, что ядро не проверяет.

| Что случилось | Что делает ядро |
|---|---|
| версия раздела ниже версии плагина | до активации вызывает `migrate(fromVersion, data)` плагина и сохраняет результат |
| версия раздела выше (плагин откатили) | плагин не активируется, раздел не трогается, причина в журнале |
| раздел не прошёл схему или `validate` | отказ только этому плагину, остальные работают |
| миграция бросила исключение | отказ только этому плагину |
| файл поправили вручную с ошибкой | значение остаётся прежним, отказ в журнале |

Модуль плагина дополняет манифест значениями по умолчанию, `migrate` и `validate`. Путь схемы в манифесте - `./<файл>.json` внутри каталога плагина; ссылка наружу - отказ.

## Правки извне

Файл воркспейса отслеживается. Правка доходит до владельца раздела через `ctx.config.onChange`. Битый файл не стирает разделы и не перезаписывается: пока человек его не починит, запись в него отменяется. Запись всегда идёт через временный файл и `rename`, поэтому оборванная запись не оставляет полупустой файл.

## Секреты

Секреты держатся на двух ролях.

1. **Хранилище ядра** (`ctx.os.secrets`, поверх системного шифрования ОС) - корень доверия. Ключи хранятся как `<pluginId>/<key>`, каждый плагин видит только свои. Без шифрования ОС (Linux без keyring) вызов отвечает `Unavailable`, а не пишет открытым текстом.
2. **Ссылки** в config: вместо значения лежит `{ "$secret": "ключ" }`.

```jsonc
"jira": { "enabled": true, "token": { "$secret": "jira-token" } }
```

`ctx.secrets.resolve` разрешает ссылку без схемы из хранилища ядра вызывающего плагина. Ссылка со схемой (`vault://...`) идёт во внешний источник секретов и должна подходить под маску `secrets.ref` вызывающего. Нет поставщика схемы - `Unavailable`; ссылка вне права - `PermissionDenied`.

Правила: значение секрета не пишется в config, state и журнал, не кэшируется ядром и не проходит через третьи плагины. Это проверяет тест, а не ревью. При удалении плагина его секреты стираются.

## Память вида и документов

Вид плагина хранит свою память через `ctx.state` вида: JSON до 64 КБ, у каждого воркспейса своя. Данные документов (`ctx.documents`) тоже лежат в состоянии воркспейса. Не используйте `localStorage` для того, что должно пережить смену воркспейса: у origin плагина он общий для всех.

## Перенос старых форматов

Ядро умеет один раз перенести старый формат воркспейса в новый: оставляет копию `.v1.bak` и записывает новый документ. Что именно считать старым форматом, знает приложение, а не ядро: оно передаёт ядру свой перенос при открытии воркспейса. Так в ядре нет предметных имён.
