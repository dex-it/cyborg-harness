Воркспейс - главная сессия приложения: файл `config` воркспейса, его `state` и окно. Воркспейс выбирается до загрузки любого плагина, поэтому его открытие - забота ядра.

## Как открывается

Воркспейс открывают флагом запуска, выбором из «Недавних» или кнопкой «Открыть…» в окне. Стенд принимает флаг `--workspace=<файл>`; без него открывается последний из «Недавних», а без них - файл по умолчанию в каталоге данных приложения. Флаг `--no-workspace` открывает окно без воркспейса: ядро не запускается, в окне только выбор.

```mermaid

  A["Выбор воркспейса"] --> B["Замок файла"]
  B --> C["Перенос старого формата"]
  C --> D["Слои config и state"]

```

## Замок

Ядро берёт замок `<файл>.lock` с номером процесса. Пока замок держит живой процесс, тот же воркспейс другой процесс открыть не может: повторный запуск переводит фокус на уже открытое окно и завершается. Замок процесса, которого уже нет, ядро забирает само. Закрытие окна или смена воркспейса снимают замок.

:::note[Несколько воркспейсов одновременно]
Стенд держит по процессу на воркспейс, процессов с общим `userData` может быть несколько ([решения](/development/decisions/), D-00 строка 5). Второй запуск того же воркспейса просит владельца поднять окно (`claimInstance` ядра: сокет с адресом по ключу воркспейса в личном каталоге - `XDG_RUNTIME_DIR` или `<userData>/run`) и завершается; если владелец не ответил в срок, процесс говорит об этом и выходит с кодом 3; если контроль экземпляров не заработал (каталог адресов чужой или не создаётся), окно всё равно открывается, а причина показана в диалоге; другой воркспейс открывается своим процессом, в «Недавних» для этого есть «в новом окне». Файлы `userData`, которые пишут все процессы (`recent.json`, `secrets.json`, слой пользователя `cyborg.json`), ядро пишет под замком `<файл>.write.lock` (`withFileLock`); сессия Chromium у каждого воркспейса своя. Каталоги `plugin-data` и `plugin-temp` общие: `writeText` атомарен, а цикл «прочитал - изменил - записал» двух процессов плагин исключает сам. Приложение, которому нужен один процесс на весь `userData`, использует `singleInstance` адаптера.
:::

## Закрытие и смена

- Плагины выключаются через `Disposable`.
- Живые процессы терминала завершаются после подтверждения человека ([Терминалы](/features/terminals/)).
- Замок снимается.
- Перезагрузка окна - не закрытие: воркспейс, хосты и процессы остаются.

Смена воркспейса из окна выключает плагины и поднимает их на новом файле; как именно приложение это делает (в стенде - перезапуском с новым `--workspace`), его дело.

## «Недавние»

Список лежит в каталоге приложения. Последний открытый - первым, без повторов по `realpath`, не больше 10. Файл, которого больше нет, не показывается. В список попадает только воркспейс, который открылся. Битый список не мешает открыть окно: следующая запись его заменит.

## Слои настроек

Файл пользователя и файл воркспейса дают два слоя. Воркспейс перекрывает пользователя: `plugins.enabled` воркспейса побеждает пользовательский, группы хостов (`plugins.hosts`) сливаются, группы вида (`plugins.uiGroups`) берутся только из файла пользователя, привязки `plugins.keybindings` воркспейса идут после пользовательских. Подробности хранения - в [Настройках и состоянии](/features/config-state/).

Состояние воркспейса лежит в каталоге приложения под ключом от `realpath` файла: один и тот же воркспейс, открытый по разным путям (симлинк, относительный путь), - одно состояние.

## Смена `plugins.enabled` на ходу

Правка списка в файле доходит до ядра без перезапуска. Убранный плагин выключается вместе с теми, кто требует его через `requires`, вернувшийся включается. Плагин, которого не было в графе при запуске, ждёт перезапуска: окно пишет «включатся после перезапуска».

## Старый формат

Когда приложение переходит с прежнего формата файлов на формат воркспейса, перенос делает хук приложения при открытии: ядро сохраняет копию `.v1.bak` и записывает новый документ. Предметных имён в ядре при этом нет.

## Что видит автор

Плагин не знает путь воркспейса. Он видит свои разделы `ctx.config` и `ctx.state`, область путей `workspace` (корни проектов, которые задают плагины с `security.roots`) и документы через `ctx.documents`. Право `security.roots` принимает только существующий каталог, не корень файловой системы, не домашний каталог и не предка каталогов приложения. Корень, который назван только в файле воркспейса (его принёс репозиторий команды), ядро не принимает: нужен путь в вашем файле пользователя или выбор в диалоге.
