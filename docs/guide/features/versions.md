Обновление приложения или плагина не должно ломать остальных и терять данные. Для этого версии есть на четырёх уровнях: API плагинов, контракты, разделы настроек и пакеты.

## API плагина

Манифест называет версию API, под которую написан плагин:

```jsonc
"id": "trackers",
"version": "2.3.0",
"engines": { "cyborg": "^1" }
```

- `engines.cyborg` - диапазон версий API: `ctx`, `UiContext`, поля манифеста и элементы `cy-*`. Нижний порог - минор, под который собран плагин: `^1.5`, а не `^1`, если плагин зовёт член, появившийся в 1.5.
- Несовместимый диапазон - плагин не загружается, причина в журнале: «нужен API Cyborg ^2, есть 1.0.0».
- Незнакомое поле манифеста - отказ с именем поля, кроме `$schema` для редактора. Если при этом версия API плагину не подходит, причина одна - версия API, а не поле.
- API версионируется семантически. В пределах мажорной версии элемент ядра не удаляется и не меняет атрибуты, член `PluginContext` не пропадает.

## Заморозка API 1.0

Публичная поверхность - `PluginContext`, `UiContext`, `PluginPermissions`, поля манифеста, теги `cy-*` и коды `CoreErrorCode` - зафиксирована снимком под тестом. Изменение снимка без повышения версии роняет проверку. Версия API определена в одном месте ядра и связана с версией пакета `@cyborg-harness/contracts`.

## Контракты

| Изменение | Версия |
|---|---|
| новый необязательный член, новое необязательное поле, новое значение в объединении событий | минорная; потребитель обязан пропускать незнакомое |
| удаление или переименование, новое обязательное поле аргумента, смена смысла | мажорная |

- **Две версии сразу.** Поставщик может отдавать обе: `"provides": { "cyborg.files": ["1.0", "2.0"] }`. Каждый потребитель получает ту, которую просил.
- **Устаревание.** Член с пометкой `@deprecated` живёт минимум до следующей мажорной версии. Ядро пишет в журнал, кто его вызывает, так что поставщик видит, когда старую версию можно убирать.
- **Владение.** `cyborg.*` закреплено за репозиторием Cyborg и пакетом `@cyborg-harness/contracts` и доступно только встроенным плагинам. Сторонние контракты называются по автору (`acme.*`) и публикуются своими пакетами.

Пример эволюции: `cyborg.tab` добавил в 1.1 необязательное поле `icon`. Поставщик 1.0 по-прежнему подходит под тип, а потребитель проверяет, что поле есть.

## Разделы config и state

Раздел плагина имеет свою версию. Новее плагина (плагин откатили) - раздел не трогается и плагин не активируется; старше - ядро вызывает `migrate`. Подробности - в [Настройках и состоянии](/features/config-state/).

## Пакеты

| Пакет | Что версионируется |
|---|---|
| `@cyborg-harness/contracts` | карта контрактов и типы API плагина; версия пакета и мажорная версия контракта - разные вещи |
| `@cyborg-harness/core` | ядро |
| `@cyborg-harness/electron` | адаптер Electron |
| `@cyborg-harness/testing` | тест-кит |

Приложение подключает `@cyborg-harness/core`, `@cyborg-harness/electron` и `@cyborg-harness/contracts` по номеру версии, а не копирует файлы. Релизы пакетов выпускаются по тегу, изменение карты контрактов без повышения версии роняет CI. Подробнее - в [справочнике пакетов](/reference/packages/).

## Платформы и среда

Ядро работает на Node 24; его несёт Electron 45. Поддерживаемые системы - macOS и Linux; сведения о платформах собраны в [справочнике](/reference/platforms/).

## Что видит автор плагина

1. Указывает `engines.cyborg` с диапазоном, которым пользуется.
2. Указывает версию своего плагина в `version`: она участвует в журнале и в миграциях.
3. Использует мажорные версии контрактов явно: `ctx.contracts.get('cyborg.agent-tool', 1)`.
4. Читает журнал: там видно, что с ним не так после обновления приложения.
