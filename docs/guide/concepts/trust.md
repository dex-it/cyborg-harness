Ядро исходит из того, что плагин может ошибаться, а чужой плагин - быть недобросовестным. Поэтому оно проверяет вызов по каналу, а не по словам вызывающего, и разбирает все входные данные как недоверенные.

## Кому ядро верит

| Источник | Доверие | Как проверяется |
|---|---|---|
| Главный процесс и ядро | Полное | - |
| Манифест | Читается, но не верится | Разбор со строгой схемой, незнакомое поле - отказ; признак «из поставки» берётся из каталога установки, а не из манифеста |
| Хост плагинов | Доверия нет | Ядро проверяет, что сообщение пришло из хоста, где живёт названный в нём плагин; форма каждого сообщения сверяется |
| Главная часть плагина | Только в пределах прав | Шлюз `ctx.os`, схема аргументов команд, объявления в манифесте |
| Вид плагина | Доверия нет | Свой `<iframe>`, CSP, мост по origin, у вида нет `ctx.os` |
| Файл воркспейса | Правят руками; приходит из репозитория команды | Проверка по схеме, битый файл не стирает разделы, рядом ложится его копия `.corrupt-<время>`; значения, расширяющие права, из него не берутся |
| Пакет плагина на диске | Читается, но не верится без подписи | Подписанный `integrity.json` (Ed25519) доверенного издателя, срок, версия не ниже принятой, отзыв; ядро исполняет проверенные байты, а не файл ([Подпись и проверка пакета](/authors/signing/)) |
| Недоверенное имя | Опасно | Поиск только по собственным ключам: `constructor` и `__proto__` не находятся в прототипе |

Внутри хоста плагины неразличимы. Плагин в общем хосте мог бы написать от имени соседа в его раздел `config` и `state`, в его команды и контракты. Поэтому сторонний плагин всегда получает отдельный хост: граница доверия ядра - процесс хоста.

## Угрозы и защита

| Угроза | Что делает ядро |
|---|---|
| Хост выдаёт себя за другого плагина | Сообщение принимается, только если названный плагин живёт в этом хосте |
| Плагин регистрирует чужую или необъявленную команду | Команда должна быть объявлена в `commands` и лежать в пространстве имён плагина |
| Аргумент команды неверной формы | Ядро сверяет аргументы со схемой манифеста до обработчика, откуда бы ни пришёл вызов |
| Плагин читает файл вне разрешённого | Путь проверяется после `realpath` на открытом дескрипторе; вне области всегда `PermissionDenied`, никогда `NotFound`, чтобы не выдавать существование файла |
| Ссылка наружу из области | `realpath` раскрывает её, область не покидается |
| Запись в защищённые места | Закрыты всегда: данные приложения, файл воркспейса и его соседи `<файл>.*` (замок, копия `.corrupt`), каталоги других плагинов, `.git` без явного права |
| Запуск через посредника | Права через чужой контракт не передаются: поставщик объявляет `guard`, ядро проверяет право у вызывающего |
| Подмена описания запуска (confused deputy) | Запуск терминала по описанию поставщика сверяется и с правом `pty` потребителя, и с правом `launch` поставщика |
| Секрет в журнале и файлах | Значение не пишется в `config`, `state` и журнал; в `config` допустима только ссылка `$secret` |
| Сетевой запрос через страницу плагина | CSP вида запрещает сеть; наружу только через `ctx.os.net` по списку хостов |
| Расширение сети через настройки | Хост `config:<поле>` берётся из файла пользователя, а не из файла воркспейса; плагин сам записать новый хост не может |
| Воркспейс из чужих рук задаёт хост или группу | Значение из файла воркспейса права не расширяет: `net.fetch` на такой хост отклоняется, запись в журнале называет поле; сторонний плагин остаётся в своём хосте |
| Страница в браузере зовёт локальный сервер плагина | Ядро отвечает 421 на чужой `Host` и 403 на заголовок `Origin`, не обращаясь к плагину |
| Бесконечная работа или рост ресурсов | Таймауты, лимиты (тело ответа, число наблюдений, серверов, диалогов) и завершение групп процессов при выгрузке |
| Зависший или падающий плагин | Сторож перезапускает хост; три сбоя подряд выключают плагина |
| Файлы плагина подменены на диске, пакет откатили на старую версию | Подпись пакета и поставки, проверка байтов перед запуском и исполнение именно их, наибольшая принятая версия, отзыв ключей и хешей: отказ и запись `integrity-failed`; при включённой проверке |
| Чужой плагин занимает пространство `cyborg.*` | Такие контракты принимаются только от плагинов из поставки |
| Окно закрыто замком навсегда | Безопасный режим выключает все плагины, включая плагин замка |
| Плагин без прав пишет агенту: фрагмент промпта, инструмент MCP | Такие контракты (`cyborg.session-prompt`, `cyborg.agent-tool`) лежат в `cyborg.*` и принимаются только от плагинов из поставки; инструмента стороннего плагина нет в сервере `cyborg` |
| Агент получает больше прав, чем у человека в Claude Code | Без вопроса идут только инструменты сервера `cyborg`; режим разрешений Cyborg не задаёт и не меняет |

## Что считается решением человека

Файл воркспейса может прийти из репозитория команды или от коллеги, поэтому часть его значений ядро не принимает. Значения, которые расширяют права, - хост `config:<поле>` в праве `net` и группы со сторонним плагином, - ядро берёт только из файла пользователя (`cyborg.json` в каталоге приложения). Остальные значения воркспейса работают как раньше.

Если адрес сервера лежит в файле воркспейса, плагин его видит, но `net.fetch` на этот адрес получает отказ, а запись журнала в «Плагинах Cyborg» говорит, какое поле где задано. Чтобы разрешить, повторите значение у себя: `settings.<плагин>.<поле>` в файле пользователя. Окно согласия, которое сделает это одним нажатием, появится на втором этапе.

## Права словами

Каждое объявленное право ядро описывает человеческим языком: «читает файлы: проекты воркспейса», «запускает программы: git - полный доступ через программу», «может закрыть окно Cyborg». Одни и те же строки видны в списке плагинов и в `cyborg-plugin check`. Полный перечень - в [справочнике прав](/reference/permissions/).

## Два класса плагинов

Честная граница защиты касается немногих плагинов.

| Класс | Примеры | Что даёт изоляция |
|---|---|---|
| Базовые модули | Сессии, агенты, файлы, git, поиск | Права широки: нужны процессы и файлы. Известно, какую программу плагин запускает и с какими флагами, но не что сделает сама программа |
| Интеграции по HTTP API | Jira, GitHub, GitLab, Confluence, Vault | Права режутся до сети к своему хосту и своего токена. Гарантия полная |

Отсюда правило для интеграций: HTTP API, а не обёртка над CLI. Обёртка над `gh` или `glab` требует `process` и попадает в широкий класс, а тот же плагин на API остаётся в узком.

:::caution[Права process и pty]
Право `process` или `pty` даёт программе все права пользователя ОС. Закреплённые аргументы и запрет опасных флагов (`deny` правила, [справочник](/reference/permissions/#запрет-флагов-deny)) уменьшают риск, но защитой не являются: склеенные короткие флаги вроде `-xD` запрет не ловит. Окно показывает такое право как «полный доступ через программу».
:::

## Известные ограничения

- Каталог пользователя выключен по умолчанию и включается флагом `--user-plugins`, а плагин оттуда считается сторонним: получает собственный хост, запись `third-party` в журнале и метку в окне. Главная часть стороннего плагина работает в процессе Node под запретами (`--permission`, пустое окружение): `require('node:fs')`, запуск программ, потоки и аддоны отказаны, а плагин, захотевший обойти шлюз, получает ошибку. **Сеть без ограничителя ОС не закрыта:** на macOS её закрывает Seatbelt, на Linux запускатель `cyborg-confine`; там, где ограничителя нет, уровень изоляции 2, и «Плагины Cyborg» прямо пишут, что плагин может открыть соединение мимо `ctx.os.net`. Если приложение вернуло сторонние плагины на `utilityProcess` или отдельного Node нет, запретов нет совсем (уровень 1): тогда это только предупреждение ([изоляция](/concepts/isolation/#уровни-изоляции-процесса), [политика каталога](/features/plugins/#каталог-пользователя-на-первом-этапе)).
- Между проверкой пути и самой операцией процесс того же пользователя может подменить компонент пути ссылкой. Закрывает это относительная работа с открытым дескриптором каталога.
- Там, где плагин сам пишет, `shell.openPath` открывает только документ из разрешённого списка: цепочка «записать файл и открыть его программой системы» право `process` не обходит. В областях только для чтения открытие исполняемых файлов запрещено по расширению и биту `x`, но такой запрет не бывает исчерпывающим. Документ открывает программа ОС, и её уязвимости и настройки, например макросы, шлюз не контролирует.
- Замок окна защищает экран от того, кто подошёл к столу, а не данные. Безопасный режим выключает замок вместе со всеми плагинами, а файлы и `state` доступны любому, кто вошёл в ОС под этим пользователем.

## Агент

Агент работает с правами пользователя, а текст в его контекст приходит от плагинов и из внешнего мира. Поэтому всё, что пишет агенту, по силе равно праву `pty` на агента, хотя поставщик такого текста не просит в манифесте ни одного права.

- **Поставщик текста агенту действует с правами агента.** Это поставщик контракта, чей вывод читает агент: `cyborg.session-prompt` (фрагмент системного промпта) и `cyborg.agent-tool` (описание и ответ инструмента). Эти контракты лежат в пространстве `cyborg.*`, а его отдают только плагины из поставки, поэтому сторонний плагин с таким `provides` отклонён, и его текста нет ни в промпте, ни в `tools/list`. Открыть эти пространства сторонним можно будет только правом «пишет агенту» в окне согласия на втором этапе изоляции.
- **Файлы настроек агента - тот же вход.** `CLAUDE.md`, `.claude/` и `.mcp.json` там, где работает агент, `~/.claude/` и `~/.claude.json` агент читает как инструкции и настройки. Хук в настройках Claude Code - команда оболочки, поэтому право `fs.write` на такие пути равно праву `process` и праву на агента. Эти пути шлюз закрывает плагинам (угроза У-46, FR-CH-3031): запись в `CLAUDE.md`, `.claude/settings*.json`, `.mcp.json`, `~/.claude.json` и в `.claude/hooks`, `commands`, `agents`, `skills`, `output-styles` даёт `PermissionDenied` при любом праве `fs.write`, чтение настроек и ключей закрыто тоже, текст `CLAUDE.md` читать можно. Это не защита от плагина с правом `process` или `pty`: такой плагин пишет что угодно программой («полный доступ через программу»), а сторонний плагин до этапа 2 и так обычный Node.
- **Cyborg не разрешает агенту больше, чем человек в своём Claude Code.** Инструменты встроенных плагинов агент зовёт без вопроса: они проверены в поставке, и сервер `cyborg` отдаёт только их, поэтому `allow: ["mcp__cyborg"]` в настройках, которые пишет `agent-claude-code`, разрешает ровно инструменты поставки. Доступ шире каталога сессии даёт `--add-dir` из `extraDirs` запроса `launch`: файлы этих каталогов агент читает без вопроса, а их skills, команды и субагенты попадают в его контекст; сегодня `sessions` каталоги не передаёт. Режим разрешений, `deny` и `ask` Cyborg не задаёт, флагов `--permission-mode` и `--dangerously-skip-permissions` не передаёт. Остальные инструменты агента подчиняются режиму, который выбрал человек, а его правила складываются с правилами Cyborg, а не заменяются ими.
- **Инструменты стороннего плагина.** В сервер `cyborg` они не попадают. Свои инструменты сторонний плагин даёт своим сервером MCP, и агент должен видеть этот сервер, только если он объявлен в манифесте плагина; необъявленный в настройки MCP сессии не попадает. «Не виден» значит, что агент о сервере не знает, а не что Claude Code спросит при вызове: описание инструмента попадает в контекст агента до вызова и само может нести инъекцию. Объявленный сервер в `allow` не входит: его вызовы спрашивает Claude Code, если человек не разрешил их правилом `mcp__<сервер>__*` в своих настройках. Поле манифеста для такого сервера ещё не заведено: оно придёт с окном согласия на втором этапе.
- **Граница prompt injection.** Ядро не закрывает инъекцию через внешние данные: файл репозитория, MR, тикет и вывод команды остаются недоверенным текстом в контексте агента. Cyborg не ослабляет режим разрешений агента и не даёт ему инструментов шире его собственных прав; что агент делает с тем, что ему разрешено, решает режим разрешений, который выбрал человек. Cyborg его не ужесточает и не ослабляет.
- **Что остаётся на ревью поставки.** Инструменты поставки идут без вопроса, поэтому встроенный инструмент, который отдаёт данные наружу, проверяется при добавлении в поставку. Сегодня инструмент один: кнопки следующих шагов, без выхода наружу.

Устройство правила и угрозы У-27 - У-30, У-46 описывают [SAD, 3.7](https://github.com/dex-it/cyborg-harness/blob/master/docs/04-architecture/design/sad.md#агент-в-модели-доверия) и [модель угроз](https://github.com/dex-it/cyborg-harness/blob/master/docs/04-architecture/design/threat-model.md#54-агент).

## Секреты

Секреты держатся на двух ролях. Хранилище ядра (шифрование ОС через `safeStorage`) - корень доверия: ключи хранятся как `<плагин>/<ключ>`, каждый плагин видит только свои. Без шифрования ОС вызов получает `Unavailable`, а не запись открытым текстом. Источник секретов внешней системы - обычный плагин, и хранилище ядра он не подменяет: иначе он видел бы секреты всех плагинов. Подробнее - [права и секреты](/features/permissions/).
