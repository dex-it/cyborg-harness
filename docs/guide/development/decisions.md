## Статусы

В шапке каждого документа есть поле `status`:

| Статус | Значение |
|---|---|
| `review` | Решение составителя записано и реализовано в коде, владелец его ещё не принял |
| `proposed` | ADR фиксирует решение автора SAD по спорному пункту и остаётся таким до приёмки владельцем |
| принято | Владелец сменил статус в шапке |

SAD и ADR сейчас в статусах `review` и `proposed`. Приёмка владельцем входит в условия готовности эпика.

## ADR

Номера идут не подряд: в каталоге нет ADR-CH-0006, 0009, 0010, 0011 и 0013. Номера не переиспользуются: ADR-CH-0006 (перенос Cyborg «душителем» с паритетом) снят, в харнесс не вошёл; ADR-CH-0009, 0010, 0011 и 0013 при слиянии с master 2026-11-06 влиты в ADR-CH-0001, 0005, 0003 и 0007 ([ресёрч-2, раздел 8](https://github.com/dex-it/cyborg-harness/blob/master/docs/research/sad2-validation.md#8-что-изменено-в-пакете-по-итогам)).

| ADR | Решение | Статус |
|---|---|---|
| ADR-CH-0001 | Своё компактное ядро без предметной области, все функции - равные плагины, без Cordis | `review` |
| ADR-CH-0002 | Манифест читается до запуска кода; API плагинов, контракты и разделы `config` и `state` версионируются семантически | `review` |
| ADR-CH-0003 | Изоляция сбоев и рендера - для всех, доступа - процесс на плагин во втором этапе; к ОС только через `ctx.os` | `review` |
| ADR-CH-0004 | Агент - обычный плагин, поставщик `cyborg.agent`; pty запускает потребитель | `review` |
| ADR-CH-0005 | Контракты и команды в манифесте, граф до запуска кода, кратность у потребителя; без шины событий | `review` |
| ADR-CH-0007 | Ядро знает роды областей, вид живёт в своём `<iframe>`, сочетания объявлены в манифесте | `review` |
| ADR-CH-0008 | Терминология: «плагин Cyborg» и плагин внешнего агента, который ставится его командой, - разные вещи; роли - поставщик и потребитель | `review` |
| ADR-CH-0012 | pty держит ядро в отдельном pty-хосте; вывод к виду идёт мимо хоста плагина | `proposed` |
| ADR-CH-0014 | Секреты: хранилище ядра - корень доверия, внешний источник - плагин, в `config` только ссылка | `proposed` |

## Главные решения коротко

- Ядро не знает предметной области. Агент, сессии, файлы, проекты и трекеры - обычные плагины, а поставка приложения - список встроенных плагинов.
- Плагины связаны контрактами, объявленными в манифесте, и проверка идёт до запуска кода. Общих сервисов и шины нет.
- Изоляция сбоев и рендера действует с первого этапа. Изоляция доступа (процесс на плагин, окна согласия, установка) - второй этап, он начинается по поводу: плагин от автора вне команды или каталог плагинов.
- Один воркспейс - одно окно, один процесс на воркспейс; процессов с общим `userData` может быть несколько ([D-00](https://github.com/dex-it/cyborg-harness/issues/21), строка 5).
- Рендерер плагина - `<iframe>` с origin по группе рендера.
- pty держит ядро в отдельном процессе, вывод идёт из него прямо во фрейм.
- Пакеты выходят в npm-scope `@cyborg-harness`: `@cyborg-harness/contracts`, `@cyborg-harness/core`, `@cyborg-harness/electron`, `@cyborg-harness/testing`; scope `@cyborg` на npmjs.com занят посторонним ([D-00](https://github.com/dex-it/cyborg-harness/issues/21), строка 3).

Объяснение каждого решения - в разделах [Как это устроено](/concepts/).

## Спорные пункты

Семнадцать пунктов, которые разбирались с автором SAD и владельцем. Исход каждого записан в строке «Решение» файла спорных пунктов.

| Группа | Пункты | Исход |
|---|---|---|
| Расхождения с текстом автора | кто держит pty; origin фрейма; что даёт второй этап; модель процессов и окон; перехват клавиш; хвост pty или снимок | pty-хост принят; origin по группе рендера; один воркспейс - один процесс, процессов несколько; клавиши подтверждены настоящими нажатиями, хвост или снимок решает спайк |
| Чего в SAD не было | владелец git; границы трекеров; вклады в меню и условные сочетания; промпты и кнопки; полоса кнопок; привязка задачи к сессии | закрыты правилом 11: контракт вклада объявляет владелец сущности или вида, вкладчик зависит от владельца |
| Решения владельца | сторонние плагины и второй агент; трекеры по CLI или HTTP; бюджеты и база замеров | открыты |
| Мелочи до контрактов | область `path:open`, `config:reveal`, копия повреждённого файла, префикс `experimental_` | команда ядра «показать файл воркспейса», копия `.corrupt-<время>`, `experimental_` не заводится; `path:open` - область `any` права `shell` |

## Открытые вопросы

Раздел 8 SAD ведёт открытые вопросы, закрытые зачёркнуты. Решения, которые блокируют работу, собраны в одной задаче эпика (D-00) и вносятся в SAD по мере ответов. Здесь они названы темами, без выбора варианта:

- форма API: вклады плагинов в меню, сочетания с условием, отмена запросов между плагинами;
- бюджеты горячих путей и против чего их мерить;
- нужна ли Windows в первой версии;
- сколько экземпляров и воркспейсов держит приложение;
- что держит экран терминала после перезапуска хоста;
- политика загрузки плагинов из каталога пользователя на первом этапе;
- опасные флаги программ, которым выдано право `process` или `pty`;
- где объявлять поля секций настроек проекта и как связывать сессию с проектом;
- установка сторонних плагинов: источник, подпись, повторное согласие при расширении прав;
- общий набор тестов контрактов для всех поставщиков.

Пока вопрос не закрыт, страницы этого сайта описывают общее поведение без выбора варианта.

## Как принимается решение

1. Вопрос формулируется в задаче или в спорных пунктах, с позициями и проверкой: замером, разбором аналогов или кодом.
2. Ответ записывается в SAD (вопрос снимается из раздела 8), при необходимости в ADR и в «Решение» спорного пункта.
3. Если ответ меняет видимое автору плагина, правится и SRS.
4. Владелец меняет статус документа.
