Изменение считается готовым, когда зелёные пять проверок: сборка, типы, линтер, тесты и дымовой тест окна. Первые четыре идут на любой машине, пятому нужен дисплей.

| Команда | Что проверяет |
|---|---|
| `npm run build` | собирает стенд playground в `playground/dist`; перед ним, `typecheck`, `lint` и `test` сами идут `build:core` (пакет ядра) и `build:electron` (адаптер Electron) |
| `npm run typecheck` | строгие типы ядра, браузерной части элементов `cy-*`, адаптера Electron, шаблона плагина (`templates/plugin`) и стенда; в том числе файлы, где строка под `@ts-expect-error` обязана не компилироваться |
| `npm run lint` | ESLint со `strictTypeChecked`, ноль предупреждений; идёт по процессу на пакет (`scripts/lint.mjs`), чтобы программы TypeScript всех пакетов не копились в одной куче Node: пик около 1 ГиБ вместо 2,1 ГиБ |
| `npm test` | модульные, сценарные и стресс-тесты на встроенном `node:test` |
| `npm run smoke` | дымовой тест окна по DevTools Protocol |
| `npm run demo` | сценарии ядра в консоли с пошаговым режимом `--step` |
| `npm run spike`, `npm run spike:hosts`, `npm run spike:gateway` | замеры фреймов, хостов и шлюза, не тесты; `spike:gateway` - проверка бюджета для CI по медиане трёх прогонов с включённой трассой операций (`--trace=off` - база) |
| `npm run check:docs-links` | относительные ссылки и якоря в `docs/` и `README.md`: путь с точным регистром, заголовок-цель; падает на битой |
| `npm run check:budgets -- --gateway gateway.json [--hosts hosts.json]` | сверка JSON замеров (`spike:gateway --json`, `spike:hosts --json`) с порогами `playground/budgets.json` |
| `npm run release -- plan v0.1.0 --rehearsal` | репетиция выпуска: что выйдет по тегу, что пропущено, чего не хватает (см. «Релизы» ниже) |

## Типы и линтер

Проверка типов использует TypeScript 7 из алиаса `typescript7`, а пакет `typescript` - это TS 6 под API `typescript-eslint`. Поэтому `npx tsc` - не тот компилятор: запускайте `npm run typecheck`.

Отключить правило линтера можно только директивой с причиной после `--`. Параметры-свойства конструктора и `enum` не пишут: Node снимает только стираемый синтаксис. Импорты пишутся с расширением `.ts`, потому что тесты идут на Node без сборки.

## Тесты

`npm test` запускает файлы `core/test/*.test.ts`, `contracts/test/*.test.ts`, `testing/test/*.test.ts`, `electron/test/*.test.ts`, `playground/src/**/*.test.ts`, `playground/test/*.test.ts`, `tools/cyborg-plugin/test/*.test.ts` и `scripts/test/*.test.ts` (проверка ссылок, бюджеты, выпуск, устройство workflow) с общим сроком 120 секунд на тест (`--test-timeout`). Зависший тест падает под своим именем и не снимает всю задачу. Флаг `--test-force-exit` закрывает другой отказ: файл, у которого после последнего теста остались слежение за файлами, хост или программа, не выходил, и задание молчало до отмены по лимиту. Теперь процесс файла завершается сам, а причину надо искать в тесте, а не в зависшем задании.

## Время в тестах

Тест ждёт события, а не срока. Фиксированная пауза («подождём 20 мс») на нагруженном раннере то коротка и красит тест, то впустую длинна. Правила:

- **Условие вместо паузы.** Ждите наблюдаемого факта через `waitFor(что, проба, { timeout, interval })` из `core/test/wait-for.ts`: проба зовётся, пока не вернёт значение, предел по умолчанию 15 секунд, а при отказе в сообщении стоят название условия, предел, число проб и последняя ошибка пробы. Готовое условие возвращается сразу, поэтому запас в пределе ничего не стоит. Собственные циклы `for (...) await sleep(20)` и локальные `until` не заводят. Адаптеру Electron нельзя импортировать из-за пределов `electron/`, поэтому в `electron/test/` лежат побайтовые копии `wait-for.ts` и `run-command.ts`; расхождение ловит `core/test/wait-for.test.ts`.
- **Пауза остаётся только для «ничего не произошло».** Проверка отсутствия события (после `dispose` событий нет) ждёт короткий срок и ничем не заменяется; такие паузы идут после того, как положительная часть теста дождалась своего.
- **Срок зависания хоста.** В тестах сторожа срок молчания хоста до `hang` берут с запасом на медленный запуск: тесты, которые ждут зависания, - 1,5 с, остальные (падение, убийство, отклонения) - 30 с, чтобы лишнее `hang` не записалось раньше `crash`. Простой цикла событий самого ядра сторож в срок не засчитывает (тик, опоздавший сверх интервала, вычитается из молчания хоста, #146), но свежий хост на занятом раннере по-прежнему получает запас. Срок в 400 мс принимал свежий хост на занятом macOS за зависший.
- **Ловушка хоста взводится после ответа.** Фикстура, роняющая хост на «следующее сообщение», получала в качестве него пинг сторожа, обогнавший ответ на команду. Ловушку снимает событие окна `system`, которое тест шлёт после ответа.
- **Ядро выгружается всегда.** Тест, поднимающий ядро с `ctx.os`, хостами или pty, выгружает его и при падении: `t.after(() => k.unload())`, `try/finally` или `trackKernels()` из `core/test/kernels.ts` (после каждого теста файла). Иначе упавшая проверка оставляет слежение и программы живыми.
- **`fs.watch` на macOS.** FSEvents начинает доставку не в тот миг, когда `fs.watch` вернулся: запись сразу после него теряется, и событие не придёт никогда. Тест пишет пробные записи до первого отклика (`armed` в `core/test/os.test.ts` и `playground/test/agents.test.ts`) и лишь потом проверяет поведение. Среди имён изменённых может быть и имя самого каталога - тест на него не опирается.
- **Внешние команды.** `npm`, `tsc`, `tar`, `git` в тестах запускают через `runCommand` и `tryCommand` из `core/test/run-command.ts`: предел 90 с с `SIGKILL`, при отказе в сообщении команда, каталог, stdout и stderr.

Новый тест на время проверяют серией: файл гоняют 20 раз под нагрузкой (например, по две пустые петли `while :; do :; done` на ядро), и ни один запуск не должен упасть.

Серия 2026-11-10 (#169, 10 ядер, 20 пустых петель, по 20 прогонов файла, падений нет): `playground/test/agents.test.ts` после перехода на пробные строки вместо паузы 300 мс, `core/test/hosts.test.ts` с `QUIET_MS` 5 с, `core/test/journal.test.ts`, `core/test/untrusted-input.test.ts`, `electron/test/secrets-file.test.ts`. Остальные оставленные паузы - время самого предмета или проверка «ничего не случилось», они серию пережили.

:::note[Проверки чистоты]
Ядро не знает предметной области, не импортирует Electron и не тянет зависимости из npm. Это проверяют тесты, а не ревью. Отдельные тесты закрепляют, что секрет не попадает в журнал, `config` и `state`, и сверяют публичные экспорты пакетов и снимок API плагина.
:::

## Дымовой тест окна

`npm run smoke` запускает собранный стенд с временным каталогом данных и ведёт его по DevTools Protocol. В нём проверяется то, что без настоящего Electron не проверить:

- плагины в нескольких хостах `utilityProcess`, перехват сочетаний и конфликт, обмен сообщениями через три хоста;
- виды во фреймах: мост, лента журнала, чужая команда отклонена, тема до `mount` и при смене;
- права `ctx.os`: отказ вне прав с записью в журнале, права словами, псевдотерминал;
- терминал вида по билету: вывод и ввод идут мимо хоста и переживают зависание хоста и его перезапуск;
- сторож: падение и зависание хоста;
- слой окна: диалоги `ask` и `menu`, замок, порядок фокуса по `F6` и `Shift+F6`;
- CSP вида (K-05): заголовок на ответе у видов с флагом `ui.inlineStyles` и без, инлайн-стиль применяется только с флагом, встроенный скрипт не выполняется, запросы наружу и на origin другой группы блокируются, сосед по группе не встраивается в `<iframe>`, а его документ из группы доступен;
- элементы `cy-*`: определены до `mount`, работают под строгой CSP в виде без флага инлайн-стилей, клавиши и события;
- воркспейс: замок с pid, второй запуск того же воркспейса отдаёт фокус первому, другой воркспейс открывается своим процессом с общим `userData`, «Недавние»; общие файлы `userData` под замком записи (`core/test/shared-files.test.ts`, `core/test/instance.test.ts`, `electron/test/secrets-file.test.ts`).
- шаблон плагина `templates/plugin`: собран `cyborg-plugin`, лежит в каталоге пользователя, активен, вид открыт, кнопка вида выполняет команду.

Проверка с настоящим `claude` пропускается, если не задана переменная `CYBORG_SMOKE_CLAUDE`. Сочетания в тесте подбираются под платформу: на macOS это `Shift+Meta+<клавиша>`, на Linux `Ctrl+Shift+<клавиша>`.

## CI

Workflow `.github/workflows/ci.yml` запускается на каждый pull request и на пуш в `master`.

| Шаг | macOS (`macos-latest`) | Linux (`ubuntu-24.04`) |
|---|---|---|
| `npm ci --ignore-scripts` на Node 24 и сборка `node-pty` под Electron с кэшем по lock-файлу (`.github/actions/install`) | да | да |
| Бинарник Electron, кэш по lock-файлу и скачивание с повтором (`node_modules/electron/install.js`, 4 попытки) | да | да |
| `npm run build`, `typecheck`, `lint`, `npm test` | да | да |
| Шаблон плагина: `cyborg-plugin check`, `build`, `pack` на `templates/plugin` | да | да |
| Пример адаптера Electron из README собирается (`node --test electron/test/example.test.ts`) | да | да |
| Дымовой тест | `node playground/scripts/smoke.mjs` | `xvfb-run --auto-servernum node playground/scripts/smoke.mjs --no-sandbox` |

Лимит - 15 минут на каждую ОС, а на `npm test` отдельно 8 минут (обычный прогон - около минуты); права токена - только чтение. Бинарник Electron скачивается отдельным шагом до тестов: раньше он тянулся лениво при первом `require('electron')` в тесте, и сбой сети (504 с GitHub Releases) красил тест. Зависший тест называется по `--test-timeout`, а не молчаливым обрывом задания. Действия закреплены по SHA коммита, новая сборка той же ветки отменяет прежнюю. Матрица идёт с `fail-fast: false`: падение на одной ОС не прячет результат другой.

Кроме `ci.yml` есть `docs-site.yml` для сайта, см. [Сайт документации](/development/docs-site/).

## Бюджеты, ссылки, зависимости

Кроме задания `check` (таблица выше) `ci.yml` держит три задания; все идут параллельно с ним, поэтому лимит `check` в 15 минут не растёт.

| Задание | Что делает | Кого красит |
|---|---|---|
| `budgets` (macOS и Linux) | собирает стенд, гоняет `spike:gateway` и `spike:hosts` с `--json`, `npm run check:budgets` сверяет числа с `playground/budgets.json`; таблица - в сводке запуска | PR, где цена шлюза `ctx.os` на Linux выше порога блокировки (бюджет с запасом 1,5 на шум раннера) на охраняемых путях; при превышении замер повторяется один раз, красным считается второе подряд |
| `docs-links` | `scripts/check-docs-links.ts` по `docs/` и `README.md` без установки зависимостей | битый относительный путь, регистр имени файла не совпал с диском, нет заголовка-якоря в файле-цели |
| `audit` | `npm audit --omit=dev --audit-level=high` по каждому пакету для потребителя (контракты, ядро, адаптер, тест-кит, `cyborg-plugin`) и отдельным шагом по корню, то есть по стенду playground; оба блокируют | уязвимость уровня high и выше в зависимостях пакета для потребителя |

Dependabot (`.github/dependabot.yml`) раз в неделю присылает PR на npm (корень и `site/`) и на действия GitHub Actions; минорные и патч-обновления идут одной группой, мажорные отдельно.

**Пороги бюджета.** Числа решения владельца (D-00, строка 6, 2026-11-07) лежат в `playground/budgets.json` со ссылкой на решение и норму NFR-CH-1001: вызов через шлюз до 64 КиБ - не больше 1 мс на p99 (цена: вызов из плагина минус то же действие без шлюза), событие `fs.watch` - не больше 5 мс сверх склейки 50 мс, мера - медиана трёх прогонов. Что блокирует, записано там же. Платформа - `gateway.blocking` (сейчас Linux): раннер macOS шумит (замер на рабочей машине шёл при load average 20-29, [macos-check.md](https://github.com/dex-it/cyborg-harness/blob/master/docs/05-verification/macos-check.md)), а у `fs.watch` на macOS цена отрицательна. Пути - `gateway.guarded` (`fs.readText`, `fs.watch`, `pty.write`, `secrets.get`): `fs.readText.cold` на раннере GitHub упирается в диск (p99 2-3 мс против 0,3-0,4 мс у горячего чтения), а у `net.fetch` цена тонет в шуме вычитания (от -2 до +1,4 мс), они идут справочно. Запас - `gateway.blockingMargin` (1,5): строка выше бюджета, но ниже бюджета с запасом, зелёная и помечена в таблице; красит значение выше бюджета с запасом. Регрессия шлюза на 2 мс поднимает все охраняемые пути выше 2 мс и краснит PR (проверено на настоящем замере). Память хоста и старт окна порогов не имеют (остаток строки 6): строки печатаются как информационные, пока в `hosts.limits` стоит `null`; число для платформы и её имя в `hosts.blocking` включают проверку. Память на macOS (`footprint`) и на Linux (PSS) - разные меры, поэтому пороги у платформ свои. Вывод терминала до кадра (16 мс) принят, но не измеряется: запись `notMeasured` в файле.

**Ссылки.** Проверяются только относительные ссылки и якоря; адреса `https:` и абсолютные пути сайта (`/development/...`) нет: первые живут вне репозитория, вторые проверяет `site/ npm run verify`. Якорь строится как у GitHub (нижний регистр, без знаков препинания, повторы с `-1`). Новый документ с битой ссылкой не пройдёт ни `docs-links`, ни `npm test`.

**Раннер Windows** в матрицу не входит: Windows вне первой версии (D-00, строка 7, вопрос 12 SAD). CI проверяет macOS и Linux.

## Релизы

Пакеты `@cyborg-harness/contracts`, `@cyborg-harness/core` и `@cyborg-harness/electron` выходят в npm (scope `@cyborg-harness`) по тегу `v<версия>`, workflow `.github/workflows/release.yml`, логика - `scripts/release.ts`. `@cyborg-harness/testing` и `cyborg-plugin` в релиз не входят.

1. **Версия.** Версии пакетов независимы. Тег `v0.1.0` выпускает пакеты, чья версия `0.1.0`, остальные пропускает; тег, которому не соответствует ни один пакет, отвергается. Версия `-dev` (линия разработки контрактов) не выпускается.
2. **Перед тегом.** В `CHANGELOG.md` каждого выпускаемого пакета `Unreleased` переименован в `## <версия> - <ГГГГ-ММ-ДД>`, версия в `package.json` повышена тем же коммитом. Без записи проверка выпуска падает.
3. **Проверка (`verify`).** `plan` сверяет тег с `package.json` и `CHANGELOG.md`, отвергает `private` и пакет без `publishConfig.registry`; затем сборка пакетов, `check:contracts`, `npm pack` (архивы в артефакт запуска) и `npm publish --dry-run`. Те же шаги идут на pull request по файлам выпуска и вручную (`workflow_dispatch` с тегом) как репетиция, публиковать они не умеют.
4. **Публикация (`publish`).** Только на push тега, только при переменной репозитория `RELEASE_PUBLISH=true`, в окружении `npm-publish` (владелец включает обязательных ревьюеров и ограничение «только теги `v*`»), только если коммит тега входит в `master`. Публикуются архивы, которые собрал `verify`, порядок - контракты, ядро, адаптер; предварительные версии получают метку `next`.
5. **Права.** `contents: read` у обоих заданий; токен `NPM_TOKEN` (гранулярный, только запись в пакеты scope) лежит в окружении `npm-publish` и виден единственному шагу публикации.

Что должен сделать владелец до первого выпуска: создать окружение `npm-publish` и секрет `NPM_TOKEN`, выбрать лицензию (сейчас у ядра, адаптера и тест-кита `UNLICENSED`, у контрактов поля нет; `workflow` предупреждает, но не блокирует), решить видимость пакетов (`publishConfig.access` равен `restricted`), поставить `RELEASE_PUBLISH=true`.
