## Окружение

Нужны Node.js 24, npm и git. Остальное ставит `npm ci`: он же пересобирает нативный модуль терминала `node-pty` под Electron (шаг `postinstall`).

```bash
git clone https://github.com/dex-it/cyborg-harness.git
cd cyborg-harness
npm ci
npm run build       # стенд в playground/dist
npm run typecheck   # типы ядра, элементов и стенда
npm run lint        # ESLint, ноль предупреждений
npm test            # тесты на node:test
npm start           # сборка и запуск стенда
npm run smoke       # дымовой тест окна (нужен дисплей)
```

Подробнее о проверках - в [Тестах и CI](/development/tests-ci/).

## Правила кода

- Ядро не импортирует Electron и ничего из стенда; стенд берёт ядро только через публичные точки входа.
- Плагин импортирует только `@cyborg-harness/contracts` и свои модули.
- Импорты пишутся с расширением `.ts`: тесты идут на Node без сборки.
- Параметры-свойства конструктора и `enum` не пишут: Node снимает только стираемый синтаксис.
- Не правят руками `node_modules/`, `playground/dist/` и `package-lock.json`.

## Цикл изменения

1. Заведите ветку от `master` с коротким именем по сути: `core-hardening`, `watchdog-blame`, `docs-site`.
2. Внесите изменение вместе с тестом: новое поведение закрепляется тестом ядра или стенда.
3. Если изменение видно автору плагина, поправьте SAD, ADR или SRS: правка документов - часть изменения, а не отдельная работа потом.
4. Прогоните сборку, типы, линтер и тесты. Дымовой тест идёт в CI на обеих платформах.
5. Откройте pull request в `master`. Заголовок называет суть одной фразой, описание - что изменено и как проверено.
6. Слейте после зелёного CI и ревью.

Задача закрыта, когда выполнены все пункты её «Критериев приёмки», а не когда слит код.

## Задачи, уровни и ключи

Работа ведётся задачами в GitHub Issues. У каждой есть уровень:

| Уровень | Что это | Метка |
|---|---|---|
| Эпик | Зонт над несколькими задачами, сам не делается, декомпозируется | `level: epic` |
| История | Крупная единица работы, закрывается несколькими PR | `level: story` |
| Задача | Единица работы, обычно один PR | `level: task` |
| Подзадача | Часть истории или задачи, отдельным PR не закрывается | `level: subtask` |

Задачи эпика привязаны к нему как подзадачи (sub-issues), поэтому список и прогресс видны на странице эпика. Заголовок задачи начинается с итерации и ключа: `[Iteration 2] [P-02] Ядро как пакет @cyborg-harness/core`. Ключ - стабильное имя, по которому задачи ссылаются друг на друга:

| Префикс | Группа |
|---|---|
| `D-` | Решения владельца и автора, блокирующие работу |
| `SP-` | Спайки: короткие исследования |
| `K-` | Ядро |
| `T-` | Технический долг и проверки |
| `P-` | Пакеты и документация |
| `PL-` | Пилоты: доказательство на ядре сценария Cyborg |

Тело задачи устроено одинаково: «Зачем», «Что сделать», «Где в коде и документах», «Критерии приёмки», «Зависимости и параллельность», «Размер и итерация», «Риски и вопросы».

## Метки

Метки работают группами `префикс: значение`.

| Группа | Значения |
|---|---|
| `type:` | `bug`, `feature`, `enhancement`, `refactor`, `research`, `architecture`, `pilot`, `security`, `chore`, `docs`, `deprecation` |
| `level:` | `epic`, `story`, `task`, `subtask` |
| `component:` | `contracts`, `core`, `electron-adapter`, `playground`, `plugins`, `tooling`, `ci`, `docs` |
| `priority:` | `critical` (ядро не запускается или ломает данные), `high`, `medium`, `low` |
| `status:` | `needs-triage`, `needs-info`, `needs-design`, `blocked`, `needs-review`, `needs-testing`, `duplicate`, `stale`, `wontfix` |
| `platform:` | `linux`, `macos`, `windows` |
| `effort:` | `s` (до 2 человеко-дней), `m` (3-8), `l` (больше 8, рассмотрите декомпозицию) |
| `iteration:` | `0`-`4` |

Есть и метки без группы: `breaking-change` (ломает API плагинов, манифест или формат данных), `regression`, `upstream` (причина в Electron, `node-pty`, Node или стороннем сервисе), `external-binary`, `credentials`, `dependencies`. Новая задача получает `status: needs-triage`.

## Вехи

Итерация - набор задач, которые ведутся параллельно. Следующая начинается, когда закрыты задачи, от которых зависят её первые. В GitHub итерациям соответствуют вехи:

| Веха | Содержание |
|---|---|
| Итерация 0: решения и спайки | снять блокеры до кода |
| Итерация 1: независимые доработки | то, что не упирается в чужие решения и общие файлы |
| Итерация 2: пакеты и форма API | ядро и адаптер становятся пакетами, закрепляется форма манифеста |
| Итерация 3: крупные узлы | самые тяжёлые куски |
| Итерация 4: пилоты Cyborg и заморозка API | доказать сценарии Cyborg, зафиксировать API 1.0 |

Состав итераций и критический путь - на странице [Дорожная карта](/development/roadmap/).

:::note[Общие файлы]
`core/src/kernel-types.ts`, `core/src/lifecycle.ts`, `core/src/kernel-context.ts` и `core/src/os-gateway.ts` правят многие задачи. Не ведите две такие правки параллельно: согласуйте порядок слияния в задачах.
:::

## Документы и их статусы

Корпус в `docs/` ведётся циклом «требования, разработка, фиксация истины». Идентификаторы с префиксом `CH-` (`BR-CH-001`, `FR-CH-1001`, `ADR-CH-0001`) не пересекаются с корпусом Cyborg. Статус в шапке документа: `review` и `proposed` значат, что решение записано составителем, но владелец его ещё не принял. Подробнее - на странице [Решения](/development/decisions/).
