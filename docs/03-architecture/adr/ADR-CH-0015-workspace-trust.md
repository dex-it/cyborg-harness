# ADR-CH-0015 Доверие к воркспейсу: значения, расширяющие права, ядро берёт только из слоя пользователя

> Решение составителя по задаче K-27 ([#87](https://github.com/dex-it/cyborg-harness/issues/87)), не согласовано с владельцем; ждёт приёмки. Строки в таблице D-00 ([#21](https://github.com/dex-it/cyborg-harness/issues/21)) у вопроса нет, он записан отдельной строкой. Записывает решение в [SAD, 3.7](../design/sad.md#37-безопасность-данных-и-контроль-плагинов), [3.5](../design/sad.md#35-изоляция-сбоев-хосты-и-сторож) и [3.10](../design/sad.md#310-главный-конфиг-и-состояние); закрывает У-40 [модели угроз](../design/threat-model.md) на этапе 1 с остатком.

## Decision Drivers

- Файл воркспейса приходит из репозитория команды или от коллеги; человек открывает его, не читая.
- Одно значение в таком файле не должно переносить токен человека на чужой хост и не должно сажать чужой код рядом со встроенным.
- Окна согласия на этапе 1 нет, подписи файлов нет (обе вещи вне задачи); решение не должно их требовать и не должно закрывать путь к ним.
- Воркспейс, который человек создал сам, ядро от присланного отличить не может: у файла нет признака происхождения.

## Context

Допущение модели угроз «файл воркспейса - решение человека» (У-40) верно, только пока воркспейс создан самим человеком. Ядро читает `config` в два слоя: `user` (`cyborg.json` в `userData`) и `workspace` (файл воркспейса); слой воркспейса перекрывает пользовательский ([SAD, 3.10](../design/sad.md#310-главный-конфиг-и-состояние)). Из значений config сегодня выводится одно право: хост `config:<поле>` в `net` ([SAD, 3.7](../design/sad.md#37-безопасность-данных-и-контроль-плагинов)). Корни областей приходят из среды приложения и диалога человека (`security.setRoots`, `granted` в `state`), программы - только из манифеста; из `config` они не берутся. Группы хостов `plugins.hosts` уже не сажают сторонний плагин в общий хост ни из какого слоя ([ADR-CH-0003](ADR-CH-0003-trust-and-isolation.md), п. 2). Группы рендера `plugins.uiGroups` ещё не заведены (K-04).

## Decision

1. **Узкий вариант: слой `user` - единственный источник значений, расширяющих права.** Файл воркспейса значения не подтверждает. Решение принимается по значению, а не по файлу целиком: признак «доверенный воркспейс» (как Workspace Trust в VS Code) не вводится. Слой назван одной константой, `TRUSTED_LAYER` в `core/src/config.ts`.
2. **Хост `config:<поле>`.** Шлюз берёт значение поля только из слоя пользователя. Значение из слоя воркспейса плагин видит в `ctx.config.get()`, как раньше, но `net.fetch` на этот хост получает `PermissionDenied`, запись `denied` называет поле и причину («задан в файле воркспейса, а хосты из настройки берутся только из файла пользователя»); та же строка видна в «Плагинах Cyborg». Если поле есть в обоих слоях, право даёт значение пользователя. Проверка: `core/test/workspace-trust.test.ts` («config:<поле> из слоя воркспейса не пускает net.fetch…», «воркспейс перекрывает значение для плагина, но не для права net», «правка файла воркспейса извне…»).
3. **Плагин не переносит значение воркспейса в слой пользователя.** `config.get()` отдаёт слитое значение; его запись целиком в слой пользователя сделала бы чужой хост доверенным. Защита поля `net` от записи плагина в слой пользователя сверяет значение только с этим слоем; запись в слой воркспейса права не расширяет и, как раньше, может повторить значение любого слоя: иначе миграция раздела и его пересохранение выключили бы плагин в воркспейсе команды. Проверка: `core/test/workspace-trust.test.ts` («плагин не переносит значение из слоя воркспейса…»), `core/test/os.test.ts` («net config:<поле>: плагин не пишет в поле хоста…»).
4. **Группы хостов.** Сторонний плагин в группе из любого слоя остаётся в своём хосте, запись `host-isolated` ([SAD, 3.5](../design/sad.md#35-изоляция-сбоев-хосты-и-сторож)); код не меняется, правило закреплено тестом. Группа только из плагинов поставки действует из обоих слоёв: права она не расширяет, цену (зависание соседа) показывает `host-own-grouped`. Проверка: `core/test/workspace-trust.test.ts` («plugins.hosts из файла воркспейса…»).
5. **Правило для новых источников.** Любое поле config, из которого ядро выводит право (хост, корень, программа, группа хостов или рендера со сторонним плагином, привязка к контракту), читается через `TRUSTED_LAYER`. Поле в манифесте плагина этого правила не касается: манифест ставит человек вместе с плагином.
6. **Подтверждение человека (этап 2, окно согласия) хранится в `userData`, а не в файле воркспейса.** Файл, который подтверждает сам себя, ничего не защищает. Запись - отдельный файл ядра рядом с `cyborg.json`: каталог приложения шлюз закрывает от плагинов, а раздел `state` плагина для согласия не годится. Ключ записи - `workspaceKey` (хеш от `realpath` файла воркспейса) и значение права, а не файл целиком: правка файла после согласия не расширяет права молча. Реализации в этой задаче нет.

## Пересечения с задачами эпика

- **K-04 (группы рендера).** `plugins.uiGroups` с именованным сторонним плагином читается только из слоя пользователя; группа воркспейса со сторонним плагином не действует, сторонний остаётся в своём origin, и ядро пишет запись по образцу `host-isolated`. Группа только из плагинов поставки читается из обоих слоёв. Читать слои надо через ту же константу и тот же разбор, что `plugins.hosts`.
- **K-20 (несколько воркспейсов и экземпляров).** Слой `user` один на `userData` и общий для воркспейсов; слой воркспейса у каждого свой и всегда недоверенный. Подтверждение этапа 2 привязано к `workspaceKey`, поэтому согласие на один воркспейс на другой не переходит, а два экземпляра с общим `userData` читают один файл согласий; запись в него идёт под замком; у `cyborg.json` замка сегодня нет (замок берётся только на файл воркспейса), и K-20 заводит его для обоих файлов. Смена воркспейса в одном окне заново берёт значения из слоя пользователя без памяти о прошлом воркспейсе.

## Consequences

- Positive: присланный воркспейс не расширяет сеть и не меняет границу доверия хостов; решение не требует признака происхождения и ничего не хранит; правило обратимо одним изменением `TRUSTED_LAYER` и точек чтения.
- Negative: сценарий «команда кладёт адрес Jira в воркспейс» ломается. Человек повторяет значение у себя: `settings.<плагин>.<поле>` в `cyborg.json` в `userData`; причину отказа называет запись журнала. Плагин не может сделать это за человека (поле `net` плагин не пишет). Окно согласия этапа 2 сведёт это к одному нажатию.
- Risks: человек, скопировавший чужой `cyborg.json` целиком, переносит доверие вместе с файлом; воркспейс, созданный самим человеком, от присланного ядро не отличает, поэтому и у своего воркспейса значение придётся задать в слое пользователя. Остальное ядро берёт из файла воркспейса, не проверяя: `plugins.enabled` воркспейса перекрывает пользовательский и включает любой установленный плагин (остаток У-40).

## Alternatives Considered

- **Широкий вариант: признак доверенного воркспейса.** Pros: сценарий команды работает после одного согласия. Cons: признак хранится по воркспейсу, а не по значению: правка файла после согласия молча расширяет права; нужно окно согласия (этап 2) и подпись или хеш файла; воркспейс, созданный самим человеком, всё равно требует признака. Why rejected: цена выше задачи, а ошибка дороже; вариант можно добавить поверх узкого, когда появится окно.
- **Подтверждение хранить в самом файле воркспейса.** Why rejected: файл подтвердил бы сам себя.
- **Убрать `config:<поле>` совсем, оставить только хосты манифеста.** Cons: плагин с серверами на стороне человека (Jira) перестаёт работать без правки манифеста. Why rejected: ломает цель интеграций по HTTP API ([SAD, 3.7](../design/sad.md#37-безопасность-данных-и-контроль-плагинов)).
