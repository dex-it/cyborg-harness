# ADR-CH-0016 Права вызывающего у команд: исполнитель объявляет `callers`, по умолчанию команду зовёт пользователь

> Решение составителя по задаче K-22 ([#82](https://github.com/dex-it/cyborg-harness/issues/82)); принято по поручению владельца 2026-11-09. Записывает форму манифеста, которую задача отдавала на решение до K-21, и закрывает угрозу У-15 [модели угроз](../design/threat-model.md); У-14 закрыта частично. Правило сводится в [SAD, 3.4 и 3.7](../design/sad.md#34-связь-между-плагинами).

## Decision Drivers

- Команда `sessions.new` запускает агента с правами пользователя. Плагин без единого права не должен получить это посредником ([У-15](../design/threat-model.md)).
- Защита должна жить у **исполнителя**: плагин-потребитель, который сам перечисляет чужие команды, видит свои вызовы, но не защищает того, кого зовут, и не может отказать другому вызывающему.
- Решение формы манифеста - до K-21: форму потом дорого менять, потому что её копируют в манифесты сторонних плагинов ([ADR-CH-0002](ADR-CH-0002-manifest-and-compatibility.md)).
- Минимально обратимая форма: расширить доступ позже можно без поломки манифестов, сузить - нельзя.

## Context

`ctx.commands.run` вызывает любую зарегистрированную команду. Ядро до этого решения сверяло только схему аргументов; право вызывающего у команд не проверялось, `guard` ([ADR-CH-0005](ADR-CH-0005-plugin-interaction.md), п. 8) был только у членов контрактов. Источник вызова ядро знает по каналу хоста: пользователь (палитра, клавиши, меню, уведомление) идёт через `Kernel.run`, вид плагина - через приложение, и оно пускает его только к командам своего плагина ([ADR-CH-0007](ADR-CH-0007-plugin-ui.md), п. 3), главная часть плагина - через сообщение `run` своего хоста.

## Decision

1. **Поле `callers` у команды в манифесте исполнителя: `"user"` (по умолчанию) или `"plugins"`.** `user` - команду зовут палитра, клавиши, меню, клики уведомлений, вид самого плагина и его главная часть. `plugins` - ещё и главные части других плагинов. Любое другое значение отклоняет разбор манифеста. Короткая запись списком (`"commands": ["a.b"]`) - команды `user`. Проверка: `core/test/command-callers.test.ts` («манифест: callers…», «манифест: неизвестное значение callers…»).
2. **Вызов из главной части чужого плагина к команде с `callers: "user"` - `PermissionDenied`**, запись `denied` у вызывающего с `reason: 'command-callers'`; обработчик не вызывается, спящий (`lazy`) исполнитель не будится. Своя команда из своей главной части разрешена. Проверка: `core/test/command-callers.test.ts` («команда с callers по умолчанию…», «отказ по callers раньше, чем ядро будит спящего…»).
3. **Вызывающего называет канал.** Сообщение `run` теперь несёт `caller`, и ядро принимает его, только если плагин живёт в хосте-отправителе (`mine`), как у `invoke`. Запрос без `caller` отклоняется схемой: назваться «пользователем» из хоста нельзя, у пользователя другой вход, `Kernel.run`. Проверка: `core/test/trust.test.ts` («run: вызывающего называет канал…»).
4. **Команда с `callers: "plugins"` может объявить `guard`**: `{ "guard": { "fs.read": "0.path" } }`, те же права и тот же разбор аргумента, что у члена контракта (`fs.read`, `fs.write`, `shell`, `secrets.ref`). Ядро сверяет аргумент с правом **вызывающего** до передачи вызова; исполнитель потом работает своими правами, то есть действует пересечение. `guard` проверяет только вызовы чужих плагинов: пользователь сам назвал путь в палитре, и свой плагин себя не проверяет. `guard` без `callers: "plugins"` - ошибка манифеста: у закрытой команды он ничего бы не проверял. Проверка: `core/test/command-callers.test.ts` («guard команды…»).
5. **Разбор манифеста сверяет `guard` со схемой аргументов.** Без `field` аргумент должен быть `string` или `any`, с `field` - `record` или `any`, и такой аргумент должен быть в `args` или `rest`; иначе ошибка манифеста: каждый чужой вызов такой команды получил бы `Invalid`. Проверка: `core/test/command-callers.test.ts` («манифест: неизвестное значение callers…»).
6. **Команду исполняет тот, кто её объявил, и она одна.** Пространство имён проверяется префиксом `${id}.`, поэтому плагины `a` и `a.b` оба могли объявить `a.b.run`, и владельцем становился зарегистрировавший первым. Граф отвергает обоих (причина `command` в `rejected`), а если один из них встроенный - только остальных: сторонний плагин не снимает чужую поставку. Вид плагина и клик по его уведомлению идут через `Kernel.runOwn(pluginId, команда, …)`: ядро исполняет только команду этого плагина, иначе `PermissionDenied`; «объявлено в моём манифесте» владельца не доказывает. Проверка: `core/test/graph.test.ts` («команда в двух манифестах…»), `core/test/command-callers.test.ts` («команда в двух манифестах: …runOwn…»).
7. **Права словами.** У исполнителя в списке прав есть строка «другие плагины могут звать команды: …» (`describeOpenCommands`), чтобы человек видел, что плагин открывает наружу. Проверка: `core/test/command-callers.test.ts` («права словами…»), `electron/test/plugins.test.ts`.

## Consequences

- Positive: привилегированная команда по умолчанию закрыта для плагинов; защита у исполнителя и не зависит от потребителя; пользовательские вызовы (палитра, клавиши, меню, вид) работают как раньше, а открыть команду плагинам - явный выбор автора исполнителя; отказ можно только смягчить (`user` -> `plugins`), не ломая манифесты.
- Negative: команды, которые плагины уже зовут друг у друга из главных частей, нужно пометить `callers: "plugins"` (в playground таких нет; в тестах ядра - `calm.echo`, `lock.now`, `victim.open`). Для стороннего плагина это ломающее изменение API, пока таких плагинов нет.
- Risks: `guard` не защищает аргумент, который не путь и не ссылка (идентификатор сессии, билет): их остаётся проверять самому исполнителю. Значение `callers` по смыслу - для главных частей; права вида не расширяются: вид зовёт только команды своего плагина, и это держит ядро (`Kernel.runOwn`, п. 6), а не только приложение.

## Alternatives Considered

- **Потребитель перечисляет чужие команды (`"consumes": { "commands": [...] }` или `commandsCalled`).** Pros: человек видит в правах потребителя, какие чужие команды тот зовёт. Cons: не защищает исполнителя, который не знает, кто его позовёт и что ему можно, а плагин без записи в манифесте можно написать и без объявления - защиту всё равно надо проверять у исполнителя. Why rejected: задача рекомендует `callers` у исполнителя; список у потребителя можно добавить позже как видимость поверх, не меняя `callers`.
- **Список конкретных плагинов в `callers` (`"callers": ["viewer", "files"]`).** Cons: исполнитель должен знать плагины заранее, сторонний плагин оказывается за бортом, имя плагина в манифесте исполнителя - зависимость от чужого id. Why rejected: избыточно для итерации 2; `"plugins"` можно уточнить списком позже, не ломая прежнее значение.
- **По умолчанию `plugins`, закрывать явно (`"user"`).** Cons: забытая метка у привилегированной команды открывает её; ошибка идёт в сторону уязвимости. Why rejected: безопасный умолчальный отказ.
- **Один булев `private`.** Why rejected: не оставляет места для третьего значения (например, списка плагинов) без смены типа поля.
- **Проверка прав вызывающего у каждой команды без `guard`, по списку прав исполнителя.** Cons: ядро не знает, какой аргумент команды что означает; без объявления исполнителя проверка либо пропускает всё, либо отказывает всем. Why rejected: тот же довод, что и для `guard` члена контракта ([ADR-CH-0014](ADR-CH-0014-secrets.md), п. 3).

## Расхождения с текущим кодом

- Предупреждение `checkPlugin` о члене контракта или команде с `callers: "plugins"`, чей аргумент-путь не охвачен `guard` (пункт 4 задачи K-22), не сделано: `checkPlugin` ещё нет, пункт переходит в [P-09](https://github.com/dex-it/cyborg-harness/issues/9). До него У-14 закрыта частично: член контракта без `guard` ядро по-прежнему не проверяет.
- Строку «другие плагины могут звать команды» показывает только список прав окна «Плагины Cyborg»: окна согласия (этап 2) ещё нет.
