# Cyborg Harness

Документация разработки Cyborg Harness - ядра плагинов (`core/`), пакета объявлений `@cyborg-harness/contracts` (`contracts/`) и стенда `playground/`. Ядро не знает предметной области: агент, сессии, файлы, проекты и трекеры - равные плагины, а поставка приложения - список встроенных плагинов. Коротко о харнесе - [OVERVIEW](OVERVIEW.md).

> Документы перенесены из `docs/cyborg-harness/` репозитория [ai-cyborg](https://github.com/dex-it/ai-cyborg) вместе с кодом ядра. Статус - `review`: решения составителя ждут приёмки владельцем. Пути вида `src/main/...` в документах - файлы Cyborg.

## Структура

Номера папок идут в порядке вывода документов: каждая следующая зона выводится из предыдущей.

| Зона | Что несёт | Из чего выводится |
|---|---|---|
| `00-strategy` | идеи (`IDEA-NN`): зачем ядро и плагины, меры успеха, статус | запрос владельца |
| `01-product` | BRD продукта: цели, стороны, BR, ограничения; доменная модель | стратегия |
| `02-use-cases` | папка на фичу, файл на сценарий (`UC-{ФИЧА}-NNNN`); сценарий лежит в папке фичи, которую разворачивает в основном, остальные названы в `touches` | BR |
| `03-requirements` | SRS фичи в папке `<NN>-<слаг>/`, истории с критериями приёмки (`stories/`), журнал решений фичи; карта фич - `README.md`, таблица покрытия - `coverage.md` | FR - из шагов и расширений сценариев, NFR - из мер BR, истории - нарезка норм по ветвям сценариев |
| `04-architecture` | SAD и модель угроз (`design/`), решения ADR-CH (`adr/`) | нормы |
| `05-verification` | план верификации (`test-plan.md`), замеры и спайки | нормы и устройство |
| `06-plans` | дорожная карта по направлениям, эпик | состояние норм |

Раскладка отличается от корпуса Cyborg ([`docs/README.md`](https://github.com/dex-it/ai-cyborg/blob/master/docs/README.md)). Там SRS лежит в папке фичи рядом с её BRD, а зон после `02-use-cases` на одну меньше. Здесь нормы вынесены в свою зону, чтобы порядок папок совпадал с порядком вывода, а BRD фич нет: десяти BR продукта хватает, и BRD фичи только пересказывал их. Фичи появляются на уровне норм. Решения владельца от 2026-11-08. Идентификаторы с префиксом `CH-` (`BR-CH-001`, `FR-CH-1001`, `ADR-CH-0001`) не пересекаются с корпусом Cyborg.

## Как рождается документация

```
ресёрч -> идея (00-strategy/IDEA-NN)
             |
BRD продукта (BR + мера успеха) <-> ранние ADR и SAD     драйверы ADR - из BR
             |
фичи с границами (по BR, не по компонентам SAD)
             |
сценарии (02-use-cases) по BR --> FR --+
BR, меры успеха ---------------> NFR --+--> SRS фичи, метод проверки у каждой нормы
             |                              с SAD - сверка
             |
истории с критериями приёмки (stories/): нарезка норм по ветвям сценариев, метки [FR-CH-NNNN]
SAD и ADR уточняются под FR и NFR; расхождение - находка
             |
дорожная карта (план): шаг -> [FR]/[NFR] + решение SAD
             |
код и тесты --> изменённое поведение возвращается в корпус
```

Три условия, без которых путь «сначала архитектура» портит корпус:

1. У каждого ADR драйвер - BR или ключевое качество из BRD. BRD хотя бы черновиком не позже ADR.
2. FR, NFR и критерии приёмки выводятся из BR и сценариев, с SAD только сверяются. Норма, разошедшаяся с SAD, - находка: закрывается решением (правка ADR или нормы), не подгонкой одного под другое. Норма, за которой не стоит ни один BR (правило из SAD, которого не требует потребность), тоже находка: её выносят в журнал решений фичи с решением владельца, а не придумывают ей BR.
3. Фичи проводятся по BR (что получает пользователь), не по компонентам SAD. Мера против угрозы лежит в фиче «безопасность и доверие», даже если ложится на контракт или вид другой фичи ([нормы](03-requirements/README.md)).

NFR идут от BR своей веткой и из сценариев не выводятся. Критерии приёмки рождаются при нарезке в истории, после NFR: правило пишется с методом проверки в SRS, пример на данных (Дано - Когда - Тогда) берётся с ветки сценария и несёт метку правила; мера NFR попадает в критерий ссылкой на идентификатор, а не переписанным числом. Полнота считается с двух сторон ([таблица покрытия](03-requirements/coverage.md)): каждая норма дала критерий, каждая ветка сценария покрыта критерием или названа открытой (вопрос без ответа критерием-догадкой не закрывается). В этом корпусе путь шёл от обратного (ресёрч, ADR, SAD, код, затем BRD и SRS: `origin: derived` в шапках), поэтому условие 2 здесь проверяется ретроспективно: при каждой правке нормы её `traced from` и источник в SAD сверяются заново.

## Границы фич

Границы объявляются до написания SRS: без них нормы соседних фич перекрываются. Блок номеров - тысяча на фичу (фича `NN` нумерует с `N001`); номер сквозной и при переносе нормы в другую фичу не меняется ([нормы](03-requirements/README.md)).

| Фича | Покрывает | Не покрывает | Блок номеров |
|---|---|---|---|
| `01-plugin-host` | манифест, обнаружение и состояния, граф контрактов, хосты и сторож, откат, выгрузка, ленивая активация, воркспейс, pty у ядра; накладные расходы, устойчивость, компактность | вид плагина и слои окна (02); права и изоляция как меры против угроз (03); журнал и трасса (04) | 1000-1999 |
| `02-extension-contracts` | контракты, события, команды и сочетания, виды и документы, слой окна, контракт агента; доступность | меры безопасности вида: группы рендера, CSP, DOM (03); версии контрактов и миграции (05) | 2000-2999 |
| `03-security-trust` | шлюз `ctx.os` и права, этапы изоляции, секреты, допуск команд, группы рендера и адреса окна, агент в модели доверия, безопасный режим, учёт угроз | устройство хостов и сторожа (01); журнал и трасса как наблюдаемость (04) | 3000-3999 |
| `04-observability` | журнал и окно «Плагины Cyborg», трасса операций, журнал плагина, хранение и выгрузка | отказы, которые журнал только показывает: изоляция сбоев (01), запрет по правам (03) | 4000-4999 |
| `05-compatibility` | `engines.cyborg`, версии API и контрактов, `config` и `state` с миграциями, снимок API | загрузка и граф (01); пакеты и выпуск (06) | 5000-5999 |
| `06-delivery` | пакеты `@cyborg-harness/*`, упакованная сборка, платформы | форма API плагина (05); инструменты автора (07) | 6000-6999 |
| `07-author-kit` | пакет объявлений, проверка импортов, шаблон, сборка, `checkPlugin`, тест-кит, руководство | сам формат манифеста и контрактов (01, 02, 05) | 7000-7999 |

Нормы блока 1000 и 2000 лежат и в других фичах: они выведены, когда фич было две, и номер не переписывался (поэтому в `04-observability` есть FR-CH-1010, в `07-author-kit` - FR-CH-1xxx и FR-CH-2xxx).

## Адресация корпуса

- `.docs_layout` в корне репозитория - ключи путей по [раскладке `docs-layout`](https://github.com/dex-it/ai-kit/tree/master/plugins/skills/dex-skill-docs-layout) каталога ai-kit. Ключ `root` указывает на `docs/03-requirements/` (папки фич), `product` и `domain` - на `docs/01-product/`: уровень продукта и корпус фич здесь расходятся ([отступления](#отступления-от-раскладки)).
- `docs/.req_counter/` - счётчик номеров, файл на ключ, значение - последний выданный номер. Ключи: `feature` (последняя фича, 07), `BR` (010), `ADR` (0016) и `N.FR`, `N.NFR` - класс в блоке номеров фичи `N` (`01.FR`, `01.NFR`, ..., `07.FR`). Новый номер берётся инкрементом файла своего ключа, а не подсчётом по SRS; `N.UC` - последний сценарий и `N.ST` - последняя история блока фичи `N` (сценарии `UC-{ФИЧА}-NNNN`, где `{ФИЧА}` - слаг папки фичи без номера в верхнем регистре; истории `ST-NNNN`).
- Проверка согласованности: значение каждого счётчика не меньше максимального номера своего класса в корпусе (`git grep -ohE '(N?FR|BR|ADR)-CH-[0-9]+'`, максимум по классу и по первой цифре номера); для `N.UC` и `N.ST` её делает `npm run check:docs-trace`.
