# Пилот PL-04: дерево файлов и git через границу плагинов, `fs.watch` вместо опроса

Задача [PL-04 #23](https://github.com/dex-it/cyborg-harness/issues/23). Дата: 2026-11-10. Вопрос: выдерживает ли ядро путь «дерево репозитория + отметки git + открытие файла», когда `files`, `git` и `viewer` живут в трёх хостах и каждое чтение идёт через `ctx.os`, а обновление - по событиям `fs.watch`, без опроса раз в 3 с, как в Cyborg. Плагины стенда (`playground/plugins/files`, `git`, `viewer`) нужны для проверки ядра и контрактов, а не как перенос: окна у них нет, в `DEFAULT_CONFIG` они не включены, а проверяемые свойства закреплены тестами `playground/test/pilot-*.test.ts` и черновиками контрактов в пакете.

## Как мерили

- **Стенд.** `npm run pilot:files -- --repo <путь> ...` (`playground/scripts/pilot-files.mjs`). Репозиторий клонируется во временный каталог (`git clone --local`), исходный не трогается. Ядро поднимает три плагина в трёх хостах-процессах (`forkHosts`), как в тестах. **Это не Electron:** цена вызова здесь - канал `child_process`, а не `utilityProcess`; шлюз в главном процессе тот же. Цифры T-07 ([spike-gateway.md](spike-gateway.md)) сняты в Electron.
- **Задержка шлюза.** Плагин сам считает время вокруг `await ctx.os.fs.list/stat/readText`, 300 вызовов после 30 разогревочных, по одному; «голое» - тот же вызов (`readdir`, `stat`, `readFile`) в том же процессе хоста без шлюза. Файл для `stat` и `readText` - первый отслеживаемый файл репозитория (небольшой).
- **Прогоны.** 3 прогона на репозиторий, в таблицах медиана по прогонам. **Чистого сеанса не было:** на машине работали другие процессы (MacBookPro Apple M1 Pro, 10 ядер, macOS, Node v24.20.0); load average (1 минута) на старте прогонов: `ai-cyborg` 17,8 / 12,3 / 9,6; `cyborg-harness` 7,5 / 7,1 / 5,1; `upcore.backend` 4,8 / 4,1 / 3,8; `ai-kit` 3,9 / 12,6 / 11,0. Для задержек это шум в худшую сторону.
- **Простой.** Окно 10 с после раскрытия 48 каталогов. Слежение: процессорное время процесса замера (ядро и шлюз) плюс прямых потомков (хосты) по `ps`. Опрос: эмуляция тика Cyborg ([`app.ts:959`](https://github.com/dex-it/ai-cyborg/blob/master/src/renderer/app.ts), `tree.ts`) - раз в 3 с `git status --porcelain=v1 -z --untracked-files=all` и `git rev-parse --abbrev-ref HEAD` плюс то же фоновое потребление хостов; процессорное время git берётся из `/usr/bin/time -p` (разрешение 10 мс). Настоящий Cyborg не запускался.
- **Checkout.** Целевой коммит - глубина `HEAD~n`, при которой различий не меньше ~3 000 файлов (или самая большая, какая есть). Раскрыто 48 самых населённых каталогов; часть их checkout убирает. Для сравнения число событий считает рекурсивное `fs.watch(root, { recursive: true })` процесса замера.

Разделы 1-5 сняты на `files` с отдельными слежениями за корнем и раскрытыми каталогами (до [#205](https://github.com/dex-it/cyborg-harness/issues/205)); перемер `ai-kit` после перевода на рекурсивное слежение - раздел 6 и сравнение с ними.

| `ai-kit` | 2,4 | 573 (442 - 583) | 368 (под нагрузкой; разово в тихую минуту 235-284) | 236,6 |

«Холодно» - первый вызов после старта хостов: загрузка модулей плагинов и первый запуск программы. В приложении хосты живут с запуска, поэтому эта часть переезжает в старт, а на открытии остаётся тёплая цифра: у малых репозиториев 26-42 мс при 17 мс самого `git status`, у `ai-kit` она равна `git status` (235-284 мс). Раскрытие 48 каталогов - 27-38 мс суммарно, 0,56-0,65 мс на каталог (p50). **Тёплая отметка после правки файла** (событие, `stat`, `git status` через границу хостов): 90-119 мс у `ai-cyborg` и `cyborg-harness`, 297-361 мс у `upcore.backend`, 337-460 мс у `ai-kit`; из них 50 мс - склейка событий шлюза. Опрос Cyborg показывает правку не позже чем через 3 с плюс время `git status`.

`git status` в режиме плагина (по умолчанию, неотслеживаемые каталоги свёрнуты) и Cyborg (`--untracked-files=all`) стоят одинаково с точностью до разброса (`ai-kit`: 236,6 и 230,7 мс; остальные в пределах 1,5 мс).

|---|---|---|---|

| `cyborg-harness` | 21 (0,2%) | 59 (0,6%) | +38 |
| `upcore.backend` | 10 (0,1%) | 373 (3,7%) | +363 |
| `ai-kit` | 8 (0,1%) | 1 678 (16,8%) | +1 670 |

В обоих столбцах есть постоянный фон ядра и хостов (сторож хостов раз в секунду, канал); слежение даёт только этот фон, поэтому в простое дерево на событиях ничего не добавляет. Опрос растёт с размером репозитория, потому что тик - это полный `git status`. Тест `files: без событий нет ни одного вызова...` держит это свойство: за 1,5 с простоя счётчики `list`, `stat`, число запросов отметок и запусков git не сдвигаются (запуски считает программа-обёртка `git` в `PATH`, независимо от плагинов).

Время от конца `git checkout` до последнего изменения в дереве: 0,24-0,5 с (`ai-cyborg`, `cyborg-harness`, `upcore.backend`), 0,4-1,0 с (`ai-kit`; сам checkout 1,7-2,1 с). Слежение не упало ни разу, лавины перерисовок нет: тысячи событий склеены в десятки пачек и единицы запросов git; отметок после возврата не осталось (дерево чистое, как `git status`).

**Событиям нельзя верить как единственному источнику.** Первый вариант `files` (обновлять только узлы, где пришли события) расходился с диском: на `cyborg-harness` после перехода на 600-файловый коммит 11 узлов из 48 показывали каталоги, которых уже нет, и старый состав; на `ai-cyborg` в двух прогонах из трёх расходились 4 узла (в дереве 41 имя при 6 на диске). FSEvents при лавине не назвал часть ушедших каталогов, а оповещение git об индексе тоже не пришло. Теперь, если подряд пришло не меньше 16 имён или git сообщил об индексе или голове, то после тишины в 300 мс **перечитываются все раскрытые узлы** (до 64 вызовов `fs.list` по ~0,2 мс): расхождений 0 в 24 переходах (4 репозитория, 3 прогона, туда и обратно). Тесты теряют события обёрткой над `fs.watch` (`потеряла события каталогов при checkout`, `лавина событий...`) и краснеют без перечитывания.

## 5. Удаление наблюдаемого каталога и симлинки

- **Удаление.** Раскрытый каталог удалён (включая время самого `rm`): узел и поддерево забыты, слежение снято, родитель перечитан за 90-132 мс на малых репозиториях, 286 мс на `upcore.backend`, 614 мс на `ai-kit` (много файлов под удалением). Ошибок в журнале нет. Корень удалён: `rootLost` с причиной, слежений 0 (тест). **Шлюз слежение за удалённым каталогом не закрывает** (`onClose` не приходит: путь после удаления разрешается как «родитель плюс имя», и проверка прав его пропускает); об удалении плагин узнаёт по событию с именем самого каталога и `NotFound` при чтении.
- **Симлинки внутри репозитория.** Ссылки на файл внутри, на сам корень и на каталог снаружи появляются в дереве как `link` за 65-68 мс после создания; `files` ссылки не раскрывает. Открытие через ссылку внутрь работает, через ссылку наружу - `PermissionDenied` (тест).

## 6. Рекурсивное слежение за корнем (#205): перемер `ai-kit` на macOS и Linux

`files` перешёл на одно `fs.watch(root, …, { recursive: true })` вместо слежений за корнем и раскрытыми каталогами. Перемер настоящего `ai-kit` (15 090 файлов в 5 700 каталогах, переход на коммит с 14 744 изменёнными файлами, 48 раскрытых каталогов), `npm run pilot:files -- --repo <ai-kit> --runs=3 --control=0`, три прогона, медианы; во всех шести переходах (три прогона, туда и обратно) на каждой ОС дерево совпало с диском (0 расхождений), открытых слежений шлюза 1 во все моменты замера. macOS - тот же MacBookPro M1 Pro, load average на старте прогонов 11-17 (чужие процессы; для задержек это шум в худшую сторону). Linux - Docker (OrbStack) на той же машине, `node:24` (v24.22.2, aarch64), чистый контейнер без чужой нагрузки, `fs.inotify.max_user_watches` 1 048 576; репозиторий клонирован внутрь контейнера (`git clone --no-hardlinks`), исходный `ai-kit` не тронут.

|---|---|---|---|

| Перечитываний всех узлов (`resyncs`) туда / обратно | 50 / 33 | 11 / 11 | 60 / 11 |
| От конца `git checkout` (дождались процесс) до последнего изменения в дереве, туда / обратно | 0,4-1,0 с | 0,65 / 1,4 с | 0,52 / 0,6 с (счёт идёт после того, как главный цикл освободился, см. ниже) |

| Расхождений дерева с диском | 0 из 3 | 0 из 6 переходов | 0 из 6 переходов |
| `files.root` (открытие слежения и корня) | не снималось | 2,7-15 мс | 94-113 мс (inotify на 5 700 каталогов) |
| Простой 10 с (процессорное время ядра и хостов; ни одного вызова `fs.*`, ни одного git) | 8 мс | 24-44 мс (нагрузка машины) | 9-21 мс |

- **Паритет отметок с опросом достигнут.** Правка отслеживаемого файла в нераскрытом каталоге даёт отметку сама (тест «правка вглубь нераскрытого каталога…»; раньше отметка ждала постороннего события). На `ai-kit` правка в раскрытом каталоге до отметки в дереве: 380-635 мс на macOS и 206-321 мс на Linux, из них `git status` около 240 мс на macOS и 45 мс на Linux (размер репозитория тот же, разница в ФС и кэше).
- **Событий в 20-70 раз больше, а работы меньше.** Рекурсивное слежение называет все 21 тысячу изменённых путей (раньше - только имена в 48 каталогах). Дерево разбирает их пачками (25-41 против 37-50), запросов `git status` не 9, а 2-3: в лавине (не меньше 16 имён подряд) отметки запрашиваются один раз после тишины, а не на каждую пачку. До этого решения перемер дал 8 и 24 запроса туда и обратно (по запросу на пачку, пока пачки идут): `git status` не успевал за checkout, результат прохода устаревал, пока шёл следующий.
- **Linux: Node блокирует главный цикл.** Рекурсивное слежение Node на Linux - это `inotify` на каждый каталог, который он обслуживает в JavaScript на том же потоке; при checkout, удаляющем и создающем тысячи каталогов, цикл событий процесса стоял 16,3-17,3 с (`git checkout` сам занял 0,4 с). Контроль без нашего кода: голый `node -e` с одним `fs.watch(repo, { recursive: true })` на том же `ai-kit` в том же контейнере и тот же `git checkout` - отставание цикла 7,4 с (21 998 событий), без слежения 18 мс. В процессе замера (ядро со шлюзом, склейка событий, хосты) вдвое больше. Это главный процесс приложения: такой checkout заморозит окно на секунды. Обратный переход (создание каталогов) - 59 мс, потому что узлы уже есть. **На macOS слежение FSEvents, цикл не блокируется (17-22 мс).** Остаток вынесен в задачу.
- **Первый вариант замера** (с контрольным рекурсивным слежением Node рядом с плагином, для сравнения числа событий) на Linux растянул checkout до 31-34 с по той же причине: два рекурсивных слежения вдвое больше работы. Контрольное слежение теперь отключается `--control=0`; прежние числа разд. 4 в столбце «для сравнения» сняты с ним.

## Предел слежения и решение

`fs.watch(path)` шлюза без параметров следит за **одним каталогом, не рекурсивно**, и таких слежений не больше `MAX_WATCHES = 64` на плагин (`core/src/os-gateway.ts`). С `{ recursive: true }` ([#182](https://github.com/dex-it/cyborg-harness/issues/182)) оно следит за деревом одной записью лимита. Каталогов с отслеживаемыми файлами в репозиториях стенда:

| Репозиторий | Каталогов с отслеживаемыми файлами | Хватает ли 64 слежений на все |
|---|---|---|
| `ai-cyborg` | 64 | нет: с корнем 65 |
| `cyborg-harness` | 124 | нет |
| `upcore.backend` | 1 035 | нет |
| `ai-kit` | 5 700 | нет |

**Решение (принято по поручению владельца 2026-11-10; обновлено 2026-11-10 переводом пилота, [#205](https://github.com/dex-it/cyborg-harness/issues/205)).**

- **Было.** `files` следил за корнем и раскрытыми каталогами по отдельности, до 64, и при нехватке вытеснял давно раскрытые (узел помечался устаревшим и перечитывался при раскрытии). Узлам дерева 64 хватало, отметкам git - нет: правка в нераскрытом каталоге событий не давала, отметка появлялась только по другому событию. Паритет с опросом Cyborg требовал рекурсивного слежения за корнем.
- **Стало.** `files` держит **одно** `fs.watch(root, …, { recursive: true })`; вытеснения, пометки «устарел» и очереди постановки слежений нет. Имя в событии - путь от корня через `/`: прямые дети раскрытого узла обновляет этот узел (`stat` на известное имя, `list` на незнакомое), имена внутри `.git` отбрасываются, имена глубже раскрытого узла только запрашивают отметки (а если узел не знает первого каталога на пути, он перечитывается). `git` остался на нерекурсивном слежении за самим `.git` (индекс, голова): рекурсивное принесло бы ему поток событий `objects/` и `logs/`, которого он не использует.
- **Цена на Linux.** `inotify` на каждый каталог внутри корня: `fs.inotify.max_user_watches` (8 192 на пользователя в части дистрибутивов, на ai-kit нужно не меньше 5 700 плюс остальные приложения) может не хватить, тогда `files.root` отказывает `Unavailable` с названием предела (проверка шлюза #182), запасного нерекурсивного режима нет; и массовое создание и удаление каталогов блокирует главный цикл процесса на секунды (раздел 6). Для macOS (FSEvents) цены нет.

Замер шлюза на синтетическом дереве размера `ai-kit` (#182, 5 700 каталогов в трёх уровнях, 15 090 файлов; macOS, FSEvents, `recursive: true` через `OsGateway`): 15 090 файлов записаны за 858 мс одновременно, слушатель получил 13 пачек (склейка 50 мс), 24 804 имён с повторами (create и modify одного файла), первая пачка через 737 мс от начала записи, последняя через 931 мс; процесс замера занял 321 МиБ RSS вместе с самим деревом. Он заменён настоящим `ai-kit` (раздел 6).

## Права и расхождение с Cyborg

- Чтение за пределами корней воркспейса - `PermissionDenied`, а не `NotFound`: `files.root('/etc')`, `files.open('/etc/hosts')` (тесты). Плагин без права `fs.read` на путь не открывает его в `viewer` (`guard`, `reason: 'via-contract'` у вызывающего), `viewer` читает по своему праву, так что действует пересечение прав (тест). Команды `files.*` закрыты чужим плагинам (`callers` по умолчанию `user`).
- `git` отвечает вызывающему без права читать репозиторий `PermissionDenied`, а на репозиторий вне корней - тоже отказом, даже если право есть у вызывающего (тест «пересечение»).
- **Расхождение с Cyborg.** `AllowedPaths` в ai-cyborg (`src/main/allowed-paths.ts`) сначала сверяет путь строкой: путь под корнем разрешён без `realpath`, ссылки внутри каталога не раскрываются, и `/repo/link-out/secret` с `link-out` на каталог снаружи разрешён. Ядро всегда раскрывает ссылки (`realpath`): тот же путь - `PermissionDenied`. Ссылка наружу, читавшаяся в Cyborg, перестанет читаться (регрессия для человека, у которого в репозитории `docs -> ../shared`); ссылка внутрь читается так же. Шлюз не ослабляется: решение - принять строгость ядра, а такие ссылки отдать плагину как `link` (`files` не раскрывает ни одну), выбор «показывать ли цель» - дело UI; расхождение внесено в остатки переноса `files`, шлюз не правится.

## Сравнение с базой Cyborg ([cyborg-baseline.md](cyborg-baseline.md))

В PL-09 нет строк «время дерева» и «процессор в простое» отдельно, есть «Проект и дерево на экране от запуска процесса: 455 мс» - метрика всего приложения, к тройке плагинов не сводится. Сравнивается поэтому то, что можно снять тем же способом на тех же репозиториях:

- **Время открытия панели** = `git status` + список каталога. У Cyborg это `git status --untracked-files=all` плюс `rev-parse` и чтение каталога: 16,5-231 мс по репозиториям. Пилот на тёплых хостах: 26-42 мс против 17 мс у `git status` на малых репозиториях (слежение, канал и три хоста) и на уровне `git status` на `ai-kit`. **Холодное первое открытие хуже на 190-340 мс** (206 мс против 17 на `ai-cyborg`); оно приходится на старт хостов. Правило «не хуже базы на 10%» для холодного открытия **не выполнено**, отклонение объяснено загрузкой модулей и первым запуском процесса, но не разложено по частям (не измерялось).
- **Нагрузка простоя:** слежение 0,1-0,2% ядра против 0,4-16,8% у опроса (раздел 3): лучше базы на порядок и более, растёт с размером репозитория. Сам Cyborg не запускался; эмуляция берёт у него команды и период тика, но не его отрисовку.
- **Обновление после правки:** 90-460 мс против «до 3 с + `git status`».

## Решения (принято по поручению владельца 2026-11-10)

1. **Открытие файла - команда `viewer.open`, а не `file.open` и не член контракта.** Команда исполнителя обязана лежать в его пространстве имён (`${id}.`, [ADR-CH-0016](../04-architecture/adr/ADR-CH-0016-command-callers.md), п. 6), поэтому `file.open` из SAD мог бы объявить только плагин `file`; `callers: "plugins"` и `guard` `fs.read` на `path` дают ту же проверку права вызывающего, что `via-contract` у члена контракта (общий `Guard`, `checkFor`). Критерий задачи «через контракт с правом на аргумент» закрыт этим механизмом; SAD (разд. 3.4, 5) и руководство исправлены на `viewer.open`.
2. **Черновики контрактов - подмножество SAD.** `cyborg.git` v1: `status(repo)`, `onChange(repo, listener)`; остальные члены (`headContent`, `branches`, `switch`, `remotes`, `files`) придут необязательными (минор), [#196](https://github.com/dex-it/cyborg-harness/issues/196). `cyborg.tree-decoration` v1: `marks(root)`, `onChange(listener)`, кратность many, объявляет владелец дерева. Не репозиторий - `status` отвечает `null`. Минимальная обратимая форма: добавление членов - минор, пакет в линии `-dev`.
3. **`git status` без `--untracked-files=all`.** Цена одинакова (раздел 2), а неотслеживаемый каталог приходит одной записью; дерево отмечает всё внутри него само.
4. **Защита `git`.** Правило `process` закрепляет `--no-optional-locks -c core.fsmonitor=false -c core.hooksPath=/dev/null status --porcelain=v1 -z --branch` (как `SAFE_CONFIG` в ai-cyborg); тест доказывает, что без защиты этот `git` выполнил бы `core.fsmonitor` из конфига репозитория, а с ней - нет. **Фильтры `filter.*.clean|process|required`** из конфига репозитория (их `status` гоняет по файлам с изменившимся stat, одним `-c` не отключить) перекрыты ([#183](https://github.com/dex-it/cyborg-harness/issues/183), принято по поручению владельца 2026-11-10): перед каждым `status` плагин собирает ключи репозитория и вложенных (`config --show-scope --null --name-only --get-regexp`, `ls-files --stage -z`, рекурсия по заполненным подмодулям до глубины 8) и передаёт `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*`, `GIT_CONFIG_VALUE_*` (`filter.*.required` получает `false`, остальные - пустое значение), как `filterOverrides` в ai-cyborg; `playground/plugins/git/filters.ts`. Три правила `process` закрепляют аргументы и имена переменных (`env` правила, маска для номерных); фильтры пользовательского и системного конфига доверенные и остаются. Сбой сбора ключей (вывод длиннее предела, ключ или путь подмодуля не в UTF-8, вложенность глубже предела) отказывает всему `status`: неполный набор ключей молча не используется. Тесты: фильтр репозитория и подмодуля не выполняется (контроль: тот же `git` без перекрытия его запускает), `playground/test/pilot-git.test.ts`, `git-filters.test.ts`. **Цена:** на каждый опрос теперь три запуска `git` вместо одного (`config` и `ls-files` идут параллельно, потом `status`); замер `npm run pilot:files` в этой задаче не повторялся, числа раздела 2 сняты до неё, `gitRuns` в стенде считает только `status`.
5. **Предел слежения** - см. выше. Было: узлам хватает, отметкам нет ([#182](https://github.com/dex-it/cyborg-harness/issues/182)); с 2026-11-10 `files` следит одним рекурсивным слежением за корнем ([#205](https://github.com/dex-it/cyborg-harness/issues/205)).
6. **Лавина и смена ветки.** После тишины в 300 мс перечитываются все раскрытые узлы, если подряд пришло не меньше 16 имён или git сообщил об индексе или голове. Порог и тишина подобраны по замерам, константы в `files/index.ts`. С переводом на рекурсивное слежение (#205) в лавине отметки запрашиваются один раз после тишины, а не на каждую пачку: на `ai-kit` 2-3 запроса `git status` вместо 8 и 24 (раздел 6).
7. **Пилотные плагины не включены в `DEFAULT_CONFIG`**, окна у них нет: цель - ядро и контракты. Они собираются в `playground/dist/plugins`, но не входят в упакованную поставку (`dist/delivery`): её проверка ждёт, что каждый плагин поставки активен.
8. **Одно рекурсивное слежение за корнем, без запасного режима (#205, принято по поручению владельца 2026-11-10).** Минимальная обратимая форма: прежние вытеснение и пометки «устарел» удалены целиком, а не оставлены запасным путём, потому что два пути удваивали бы поверхность тестов ради случая, который шлюз называет явно (`Unavailable` с `fs.inotify.max_user_watches`, `files.root` отказывает, а не молчит). Вернуть нерекурсивный режим можно отдельной задачей, если Linux-потребители упрутся в предел.
9. **Имена внутри `.git` дерево и отметки не трогают.** Сегмент `.git` в пути события отбрасывается до подсчёта пачек и лавины: коммит, `fetch` и сборка мусора шумят сотнями имён в `objects/` и `logs/`, а то, что меняет отметки (индекс, голова), приносит `onChange` поставщика. Тест: сорок файлов в `.git/objects` не дают ни пачки, ни `git status`.
10. **`git` остаётся на нерекурсивном слежении за `.git`.** Ему нужны имена верхнего уровня (`index`, `HEAD`, `packed-refs`, `*_HEAD`); рекурсия принесла бы поток `objects/` и вторую запись лимита ради ничего.
11. **Отметки в лавине - один запрос после тишины.** Пока идёт checkout, `git status` на каждую пачку не успевает за деревом (перемер: 24 запроса при обратном переходе против 3 теперь); слежение за корнем шлёт события со всего дерева, и без этого запросов стало бы вдвое-втрое больше прежних. Цена: отметки в лавине приходят на 0,3 с позже.
12. **`pilot-kit` и `lossy` понимают форму `watch(path, { recursive: true }, listener)`**, в которой шлюз зовёт ОС с рекурсией; счётчики стенда: `watches.recursive`, `watches.rawBy`.

## Остатки и открытые наблюдения

- **Linux: рекурсивное слежение Node блокирует главный цикл при массовом создании и удалении каталогов** (раздел 6: 16,6 с в процессе замера и 7,4 с у голого `fs.watch` на `ai-kit`; macOS 17-22 мс). Касается шлюза (`OsGateway`, `recursive`), а не только пилота; нужны либо слежение вне главного потока (воркер или нативный наблюдатель вроде `@parcel/watcher`), либо запрет `recursive` на деревьях больше предела. Вынесено в задачу [#211](https://github.com/dex-it/cyborg-harness/issues/211) `[Iteration3][Techdebt] Рекурсивное слежение на Linux блокирует главный цикл`.
- **Предел `fs.inotify.max_user_watches` на Linux:** `files.root` на дереве с числом каталогов больше предела отказывает `Unavailable`; запасного нерекурсивного режима нет (решение 8). В замере предел 1 048 576, на машинах с 8 192 `ai-kit` (5 700 каталогов) с остальными приложениями не поместится. Не измерялось на машине с малым пределом.
- **Перемер сделан только на `ai-kit`** (по задаче #205); разделы 1-5 и их таблицы по остальным репозиториям (`ai-cyborg`, `cyborg-harness`, `upcore.backend`) сняты на предыдущей форме слежения и не повторялись. Linux - контейнер на aarch64 с `node:24`, не x86-64 и не Ubuntu CI; шаг «простой: опрос» на Linux не считается (в контейнере нет `/usr/bin/time`, процессорное время git равно 0).
- **`git`: полный набор членов `cyborg.git`** - [#196](https://github.com/dex-it/cyborg-harness/issues/196), по мере потребителей. Перекрытие `filter.*.clean` закрыто ([#183](https://github.com/dex-it/cyborg-harness/issues/183)); вопрос 5 SAD (списки `process`) остаётся общим.
- **Перекрытие фильтров: окно между сбором ключей и `status`.** Конфиг репозитория, переписанный в эти миллисекунды другим процессом, ключ уже не попадёт в набор; граница та же, что у `filterOverrides` в ai-cyborg (кто пишет в `.git/config`, исполняет код и без фильтра). Цену трёх запусков можно снять кэшем набора ключей по mtime `.git/config` и индекса, если замер покажет нужду.
- **Ни одно событие не доходит - дерево не узнает.** Если ОС теряет все события корня и `.git`, перечитывание не включится (нет триггера); без опроса это не лечится, лечит только сверка по фокусу окна (`ctx.window.onFocusChange`), не сделанная здесь.
- **`ctx.os.fs` без `lstat`:** `FileStat.kind` раскрывает ссылку, поэтому для нового имени в событии узел читает каталог (`list`), а не делает `stat`.
- **Хвост #147.** Каждый тест, который меняет файлы сразу после `fs.watch`, сначала «взводит» слежение пробной записью (`arm` в `pilot-files.test.ts`, как в `core/test/os.test.ts`); без этого удаление раскрытого каталога сразу после слежения терялось в 2 прогонах из ~20.
- **Репозиторий должен быть корнем рабочего дерева:** пути `git status --porcelain` считаются от корня, у подкаталога репозитория метки не совпали бы с деревом.
- **Не измерялось:** Electron `utilityProcess` вместо `child_process`; Linux с малым `fs.inotify.max_user_watches`; настоящий Cyborg под нагрузкой (только эмуляция тика); разложение холодного открытия; `fs.lstat`.
