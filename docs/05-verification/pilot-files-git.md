# Пилот PL-04: дерево файлов и git через границу плагинов, `fs.watch` вместо опроса

Задача [PL-04 #23](https://github.com/dex-it/cyborg-harness/issues/23). Дата: 2026-11-10. Вопрос: выдерживает ли ядро путь «дерево репозитория + отметки git + открытие файла», когда `files`, `git` и `viewer` живут в трёх хостах и каждое чтение идёт через `ctx.os`, а обновление - по событиям `fs.watch`, без опроса раз в 3 с, как в Cyborg. Плагины стенда (`playground/plugins/files`, `git`, `viewer`) нужны для проверки ядра и контрактов, а не как перенос: окна у них нет, в `DEFAULT_CONFIG` они не включены, а проверяемые свойства закреплены тестами `playground/test/pilot-*.test.ts` и черновиками контрактов в пакете.

## Как мерили

- **Стенд.** `npm run pilot:files -- --repo <путь> ...` (`playground/scripts/pilot-files.mjs`). Репозиторий клонируется во временный каталог (`git clone --local`), исходный не трогается. Ядро поднимает три плагина в трёх хостах-процессах (`forkHosts`), как в тестах. **Это не Electron:** цена вызова здесь - канал `child_process`, а не `utilityProcess`; шлюз в главном процессе тот же. Цифры T-07 ([spike-gateway.md](spike-gateway.md)) сняты в Electron.
- **Задержка шлюза.** Плагин сам считает время вокруг `await ctx.os.fs.list/stat/readText`, 300 вызовов после 30 разогревочных, по одному; «голое» - тот же вызов (`readdir`, `stat`, `readFile`) в том же процессе хоста без шлюза. Файл для `stat` и `readText` - первый отслеживаемый файл репозитория (небольшой).
- **Прогоны.** 3 прогона на репозиторий, в таблицах медиана по прогонам. **Чистого сеанса не было:** на машине работали другие процессы (MacBookPro Apple M1 Pro, 10 ядер, macOS, Node v24.20.0); load average (1 минута) на старте прогонов: `ai-cyborg` 17,8 / 12,3 / 9,6; `cyborg-harness` 7,5 / 7,1 / 5,1; `upcore.backend` 4,8 / 4,1 / 3,8; `ai-kit` 3,9 / 12,6 / 11,0. Для задержек это шум в худшую сторону.
- **Простой.** Окно 10 с после раскрытия 48 каталогов. Слежение: процессорное время процесса замера (ядро и шлюз) плюс прямых потомков (хосты) по `ps`. Опрос: эмуляция тика Cyborg ([`app.ts:959`](https://github.com/dex-it/ai-cyborg/blob/master/src/renderer/app.ts), `tree.ts`) - раз в 3 с `git status --porcelain=v1 -z --untracked-files=all` и `git rev-parse --abbrev-ref HEAD` плюс то же фоновое потребление хостов; процессорное время git берётся из `/usr/bin/time -p` (разрешение 10 мс). Настоящий Cyborg не запускался.
- **Checkout.** Целевой коммит - глубина `HEAD~n`, при которой различий не меньше ~3 000 файлов (или самая большая, какая есть). Раскрыто 48 самых населённых каталогов; часть их checkout убирает. Для сравнения число событий считает рекурсивное `fs.watch(root, { recursive: true })` процесса замера.

В приложении хосты живут с запуска, поэтому эта часть переезжает в старт, а на открытии остаётся тёплая цифра: у малых репозиториев 26-42 мс при 17 мс самого `git status`, у `ai-kit` она равна `git status` (235-284 мс). Раскрытие 48 каталогов - 27-38 мс суммарно, 0,56-0,65 мс на каталог (p50). **Тёплая отметка после правки файла** (событие, `stat`, `git status` через границу хостов): 90-119 мс у `ai-cyborg` и `cyborg-harness`, 297-361 мс у `upcore.backend`, 337-460 мс у `ai-kit`; из них 50 мс - склейка событий шлюза. Опрос Cyborg показывает правку не позже чем через 3 с плюс время `git status`.

`git status` в режиме плагина (по умолчанию, неотслеживаемые каталоги свёрнуты) и Cyborg (`--untracked-files=all`) стоят одинаково с точностью до разброса (`ai-kit`: 236,6 и 230,7 мс; остальные в пределах 1,5 мс).

Слежение не упало ни разу, лавины перерисовок нет: тысячи событий склеены в десятки пачек и единицы запросов git; отметок после возврата не осталось (дерево чистое, как `git status`).

**Событиям нельзя верить как единственному источнику.** Первый вариант `files` (обновлять только узлы, где пришли события) расходился с диском: на `cyborg-harness` после перехода на 600-файловый коммит 11 узлов из 48 показывали каталоги, которых уже нет, и старый состав; на `ai-cyborg` в двух прогонах из трёх расходились 4 узла (в дереве 41 имя при 6 на диске). FSEvents при лавине не назвал часть ушедших каталогов, а оповещение git об индексе тоже не пришло. Теперь, если подряд пришло не меньше 16 имён или git сообщил об индексе или голове, то после тишины в 300 мс **перечитываются все раскрытые узлы** (до 64 вызовов `fs.list` по ~0,2 мс): расхождений 0 в 24 переходах (4 репозитория, 3 прогона, туда и обратно). Тесты теряют события обёрткой над `fs.watch` (`потеряла события каталогов при checkout`, `лавина событий...`) и краснеют без перечитывания.

## 5. Удаление наблюдаемого каталога и симлинки

- **Удаление.** Раскрытый каталог удалён (включая время самого `rm`): узел и поддерево забыты, слежение снято, родитель перечитан за 90-132 мс на малых репозиториях, 286 мс на `upcore.backend`, 614 мс на `ai-kit` (много файлов под удалением). Ошибок в журнале нет. Корень удалён: `rootLost` с причиной, слежений 0 (тест). **Шлюз слежение за удалённым каталогом не закрывает** (`onClose` не приходит: путь после удаления разрешается как «родитель плюс имя», и проверка прав его пропускает); об удалении плагин узнаёт по событию с именем самого каталога и `NotFound` при чтении.
- **Симлинки внутри репозитория.** Ссылки на файл внутри, на сам корень и на каталог снаружи появляются в дереве как `link` за 65-68 мс после создания; `files` ссылки не раскрывает. Открытие через ссылку внутрь работает, через ссылку наружу - `PermissionDenied` (тест).

## Предел слежения и решение

`fs.watch(path)` шлюза следит за **одним каталогом, не рекурсивно** (`watchFs(target, ...)` вызывается без параметров, `core/src/os-gateway.ts`), и таких слежений не больше `MAX_WATCHES = 64` на плагин. Тест `слежение не рекурсивное...` закрепляет: правка на два уровня глубже корня события не даёт и отметка не появляется, пока что-то другое не запросит `git status`.

| Репозиторий | Каталогов с отслеживаемыми файлами | Хватает ли 64 слежений на все |
|---|---|---|
| `ai-cyborg` | 64 | нет: с корнем 65 |
| `cyborg-harness` | 124 | нет |
| `upcore.backend` | 1 035 | нет |
| `ai-kit` | 5 700 | нет |

**Решение (принято по поручению владельца 2026-11-10).**

- **Для узлов дерева 64 достаточно.** Слежение нужно только за корнем и раскрытыми каталогами; `files` держит до 64 и при нехватке вытесняет давно раскрытые (узел помечается устаревшим и перечитывается при следующем раскрытии), отказа шлюза не бывает (тест на 70 каталогов). Человек раскрывает десятки каталогов, не тысячи.
- **Для отметок git не достаточно.** Правка файла в нераскрытом каталоге (агент пишет вглубь репозитория) событий не даёт, отметка появится только по другому событию. Cyborg видит такую правку через опрос. Без опроса паритет нужен рекурсивному слежению за корнем одной записью: у `ai-kit` оно даёт 19 тысяч событий на checkout против тысячи при слежении по каталогам, но это один вызов и одна запись в лимите; на macOS это один поток FSEvents, на Linux Node ставит `inotify` на каждый каталог внутри и упирается в `fs.inotify.max_user_watches`, а не в 64 плагина. **Нужна доработка шлюза - отдельная задача [#182](https://github.com/dex-it/cyborg-harness/issues/182)** (рекурсивное слежение за корнем, закрытие слежения при удалении каталога); в PL-04 шлюз не правится ([#147](https://github.com/dex-it/cyborg-harness/issues/147) ведёт другая ветка, а реализация рекурсии выведена из задачи).

**Рекурсивное слежение шлюза (#182, 2026-11-10).** `ctx.os.fs.watch(путь, слушатель, onClose, { recursive: true })` следит за деревом одной записью лимита 64; имя в событии - путь от каталога (`src/deep/c.ts`), закрытые плагину места в события не попадают, удаление наблюдаемого каталога (и замена каталогом с другим inode) закрывает слежение с причиной. Пилот `files`/`git` на него пока не переведён: тест `слежение не рекурсивное...` описывает прежнее поведение плагина и остаётся до перевода (отдельная задача), а поведение шлюза закреплено тестами `core/test/os.test.ts` («fs.watch recursive: …», «fs.watch каталога: каталог удалён …»).

Замер шлюза на синтетическом дереве размера `ai-kit` (5 700 каталогов в трёх уровнях, 15 090 файлов; macOS, FSEvents, `recursive: true` через `OsGateway`; настоящий checkout `ai-kit` и `npm run pilot:files` в среде исполнителя недоступны): 15 090 файлов записаны за 858 мс одновременно, слушатель получил 13 пачек (склейка 50 мс), 24 804 имён с повторами (create и modify одного файла), первая пачка через 737 мс от начала записи, последняя через 931 мс; процесс замера занял 321 МиБ RSS вместе с самим деревом. На Linux Node ставит inotify на каждый каталог внутри, и 5 700 каталогов требуют столько же слежений `fs.inotify.max_user_watches` (по умолчанию 8 192 на пользователя в части дистрибутивов, 65 536 и выше в новых): при нехватке `watch` отказывает `Unavailable` с названием предела; замера на Linux нет. Замер на настоящем checkout `ai-kit` остаётся за #182.

## Права и расхождение с Cyborg

- Чтение за пределами корней воркспейса - `PermissionDenied`, а не `NotFound`: `files.root('/etc')`, `files.open('/etc/hosts')` (тесты). Плагин без права `fs.read` на путь не открывает его в `viewer` (`guard`, `reason: 'via-contract'` у вызывающего), `viewer` читает по своему праву, так что действует пересечение прав (тест). Команды `files.*` закрыты чужим плагинам (`callers` по умолчанию `user`).
- `git` отвечает вызывающему без права читать репозиторий `PermissionDenied`, а на репозиторий вне корней - тоже отказом, даже если право есть у вызывающего (тест «пересечение»).
- **Расхождение с Cyborg.** `AllowedPaths` в ai-cyborg (`src/main/allowed-paths.ts`) сначала сверяет путь строкой: путь под корнем разрешён без `realpath`, ссылки внутри каталога не раскрываются, и `/repo/link-out/secret` с `link-out` на каталог снаружи разрешён. Ядро всегда раскрывает ссылки (`realpath`): тот же путь - `PermissionDenied`. Ссылка наружу, читавшаяся в Cyborg, перестанет читаться (регрессия для человека, у которого в репозитории `docs -> ../shared`); ссылка внутрь читается так же. Шлюз не ослабляется: решение - принять строгость ядра, а такие ссылки отдать плагину как `link` (`files` не раскрывает ни одну), выбор «показывать ли цель» - дело UI; расхождение внесено в остатки переноса `files`, шлюз не правится.

## Сравнение с базой Cyborg ([cyborg-baseline.md](cyborg-baseline.md))

В PL-09 нет строк «время дерева» и «процессор в простое» отдельно, есть «Проект и дерево на экране от запуска процесса: 455 мс» - метрика всего приложения, к тройке плагинов не сводится. Сравнивается поэтому то, что можно снять тем же способом на тех же репозиториях:

- **Время открытия панели** = `git status` + список каталога. У Cyborg это `git status --untracked-files=all` плюс `rev-parse` и чтение каталога: 16,5-231 мс по репозиториям. Пилот на тёплых хостах: 26-42 мс против 17 мс у `git status` на малых репозиториях (слежение, канал и три хоста) и на уровне `git status` на `ai-kit`. **Холодное первое открытие хуже на 190-340 мс** (206 мс против 17 на `ai-cyborg`); оно приходится на старт хостов. Правило «не хуже базы на 10%» для холодного открытия **не выполнено**, отклонение объяснено загрузкой модулей и первым запуском процесса, но не разложено по частям (не измерялось).
- **Нагрузка простоя:** слежение 0,1-0,2% ядра против 0,4-16,8% у опроса (раздел 3): лучше базы на порядок и более, растёт с размером репозитория. Сам Cyborg не запускался; эмуляция берёт у него команды и период тика, но не его отрисовку.
- **Обновление после правки:** 90-460 мс против «до 3 с + `git status`».

## Решения (принято по поручению владельца 2026-11-10)

1. **Открытие файла - команда `viewer.open`, а не `file.open` и не член контракта.** Команда исполнителя обязана лежать в его пространстве имён (`${id}.`, [ADR-CH-0016](../04-architecture/adr/ADR-CH-0016-command-callers.md), п. 6), поэтому `file.open` из SAD мог бы объявить только плагин `file`; `callers: "plugins"` и `guard` `fs.read` на `path` дают ту же проверку права вызывающего, что `via-contract` у члена контракта (общий `Guard`, `checkFor`). Критерий задачи «через контракт с правом на аргумент» закрыт этим механизмом; SAD (разд. 3.4, 5) и руководство исправлены на `viewer.open`.
2. **Черновики контрактов - подмножество SAD.** `cyborg.git` v1: `status(repo)`, `onChange(repo, listener)`; остальные члены (`headContent`, `branches`, `switch`, `remotes`, `files`) придут необязательными (минор), [#196](https://github.com/dex-it/cyborg-harness/issues/196). `cyborg.tree-decoration` v1: `marks(root)`, `onChange(listener)`, кратность many, объявляет владелец дерева. Не репозиторий - `status` отвечает `null`. Минимальная обратимая форма: добавление членов - минор, пакет в линии `-dev`.
3. **`git status` без `--untracked-files=all`.** Цена одинакова (раздел 2), а неотслеживаемый каталог приходит одной записью; дерево отмечает всё внутри него само.
4. **Защита `git`.** Правило `process` закрепляет `--no-optional-locks -c core.fsmonitor=false -c core.hooksPath=/dev/null status --porcelain=v1 -z --branch` (как `SAFE_CONFIG` в ai-cyborg); тест доказывает, что без защиты этот `git` выполнил бы `core.fsmonitor` из конфига репозитория, а с ней - нет. **Фильтры `filter.*.clean|process|required`** из конфига репозитория (их `status` гоняет по файлам с изменившимся stat, одним `-c` не отключить) перекрыты ([#183](https://github.com/dex-it/cyborg-harness/issues/183), принято по поручению владельца 2026-11-10): перед каждым `status` плагин собирает ключи репозитория и вложенных (`config --show-scope --null --name-only --get-regexp`, `ls-files --stage -z`, рекурсия по заполненным подмодулям до глубины 8) и передаёт `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*`, `GIT_CONFIG_VALUE_*` (`filter.*.required` получает `false`, остальные - пустое значение), как `filterOverrides` в ai-cyborg; `playground/plugins/git/filters.ts`. Три правила `process` закрепляют аргументы и имена переменных (`env` правила, маска для номерных); фильтры пользовательского и системного конфига доверенные и остаются. Сбой сбора ключей (вывод длиннее предела, ключ или путь подмодуля не в UTF-8, вложенность глубже предела) отказывает всему `status`: неполный набор ключей молча не используется. Тесты: фильтр репозитория и подмодуля не выполняется (контроль: тот же `git` без перекрытия его запускает), `playground/test/pilot-git.test.ts`, `git-filters.test.ts`. **Цена:** на каждый опрос теперь три запуска `git` вместо одного (`config` и `ls-files` идут параллельно, потом `status`); замер `npm run pilot:files` в этой задаче не повторялся, числа раздела 2 сняты до неё, `gitRuns` в стенде считает только `status`.
5. **Предел слежения** - см. выше: узлам хватает, отметкам нет, [#182](https://github.com/dex-it/cyborg-harness/issues/182).
6. **Лавина и смена ветки.** После тишины в 300 мс перечитываются все раскрытые узлы, если подряд пришло не меньше 16 имён или git сообщил об индексе или голове. Порог и тишина подобраны по замерам, константы в `files/index.ts`.
7. **Пилотные плагины не включены в `DEFAULT_CONFIG`**, окна у них нет: цель - ядро и контракты. Они собираются в `playground/dist/plugins`, но не входят в упакованную поставку (`dist/delivery`): её проверка ждёт, что каждый плагин поставки активен.

## Остатки и открытые наблюдения

- **Рекурсивное слежение и закрытие слежения при удалении каталога** в шлюзе - [#182](https://github.com/dex-it/cyborg-harness/issues/182) (см. «Предел слежения»).
- **`git`: полный набор членов `cyborg.git`** - [#196](https://github.com/dex-it/cyborg-harness/issues/196), по мере потребителей. Перекрытие `filter.*.clean` закрыто ([#183](https://github.com/dex-it/cyborg-harness/issues/183)); вопрос 5 SAD (списки `process`) остаётся общим.
- **Перекрытие фильтров: окно между сбором ключей и `status`.** Конфиг репозитория, переписанный в эти миллисекунды другим процессом, ключ уже не попадёт в набор; граница та же, что у `filterOverrides` в ai-cyborg (кто пишет в `.git/config`, исполняет код и без фильтра). Цену трёх запусков можно снять кэшем набора ключей по mtime `.git/config` и индекса, если замер покажет нужду.
- **Ни одно событие не доходит - дерево не узнает.** Если ОС теряет все события каталога и `.git`, перечитывание не включится (нет триггера); без опроса это не лечится, лечит только рекурсивное слежение плюс сверка по фокусу окна (`ctx.window.onFocusChange`), не сделанная здесь.
- **`ctx.os.fs` без `lstat`:** `FileStat.kind` раскрывает ссылку, поэтому для нового имени в событии узел читает каталог (`list`), а не делает `stat`.
- **Хвост #147.** Каждый тест, который меняет файлы сразу после `fs.watch`, сначала «взводит» слежение пробной записью (`arm` в `pilot-files.test.ts`, как в `core/test/os.test.ts`); без этого удаление раскрытого каталога сразу после слежения терялось в 2 прогонах из ~20.
- **Репозиторий должен быть корнем рабочего дерева:** пути `git status --porcelain` считаются от корня, у подкаталога репозитория метки не совпали бы с деревом.
- **Не измерялось:** Electron `utilityProcess` вместо `child_process`; Linux (`inotify`, рекурсия Node); настоящий Cyborg под нагрузкой (только эмуляция тика); разложение холодного открытия; `fs.lstat`.
