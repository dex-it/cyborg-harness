# Пилот PL-07: CLI-плагин с пулом процессов и отменой (срез трекеров)

Задача [PL-07 #30](https://github.com/dex-it/cyborg-harness/issues/30). Дата: 2026-11-11. Вопрос: выдерживает ли ядро путь «трекеры Cyborg через `gh api`, `glab api`, `jira`»: пул запросов с конкуренцией 6, тайм-аут 120 с, предел вывода, убийство группы процессов при тайм-ауте и выгрузке плагина, отмена устаревшего запроса. Плагин `playground/plugins/trackers` нужен для проверки ядра и контрактов, а не как перенос: окна у него нет, в `DEFAULT_CONFIG` его нет, в поставку приложения он не входит (`PILOT_ONLY` в `playground/scripts/build.mjs`), а проверяемые свойства закреплены тестами `playground/test/pilot-trackers.test.ts`.

## Что сделано

| Пункт задачи | Что в репозитории |
|---|---|
| 1. Плагин-срез `trackers` | `playground/plugins/trackers`: `trackers.list(tracker, цель, { requestId?, timeoutMs? })` для `github` (`gh api`), `gitlab` (`glab api`) и `jira` (`jira issue list --raw`); права `process` с закреплёнными префиксами аргументов и именами переменных (`manifest.json`); пул на 6 (`pool.ts`, `POOL_SIZE`). Контракт `cyborg.trackers` не заводился: плагин отдаёт команды (`callers: "plugins"`), чтобы не менять публичный API до заморозки |

## Как мерили

- **Стенд.** Ядро поднимает плагин в хосте-процессе (`forkHosts`), потребитель - проба в другом хосте; шлюз в главном процессе тот же, что в приложении. **Это не Electron:** цена вызова между хостами здесь - канал `child_process`, а не `utilityProcess`.
- **Программы.** Подставные `gh`, `glab`, `jira` - обёртки в `PATH`, запускающие `fake-trackers.mjs`. Журнал ведёт сама программа, не плагин: в `calls.log` на каждый запуск пишется, сколько программ было живо в момент старта (каталог `live/` с файлом на pid, живость по `kill(pid, 0)`), `children.log` называет внуков. Пик и сироты берутся из этого журнала, а не из счётчиков плагина (счётчики плагина `trackers.stats` в тесте сверяются с ним).
- **Сирота.** pid программы или её внука, который отвечает на `kill(pid, 0)` после отмены, тайм-аута или выгрузки. Внук программы (режим `child`) остаётся в её группе процессов, как сборка или MCP-сервер.
- **Машина.** MacBookPro Apple M1 Pro, macOS, Node v24.20.0. **Чистого сеанса не было:** load average (1 минута) на старте прогонов 12-16 (параллельные прогоны других задач); запуск `node` для подставной программы стоит из-за этого около 300 мс, для времени ответа пула это шум в худшую сторону.

## 1. Пул: число процессов в пике и время ответа

20 вызовов `gh api` к разным репозиториям, каждый отвечает через 250 мс, пул 6 (3 прогона):

| Показатель | Значение |
|---|---|
| Пик живых программ по журналу самих программ | **6** во всех прогонах (потолок достигнут, не превышен) |
| Время 20 вызовов | 1 245 - 1 503 мс (4 волны по 250 мс плюс запуск `node` на волну) |
| Одиночный вызов через плагин и ядро / голый запуск той же программы | 301 / 298 и 303 / 299 мс (медиана 9): добавка плагина, канала и шлюза - единицы миллисекунд, в пределах шума |
| Счётчики плагина после серии | `limit 6, running 0, queued 0, peak 6`, `failed 0`, сирот 0 |

Потолок ядра на одновременные `process.run` плагина - 16 (`LIMITS.runs`), сверх него `Invalid` без очереди. Пул на 6 лежит под ним с запасом. **Очередь принадлежит плагину:** ядро только держит потолок и не знает ни о приоритетах, ни об очередях (решение: SAD, раздел 3.7, пункт про пределы, и вопрос 23). Плагину с несколькими пулами (трекеры, поиск, MR) сумма их конкуренций должна укладываться в 16, иначе вызов получает `Invalid`; это стоит учесть при переносе (открытое наблюдение).

## 2. Тайм-аут и выгрузка: сирот нет

| Событие | До исчезновения всех программ и внуков (мс, 3 прогона) | Сирот |
|---|---|---|
| Тайм-аут 500 мс у зависшей программы с внуком | 0 - 1 | 0 |
| Выгрузка плагина при 6 работающих программах, 6 внуках и 4 запросах в очереди | 3 - 14 | 0; очередь программ не запускала (в журнале программ 6 запусков) |
| Отмена сигналом (K-09), программа с внуком | 11 - 13 | 0 |
| Отмена по идентификатору | 11 - 13 | 0 |

Замеры - от возврата вызова, поэтому они измеряют остаток после того, как вызывающий уже получил отказ. В ядре поправлена одна дыра: отмена слала группе только `SIGTERM`, а тайм-аут и предел вывода добавляют `SIGKILL` через 2 с. Программа, глушащая `SIGTERM`, переживала отмену и держала место в пределе одновременных запусков до выгрузки плагина. Теперь отмена идёт тем же `terminate()` (тест `core/test/os-lifetime.test.ts`, краснел на прежнем коде; раздел «Решения» SAD, вопрос 23).

## 3. Отмена

- **Сигналом (K-09).** Потребитель передаёт `AbortSignal` последним аргументом `ctx.commands.run`; обработчик получает сигнал, связывает его со своим контроллером и передаёт тот же сигнал в `process.run`. Вызывающий получает `Cancelled` сразу, процесс и внук завершены.
- **Идентификатором.** Вид сигнала передать не может, поэтому запрос несёт `requestId`, а `trackers.cancel(requestId)` отменяет его (`true`; для неизвестного или законченного запроса `false`). Занятый `requestId` - ошибка.
- **В очереди.** Отменённый запрос покидает очередь и вызывает `process.run` с уже сработавшим сигналом: ядро отказывает `Cancelled` и программу не запускает. Так отказ несёт настоящий код ядра - плагин сам его построить не может (раздел 6).
- **Устаревший ответ.** Новый запрос к тому же списку отменяет прежний (`superseded` в счётчиках); старый вызывающий получает `Cancelled`, а не данные. Ответ, который успел прийти до сработавшей отмены, тоже не отдаётся (проверка после `await process.run`).

## 4. Предел вывода

Задача описывала молчаливую обрезку на 16 МиБ без признака. К началу пилота это уже не так: K-12 ([ctx-os-coverage.md](ctx-os-coverage.md)) задал предел в **байтах** на `stdout` и `stderr` отдельно, `ProcessOptions.maxOutputBytes` (от 1 байта до 64 МиБ, по умолчанию 16 МиБ), `ProcessResult.truncated` и остановку программы (`SIGTERM`, через 2 с `SIGKILL`). Из трёх вариантов задачи (настраиваемый предел, явный признак, убийство) выбраны все три, форма API не менялась. Поведение закреплено `core/test/os.test.ts` и контрактами; пилот добавляет:

- плагин просит `maxOutputBytes: 64 МиБ` (буфер трекеров Cyborg, он же потолок ядра);
- ответ в 20 МиБ (больше 16, меньше 64) приходит целым JSON, все 20 МиБ на месте;
- ответ в 65 МиБ даёт ошибку `trackers: ответ gh больше 64 МиБ, список не прочитан целиком`, а не оборванный JSON; программа остановлена;
- **что обязан делать любой плагин:** проверить `truncated` до разбора. Забытая проверка не даёт тихой потери (`signal` остановленной программы и оборванный JSON тоже станут ошибкой), но с неверным текстом: мутация пилота «проверку `truncated` убрать» краснит тест на ошибку «ответ больше».

Что можно добавить в ядро и чего пока не сделано: ядро не отличает обрезку от целого ответа за плагина (решает плагин: трекер отказывает, поиск берёт прочитанное); для трекеров этого достаточно.

## 5. Правила аргументов: что нужно ядру

Правило `process` сверяет программу, **первые** аргументы по позициям и имена переменных. Всё после закреплённого префикса правило не видит. Тест `trackers: чужая программа…` показывает обе стороны на правилах манифеста `trackers`:

| Вызов | Результат |
|---|---|
| `rm …`, `gh auth token`, `gh api --method DELETE …`, `jira issue delete …`, `GH_TOKEN` в `env` | `PermissionDenied`, запись `denied` с причиной (аргументы не называются: в них бывают токены), программа не запускалась. Подряд идущие одинаковые отказы журнал склеивает |
| `gh api --method GET repos/a/b/issues -X DELETE --hostname evil.example` | **проходит:** префикс совпал, флаги в хвосте ядро не проверяет |

Отказ в середине команды (например, запрет `--hostname`, `--input`, `-X` после общего префикса) ядром сейчас невозможен. В пилоте это закрыто в плагине: цель запроса (`owner/repo`, путь проекта, ключ Jira) проверяется по списку допустимых сегментов, ни один не начинается с `-`, и сегмент попадает в argv одним элементом (`tools.ts`, тест «цель с флагом или лишними сегментами…»). Этого достаточно, пока argv собирает сам плагин.

**Что нужно ядру, если списки опасных флагов Cyborg (разрешённые и запрещённые флаги, SAD, вопрос 5) переносятся в манифест.** Минимальная обратимая форма - необязательное поле правила `deny: readonly string[]` рядом с `args`: ядро отказывает, если любой элемент argv после префикса равен названному флагу или начинается с `флаг=`. Это минорное добавление `ProgramRule` (существующие правила не меняются). Требует решения владельца до заморозки API (D-00, строка 9): форма (`deny`, `allow` или шаблон хвоста), кто ведёт списки для `git`, `gh`, `glab` и как сверяет их с новыми версиями программ. **Исполнитель API не менял**: пилот закрыт на стороне плагина, обратимого вреда нет.

## 6. Открытые наблюдения

- **Ошибка с кодом из плагина.** Плагин не может построить `CoreError`: контракты экспортируют только тип `CoreErrorCode`, а любая обычная ошибка обработчика приходит вызывающему как `Remote`. Пилот получает `Cancelled` для запроса в очереди обходом (вызов `process.run` с сработавшим сигналом). Если плагинам нужны свои коды (`Cancelled`, `Timeout`), ядру потребуется способ их задать.
- **`cwd` и `NotFound`.** Нет каталога `cwd` - тот же `NotFound`, что и «программы нет в PATH»; каталог `plugin-temp` ядро не создаёт заранее, поэтому плагин создаёт его сам при активации (`fs.mkdir`). Понять причину по тексту: `spawn gh ENOENT` одинаков.
- **Сумма пулов плагина** не больше 16 (раздел 1).
- **Windows.** Группы процессов - POSIX (`detached`, `kill(-pid)`); тесты выгрузки и отмены, как и прежние `os-lifetime`, на Windows пропускаются. Windows вне первой версии (D-00, строка 7).
- **Права `net` для хабов** с пользовательскими адресами пилот не затрагивает: он ходит через программы, а не через `net.fetch`; переход на HTTP API не входит в задачу.

## Не проверено

- Настоящие `gh`, `glab`, `jira` с входом в аккаунт и сетью: живого `claude` и входа у исполнителя нет, поведение программ взято из `interpret` Cyborg по [ctx-os-coverage.md](ctx-os-coverage.md). Ручная проверка: `gh auth status && gh api --method GET 'repos/dex-it/cyborg-harness/pulls?state=open&per_page=100' | wc -c`, то же для `glab api` и `jira issue list --raw -p <ключ>`, с реальными размерами ответов.
- Electron (`utilityProcess`) и конкуренция 6 при реальных сетевых задержках.
- Ответ настоящего `gh api` в десятки МиБ (`--paginate` крупного репозитория): проверен только подставным JSON в 20 и 65 МиБ.
