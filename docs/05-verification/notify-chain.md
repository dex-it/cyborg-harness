# Пилот PL-02: хук - статус - уведомление в другом плагине

Задача [PL-02 #18](https://github.com/dex-it/cyborg-harness/issues/18), зависит от [K-19 #57](https://github.com/dex-it/cyborg-harness/issues/57). Вопрос: доходит ли событие хука `claude` до плагина в другом хосте без общей шины, показывает ли тот уведомление по правилам (окно без фокуса, один раз на событие), снимает ли его при работе сессии и возвращает ли клик в команду плагина.

Дата: 2026-11-10. Стенд: macOS 27.2 (26B123), Apple M1 Pro, Node 24.20, Electron 45.2.2 (замер - Node без Electron, см. разд. 4). Linux в этой сверке не снимался.

## 1. Что собрано

| Звено | Где | Что делает |
|---|---|---|
| Хук claude | `agent-claude-code`, `HOOK_COMMAND` в `--settings` | `{ cat; echo; } >> "$CYBORG_EVENTS"`: JSON события дописывается в файл сессии |
| Чтение файла | `agent-claude-code`, `watch` | `ctx.os.fs.watch` каталога сессий, `readSlice` от места, где остановились; строки в `AgentEvent` |
| Статус сессии | `sessions`, поставщик `cyborg.sessions` | `AgentEvent` -> `SessionEvent` (`cwd`, `activity`, `waiting`, `exit`) для подписчиков из других хостов |
| Решение «показать» | `session-notifications`, `optional: cyborg.sessions` | `waiting` и окно без фокуса (`ctx.window.onFocusChange`) -> `ctx.os.notify.show(..., { onClick })`; `activity` и `exit` -> `notify.close` |
| Клик | ядро (K-19) + команда `session-notifications.open` | Ядро поднимает окно (`raiseWindow`), закрывает уведомление и запускает команду плагина с id сессии |

Контракт `cyborg.sessions` 1 введён черновиком: только `onChange` (`contracts/sessions.ts`, решения - в описании PR). Расхождение с SAD: раздел 5 называет `sessions` плагином, а члены `create`, `send`, `reveal`, метки в пакете ещё не объявлены.

## 2. Критерии задачи и чем они закрыты

| Критерий | Чем закрыт | Статус |
|---|---|---|
| Два плагина в разных хостах: «ждёт» из `sessions` доходит до `session-notifications` | `playground/test/session-notifications.test.ts`: «те же плагины в разных процессах ОС (forkHosts)» - три процесса Node, хук - настоящая команда из `--settings`, `k.hostOf` у всех разный | автоматически |
| Окно без фокуса - уведомление один раз на событие; в фокусе - нет | тот же файл: «ждёт от хука… один раз на событие», «окно в фокусе… (гонка)»; среда уведомлений подставная | автоматически |
| Гонка «событие пришло, пока фокус только что вернулся» | «окно в фокусе… (гонка)»: фокус ушёл и вернулся до события - уведомления нет | автоматически |
| Клик вызывает команду плагина | «клик по уведомлению поднимает окно и запускает команду плагина» (`events.click()` подставной среды: ядро поднимает окно через `raiseWindow` и запускает `session-notifications.open` с id сессии); то же через границу процессов в forkHosts-тесте | автоматически, до границы приложения |
| Клик по настоящему системному уведомлению возвращает фокус окну | нет возможности нажать баннер ОС из теста; пошаговая проверка - разд. 5 | **вручную, владельцем** |
| Закрытие из плагина | «сессия снова занята или вышла - уведомление снимается»: новый запрос человека и выход снимают уведомление своей сессии, чужая не затронута; шлюз K-19 - `core/test/os.test.ts` («notify: клик… close, пределы и выгрузка») | автоматически |
| Без права `notify` отклоняется и попадает в журнал | у плагина без права нет `ctx.os.notify` (тест «без права notify…»: плагин пишет в журнал, что показывать нечем, цепочка работает); подделанный запрос `notify.show` и `notify.close` - `PermissionDenied` и запись `denied` в журнале плагина (`core/test/trust.test.ts`, «os: notify.show и notify.close…») | автоматически |
| Задержка от записи хука до показа | разд. 4 | измерено на macOS |
| Проверка на подставном `claude` | хук - настоящая команда из `--settings`, `claude` в PATH - заглушка из `agentEnv` (как в `playground/test/agents.test.ts`) | автоматически |
| Проверка на живом `claude` | не выполнялась: нужны вход в аккаунт и сеть | не проверено |

## 3. Что показали тесты о ядре

- Подписка на `cyborg.sessions` проходит границу хостов штатно (правило 5 модели контрактов): колбэк остаётся в хосте потребителя, `dispose` снимает его у поставщика. Отдельной шины не понадобилось.
- `onFocusChange` сообщает только перемены. Начального состояния нет: плагин считает окно активным до первой перемены (иначе каждый запуск начинался бы с уведомлений). Если плагин поднят, когда окно уже без фокуса, первое событие «ждёт» будет пропущено. Для переноса уведомлений Cyborg это пробел API: нужен способ спросить текущий фокус (`ctx.window.focused()` или начальное значение в первом вызове). Вынесено в открытые наблюдения PR.
- Нет способа открыть вкладку документа сессии из плагина: клик поднимает окно и запускает команду, но выбрать вкладку нечем (`ctx.documents` умеет `open`, `save`, `close`, `list`). Команда `session-notifications.open` пока пишет в журнал и снимает учёт уведомления. Для переноса «клик открывает сессию» нужен член `reveal` в `cyborg.sessions` и способ активировать документ у ядра. Вынесено в открытые наблюдения PR.
- «Ждёт» после обычного конца хода приходит не сразу: `agent-claude-code` объявляет `waiting` через `STOP_QUIET_MS` = 30 с тишины после `Stop` (чужой Stop-хук может продолжить ход). Уведомления о разрешении и вопросе (`Notification`) идут без этой паузы.

## 4. Задержка от записи хука до показа

Запуск: `npm run spike:notify-chain -- --samples=100` (`playground/test/measure-notify-chain.ts`). Цепочка та же, что в окне: хук `Notification`/`permission_prompt` (настоящая команда `{ cat; echo; } >> "$CYBORG_EVENTS"`) -> файл -> `fs.watch` и `readSlice` в `agent-claude-code` -> `sessions` -> `cyborg.sessions` -> `session-notifications` -> `ctx.os.notify.show` -> среда уведомлений ядра. Три плагина в трёх процессах (`forkHosts`). Показ - подставная среда: замерена цепочка плагинов, не время, за которое ОС рисует баннер. Пять первых образцов - прогрев, в итог не идут.

Два прогона по 100 образцов, macOS 27.2, M1 Pro, при другой работе на машине (load average 20-30, как и в [macos-check.md](macos-check.md)):

| Интервал, мс | min | p50 | p95 | p99 | max |
|---|---|---|---|---|---|
| от конца записи хука до показа, прогон 1 | 51,3 | 63,7 | 74,6 | 80,8 | 81,0 |
| от конца записи хука до показа, прогон 2 | 51,8 | 63,3 | 90,4 | 122,0 | 126,9 |
| сам запуск хука (sh, cat, дозапись), прогон 1 | 9,3 | 15,1 | 28,4 | 35,7 | 42,3 |
| сам запуск хука, прогон 2 | 9,3 | 21,4 | 54,9 | 82,4 | 110,8 |
| от старта хука до показа, прогон 1 | 63,7 | 80,2 | 95,8 | 108,7 | 110,5 |
| от старта хука до показа, прогон 2 | 65,1 | 87,6 | 133,4 | 167,0 | 170,4 |

Выводы:

- Медиана от записи до показа - около 63 мс, худший из 200 образцов - 127 мс. Для уведомления о «ждёт» это ниже порога заметности.
- Около 50 мс из 63 - окно склейки событий `fs.watch` шлюза ядра (`WATCH_COALESCE_MS` в `core/src/os-gateway.ts`): события каталога копятся 50 мс и уходят пачкой. Остальные 10-15 мс - три прыжка между процессами и чтение среза. Если окно склейки понадобится уменьшить для других задач, нижняя граница цепочки - около 10-15 мс.
- Linux и Windows не измерялись; `fs.watch` там опирается на inotify и другие механизмы. Замер повторяется той же командой.
- Электрон в замере не участвует: отправка баннера и его клик - зона ОС (разд. 5).

## 5. Ручная проверка владельцем: клик по системному уведомлению

Автоматически нельзя нажать баннер ОС: событие `click` объекта `Notification` в Electron приходит от системы. Проверить нужно два свойства адаптера (`electron/src/os-env.ts`): объект `Notification` не теряется сборщиком мусора и клик по нему поднимает и фокусирует окно, а затем запускает команду плагина. Проверка одинакова на macOS и Linux; на Windows вне области (вопрос 12 SAD).

Подготовка (один раз):

```sh
npm ci && npm run build
FAKE=$(mktemp -d)
printf '#!/bin/sh\nexec "%s" "%s/playground/scripts/fake-claude.mjs" "$@"\n' "$(command -v node)" "$PWD" > "$FAKE/claude"
printf '#!/bin/sh\nPATH="%s":"$PATH"; export PATH\nif [ "$1" = -lc ]; then shift; exec /bin/sh -c "$@"; fi\nexec /bin/sh "$@"\n' "$FAKE" > "$FAKE/login-shell"
chmod +x "$FAKE/claude" "$FAKE/login-shell"
SHELL="$FAKE/login-shell" npx electron . --user-data-dir="$FAKE/data" --no-workspace
```

Подставной `claude` из `playground/scripts/fake-claude.mjs` по слову `ask` пишет в файл событий хук `PostToolUse`, затем `Notification` с `permission_prompt` - то же, что настоящий `claude`, когда просит разрешение; по слову `work` - только `PostToolUse` (сессия занята).

Шаги:

1. В окне стенда открыть сессию агента «Claude Code» (кнопка в панели сессий). В терминале должно появиться `fake claude: готов`.
2. Разрешить уведомления приложению Electron в настройках ОС, если ОС спросит (macOS: Системные настройки - Уведомления; Linux: ничего или настройки среды рабочего стола).
3. Ввести в терминале сессии `ask` и Enter, затем сразу переключиться в другое приложение, чтобы окно стенда потеряло фокус (в течение секунды).
4. Ожидаемо: системное уведомление с заголовком «Claude Code s…» и текстом «Просит разрешение» появилось один раз.
5. Нажать на уведомление. Ожидаемо: окно стенда вышло на передний план и получило фокус, уведомление пропало; в разделе «Журнал» плагина `session-notifications` (вкладка журнала) появилась строка `открыта сессия s…`.
6. Закрытие из плагина: повторить шаги 3-4 и не нажимать на баннер; вернуться в окно и ввести `work` и Enter (подставной `claude` пишет хук `PostToolUse`: сессия снова занята). Ожидаемо: баннер пропал сам, без нажатия.
7. Фокус в окне: ввести `ask`, не уходя из окна. Ожидаемо: уведомления нет, в журнале плагина строка «окно в фокусе, уведомление не нужно».

Что записать в PR при проверке: ОС и версия, оконный менеджер (Linux), прошёл ли каждый из пунктов 4, 5, 6, 7; если баннер не пришёл - включены ли уведомления Electron в ОС.

Не вошло в проверку: звук, значок баннера, выключатель уведомлений ([K-08](https://github.com/dex-it/cyborg-harness/issues/45)), перенос уведомлений Cyborg целиком (вне PL-02).
