# Пилот PL-10: трекер через HTTP API с токеном и правом net

Задача [PL-10 #226](https://github.com/dex-it/cyborg-harness/issues/226). Дата: 2026-11-12. Вопрос: хватает ли ядру, чтобы плагин-трекер был плагином узкого класса ([SAD, 3.7](../04-architecture/design/sad.md#37-безопасность-данных-и-контроль-плагинов), «Два класса плагинов»): сеть к хосту, который назвал человек, и свой токен, без права `process` на `gh`, `glab`, `jira` и без файлов. Решение владельца 2026-11-11 (D-00 строка 19, [спорный пункт 15](../04-architecture/design/sad2-disputed-points.md#15-трекеры-cli-или-http-api)): трекеры ходят через HTTP API. Пилот PL-07 ([pilot-trackers.md](pilot-trackers.md)) проверил ядро на CLI-срезе; здесь проверен HTTP-срез.

Плагин `playground/plugins/trackers-http` нужен для проверки ядра и контрактов, а не как перенос: окна у него нет, в `DEFAULT_CONFIG` его нет, в поставку приложения он не входит (`PILOT_ONLY` в `playground/scripts/build.mjs`). Продуктовые плагины трекеров живут в репозитории Cyborg. Свойства закреплены тестами `playground/test/pilot-trackers-http.test.ts` (10 тестов) и `core/test/net-fetch.test.ts`, `core/test/workspace-trust.test.ts`.

## Что сделано

| Пункт задачи | Что в репозитории |
|---|---|
| 1. Плагин на HTTP API одного трекера | `playground/plugins/trackers-http`: GitLab API v4, `trackers-http.list(хаб, issues\|merge_requests, проект)` через `ctx.os.net.fetch`, страницы по 100 до 10 штук (дальше список помечен `truncated`). Права в манифесте - только `"net": ["config:hubs"]` (тест сверяет манифест и разобранные права ядра). GitLab, а не GitHub: хост GitHub один, а сценарий «хост от человека» нужен именно у GitLab и Jira |
| 2. Хост от человека; несколько хостов | Раздел 1. Одна строка в `config:<поле>` работала; список не выражался. Теперь значение поля - строка или список строк (кандидат API `1.0.0-rc.3`) |
| 3. Частный адрес корпоративного хоста | Раздел 2. Решение: разрешает человек, называя хост в config слоя пользователя; признака в манифесте нет. Правило ядра не менялось, закреплено тестами пилота |
| 4. Токен | Раздел 3: ввод человеком, хранение, вычёркивание (K-29), отказ при отсутствии |
| 5. Итоги, SAD, дорожная карта | Этот документ; SAD 3.7 и вопрос 27 раздела 8; спорный пункт 15; дорожная карта (строка PL-10 и строка 19 владельца); справочник прав; CHANGELOG контрактов |

## Как мерили

- **Стенд.** Настоящее ядро; плагин `trackers-http` и пробы в хостах-процессах (`forkHosts`, как в пилотах PL-04 и PL-07); шлюз в главном процессе тот же, что в приложении. Слои `config` (`user`, `workspace`) - настоящий `SectionStore` над слоями в памяти, секреты - `memorySecrets` тест-кита. **Это не Electron:** хранилище секретов приложения (`safeStorage`) и окно ввода токена в пилоте не участвуют.
- **Трекер.** Подставной GitLab на `127.0.0.1` (`playground/test/trackers-http-kit.ts`): принимает токен по заголовку `Host`, отдаёт страницы с `x-next-page`, умеет 401 с эхом токена в теле, 302 и 500. Сервер ведёт свой журнал (`fake.seen`: хост, путь, присланный токен), поэтому «до сети дошло» и «токен ушёл» читаются по нему, а не по словам плагина.
- **Корпоративный хост с частным адресом.** Имена `gitlab.corp.example` и `gitlab2.corp.example` резолвятся подставным `lookup` ядра (`OsEnvironment.lookup`) в `127.0.0.1`: для ядра это локальный адрес, как частный адрес Jira или GitLab за VPN. Пропуск или отказ виден по тому, дошёл ли запрос до сервера.
- **Что собрано снаружи плагина.** Журнал ядра (`Kernel.journal` и `onJournal`), строки плагина (`onLog`), записи трассы (`onTrace`, K-28), документы слоёв `config`: по ним ищется токен.
- **Красный прогон.** Каждое поведение проверено порчей целевой ветки (в PR перечислено; сужение по link-local - тесты красные до правки, 5 из 16 в `net-fetch.test.ts` и 1 из 11 пилотных): без проверки токена, один ключ токена на все хабы, токен копируется в `config`, ядро без списка хостов, ядро без «названный хост пускает на локальный адрес» - тесты краснеют, после возврата зелёные.

## 1. Хост от человека и несколько хостов

**Что было.** `"net": ["config:baseUrl"]` пускает на хост из поля `baseUrl` раздела `config` плагина; значение берётся только из слоя пользователя (ADR-CH-0015), слой воркспейса права не расширяет. Поле держит одну строку. Хабов Cyborg у человека несколько и неизвестное число (D-00 строка 17: «список хабов не выражается»).

**Варианты.**

| Вариант | Итог |
|---|---|
| `"net": ["config:hub1", "config:hub2", ...]` | число хабов зашивает автор плагина в манифест; отвергнут |
| Маска `*.corp.example` | открывает поддомены неизвестного состава; шире, чем нужно; отвергнут |
| Значение поля - строка **или список строк** | **принят.** Манифест и его схема не меняются, право выдаёт тот же слой пользователя; обратим одной функцией (`configHost` в `core/src/os-gateway.ts`) |

**Форма.** Элемент списка - адрес (`https://gitlab.corp:8443/api`) или `хост:порт` без схемы; не строки в списке пропускаются. Заодно исправлен разбор `хост:порт`: `new URL('gitlab.corp:8443')` читает `gitlab.corp:` как схему и давал пустой хост, то есть молчаливый отказ. Изменение API: кандидат `1.0.0-rc.3` (минор, декларации типов не менялись, `net` остаётся `readonly string[]`; снимок пакета отличается только номером версии, эталон `core/test/api-snapshot/1.0.0.txt` не менялся). Плагин на ядре rc.2 прочёл бы список как «хоста нет» и получил бы `PermissionDenied`, лишнего не открыл бы.

**Проверки.**

| Свойство | Тест |
|---|---|
| Каждый элемент списка из слоя пользователя пускает; хост вне списка, порт вне записи, не строки - `PermissionDenied`, запрос до сервера не дошёл | `core/test/workspace-trust.test.ts`, «config:<поле> со списком…» |
| Список в слое воркспейса не даёт ни одного хоста; причина в журнале называет поле и «файл воркспейса» | то же |
| Воркспейс перекрывает список для плагина (`ctx.config.get()`), но не для права; правка списка человеком в файле пользователя расширяет, правка воркспейса нет; плагин свой список расширить не может (`config.set` - `PermissionDenied`) | то же, второй тест |
| Хаб из слоя пользователя работает, хаб из файла воркспейса - `PermissionDenied` (ADR-CH-0015), плагин видит оба в `ctx.config`, токен для второго лежит и не уходит | `playground/test/pilot-trackers-http.test.ts`, «хаб, заданный в слое пользователя…» |
| Два хаба в одной настройке, `хост:порт` без схемы работает на живом сервере | пилотный тест «несколько хабов…» |

## 2. Частный адрес корпоративного хоста (У-35)

**Задача.** `net.fetch` отвергает локальный и частный адрес из DNS, если хост не назван IP, `localhost` или именем в `.localhost` (К-25, [SAD, 3.7](../04-architecture/design/sad.md#37-безопасность-данных-и-контроль-плагинов)). Внутренний GitLab или Jira резолвится в частный адрес. Как человеку разрешить его, не открывая частную сеть всем плагинам.

**Что уже было в ядре.** Хост из `config:<поле>` ядро считает названным человеком и проверку адреса для него не ведёт. То есть путь существует, но не был закреплён сценарием «корпоративный хост, который сам резолвится в частный адрес»; пилот закрепляет его.

**Решение (принято по поручению владельца 2026-11-12).** Разрешает человек, и только он: называет хост в поле config своего слоя пользователя. Отдельного признака в манифесте (`private: true`, `allowPrivate`) не вводится.

| Основание | Следствие |
|---|---|
| Манифест пишет автор плагина, config слоя пользователя - человек. Признак в манифесте дал бы автору открыть частную сеть без человека | право на частную сеть выдаёт только слой пользователя |
| Право привязано к плагину и хосту | чужой плагин с тем же именем в манифесте или с пустой настройкой получает отказ (тест) |
| Файл воркспейса приходит из репозитория команды | хост из него частной сети не открывает (тест) |
| Не нужны ни новое поле, ни новая версия API | решение обратимо, API не расширено |

**Проверки.** В одном ядре: плагин `trackers-http` с хабом `gitlab.corp.example` в слое пользователя доходит до сервера по адресу 127.0.0.1; проба `fixed` с записью `gitlab.corp.example:<порт>` в манифесте получает `PermissionDenied` «адрес 127.0.0.1 локальный» и до сервера не доходит; проба `bare` с правом `config:hubs`, но пустой настройкой, получает `PermissionDenied` «хост не в net» (пилотный тест «У-35…»). На транспорте ядра, без плагина: `core/test/net-fetch.test.ts`, «частный адрес корпоративного хоста…» (имя в списке config пускает, то же имя в манифесте и пустой список - отказ).

**Сужение (по ответу владельца 2026-11-12: безопасность и ограниченный доступ).** Названный хост получает loopback и частные сети, но не link-local (`169.254.0.0/16`, `fe80::/10`, в том числе IPv4 внутри IPv6: `::ffff:169.254.169.254`, NAT64, 6to4) и не известные адреса метаданных облака (`168.63.129.16`, `100.100.100.200`, `192.0.0.192`, `fd00:ec2::254`). Это сужение, а не новое поле: деклараций API оно не меняет и входит в кандидат `1.0.0-rc.3`. Проверка одна, `isForbiddenAddress` (`core/src/net-transport.ts`), вызывается из `#fetch` (`core/src/os-gateway.ts`): для имени - в соединении, на том же резолве, один закрытый адрес в ответе DNS - отказ целиком; для адреса-литерала - до соединения (DNS ему не нужен), записи числа `http://2852039166/`, `0xA9.0xFE.0xA9.0xFE`, восьмеричная сводит `URL` к одному виду. Переадресации ядро не выполняет, поэтому `Location` на такой адрес плагину отдаётся ответом 3xx и сам не идёт (тест). Тесты: `core/test/net-fetch.test.ts` (единица `isForbiddenAddress`, названный и неназванный хост, литералы, переадресация) и пилотный «хаб, названный человеком, но резолвящийся в link-local…».

**Остаток.** Перепривязка DNS на самом названном имени к частному адресу (не link-local) в модели не учтена: имя выбрал человек. Список адресов метаданных - известные на сегодня; новый облачный адрес вне link-local в него надо добавлять.

## 3. Токен

| Требование | Как сделано | Проверка |
|---|---|---|
| Ввод человеком | Команда `trackers-http.set-token(хаб, токен)` без `callers: "plugins"`: её зовёт человек (палитра, вид своего плагина); главная часть другого плагина получает `PermissionDenied` «не открыл команду другим плагинам». Токен - печатные символы без пробелов, до 4096 | пилотный тест «токен вводит человек…» |
| Хранение | Хранилище секретов ядра, ключ `trackers-http/token/<хост:порт>`: свой токен у каждого хаба, токен хаба не уходит на другой | тест «несколько хабов…»: сервер видит на каждом хосте только его токен; в хранилище ровно одна запись |
| Вычёркивание из логов (K-29) | Ядро вычёркивает значения, прошедшие через `ctx.os.secrets`, из строк плагина. Плагин нарочно пишет в `ctx.log` начало тела ответа при отказе, а подставной сервер в 401 повторяет присланный токен: в строке остаётся `401 Unauthorized: token [секрет]` | тот же тест; затем токена (и прежнего, перезаписанного) нет в журнале ядра, `onJournal`, строках плагина, записях трассы и документах слоёв `config`; тест проверяет, что журнал, строки и трасса непусты |
| Отказ при отсутствии | Нет токена хаба - ошибка «не задан токен» до сети, сервер запроса не видит. Токен отвергнут сервером (401, 403) - ошибка с кодом и просьбой ввести новый; переадресация (302) не выполняется, токен на другой хост не уходит | тесты «токен вводит человек…», «сервер отвечает ошибкой или переадресацией…» |
| Хост вне права | Токен задан хосту, которого нет в `hubs`: `ctx.os.net.fetch` - `PermissionDenied`, запись `denied` «хост не в net», до сервера запрос не дошёл | тест «запрос на хост вне права…» |

Тело ответа в сообщение об ошибке для вызывающего не попадает: только код. Тело (первые 200 символов) идёт в `ctx.log` и проходит через вычёркивание ядра.

## Решения

Принято исполнителем по поручению владельца 2026-11-12; каждое обратимо.

1. **Несколько хостов** - список строк в поле `config:<поле>`, кандидат API `1.0.0-rc.3` (раздел 1).
2. **Частный адрес** - разрешает человек, называя хост в config; признака в манифесте нет; правило ядра не менялось (раздел 2).
3. **`хост:порт` без схемы** в поле config читается (исправление молчаливого отказа в том же месте).
4. **GitLab, а не GitHub** в пилоте (раздел «Что сделано», п. 1).
5. **Токен привязан к хабу** (ключ хранилища на хаб), а не один на плагин: иначе токен одного хаба ушёл бы на другой.
6. **Окна ввода токена нет:** вид и форма настроек - продуктовый плагин Cyborg; пилот проверяет ядро, ввод - команда.
7. **Предел страниц** - 10 по 100 записей, дальше `truncated`, а не рост без предела.
8. **Link-local и метаданные облака закрыты и названному хосту** (раздел 2): ядро, без поля в манифесте и без нового кандидата.

## Не проверено

- **Настоящий GitLab:** токена и сети у исполнителя нет. Ручная проверка (токен с правом `read_api`; хаб - `https://gitlab.com` либо свой корпоративный хост, в том числе с частным адресом; проект - `группа/имя` или числовой id):

  ```
  GITLAB_TOKEN=<токен> npm run pilot:trackers-http -- https://gitlab.corp.example group/project issues
  GITLAB_TOKEN=<токен> npm run pilot:trackers-http -- https://gitlab.corp.example group/project merge_requests
  ```

  Скрипт `playground/scripts/pilot-trackers-http.mjs` поднимает ядро с плагином, вводит токен командой `set-token`, как человек, и печатает строки `ok` и `FAIL`: отказ без токена до сети, список (число записей и три первых заголовка), `PermissionDenied` для хоста вне настройки (`example.org`), токена нет в журнале и строках плагина. Токен берётся только из окружения, на диск не пишется, не печатается. Ожидание: все строки `ok`, код выхода 0. Для корпоративного хоста с частным адресом это и есть ручная проверка раздела 2: сработает, если имя резолвится в 10.x, 172.16-31.x, 192.168.x или 100.64.x и сеть (VPN) подключена. Результат (число записей, время) просьба записать сюда или в PR.
- **Electron и `safeStorage`:** хранилище секретов приложения (шифрование ОС, `Unavailable` на Linux без keyring) в пилоте заменено `memorySecrets`; поведение `Unavailable` проверено ядром отдельно (`core/test/os.test.ts`).
- **Jira и GitHub:** другая схема аутентификации (Basic, Bearer) и формат ответа; проверен только GitLab.

## Открытые наблюдения

- **Список адресов метаданных** (`METADATA_V4`, `METADATA_V6`) - известные облака на сегодня (Azure, Alibaba, Oracle, AWS IPv6; остальные лежат в link-local); новые вне `169.254/16` добавляются вручную.
- **Окно согласия** показывает «хост из настройки hubs» и не говорит, что в поле может быть несколько хостов (`describePermissions`, `core/src/permissions.ts`); слова не менялись, чтобы не трогать тексты окна без решения.
- **Подсказка вызывающему.** Плагин видит слитую настройку (воркспейс перекрывает пользователя) и может пойти на хаб из файла воркспейса; ядро откажет, но сообщение плагина об этом - решение продуктового плагина.
- **OAuth-вход в трекер и перенос трекеров Cyborg** не входят в задачу.
