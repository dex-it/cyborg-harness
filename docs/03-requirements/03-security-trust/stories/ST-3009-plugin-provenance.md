# ST-3009 Происхождение плагина: подпись, проверка перед запуском, откат и отзыв

Как человек, у которого на диске лежат плагины, я хочу, чтобы ядро запускало только тот код, который подписал издатель, которому я доверяю, и не принимало ни подмену файла, ни возврат на старую версию с дырой, чтобы подмена пакета процессом того же пользователя не превращалась в исполнение чужого кода.

Нормы: FR-CH-3027, FR-CH-3028, FR-CH-3029, FR-CH-3030. SRS - [srs.md](../srs.md). Решение - [ADR-CH-0017](../../../04-architecture/adr/ADR-CH-0017-plugin-provenance.md).

## Критерии приёмки

1. [FR-CH-3027]
   - Дано собранный каталог плагина, подписанный `cyborg-plugin sign`, и открытый ключ издателя
   - Когда `cyborg-plugin verify` проверяет его и архив из него; затем изменён один байт файла, добавлен лишний файл, взят чужой ключ, срок подписи истёк
   - Тогда цельный пакет принят, а каждое из четырёх изменений даёт отказ с названным файлом или причиной словами и кодом возврата 1; подпись другого ключа под идентификатором доверенного отвергнута, правка поля записи ломает подпись
2. [FR-CH-3027]
   - Дано подписанный каталог плагина
   - Когда `cyborg-plugin pack` упаковывает его дважды (второй раз после смены времени файла) и после правки файла
   - Тогда оба архива совпадают байт в байт и содержат `integrity.json`; архив распаковывается настоящим tar и проходит `verify`; после правки файла `pack` отказывает «подпись устарела» и называет файл
3. [FR-CH-3028]
   - Дано подписанный плагин, проверка которого прошла, и файл на диске, подменённый сразу после проверки
   - Когда хост (процесс Node, общий процесс, рантайм Electron) загружает точку входа
   - Тогда исполняется проверенный код, а не подмена; файл, которого нет среди проверенных, из каталога плагина не загружается; контрольный опыт без проверенных байтов исполняет подмену
4. [FR-CH-3028]
   - Дано пакет с изменённым файлом, пакет без подписи, неподписанный ключом из `trust.json`, пакет с версией ниже принятой, пакет с отозванным ключом, повреждённый `trust.json`
   - Когда ядро в режиме «отказывать» запускает плагин
   - Тогда плагин не запущен, в журнале запись `integrity-failed` с кодом, режимом и ключом, в окне «Плагины Cyborg» состояние «остановлен» и причина словами с кнопкой «Включить снова»; список отзыва, подписанный ключом поставки, применяется, чужой подписью - нет, устаревший список предупреждает, а отзыв сохраняет
5. [FR-CH-3028]
   - Дано те же нарушения в режиме «предупреждать» и поставка в режиме по умолчанию
   - Когда ядро запускает плагины
   - Тогда запись `integrity-failed` с режимом `warn` есть, плагин запущен как раньше; без настройки `trust` пакеты не проверяются; стенд включает проверку только флагами командной строки
6. [FR-CH-3029]
   - Дано `delivery.json`, подписанный ключом выпуска, неподписанный, подписанный чужим ключом, с истёкшим сроком и с правленным списком
   - Когда приложение стартует с ключом выпуска
   - Тогда подписанная поставка без записей; в остальных случаях запись журнала `delivery-failed` и строка в `problems`, в режиме «предупреждать» плагины запущены, в режиме «отказывать» плагин с несошедшимся файлом остановлен; `verifyDelivery` с ключами называет причину
7. [FR-CH-3030]
   - Дано плагин с зависимостями npm (в том числе scoped и вложенной)
   - Когда `cyborg-plugin build` или `delivery` собирает бандл главной части
   - Тогда в выводе и в отчёте перечислены пакеты с версиями и вкладом в байтах; без зависимостей сказано, что их нет
8. [FR-CH-3030]
   - Дано workflow выпуска и `scripts/release.ts`
   - Когда выпуск идёт по тегу
   - Тогда настоящая публикация идёт с `--provenance`, сухой прогон без него, `id-token: write` только у задания `publish`, задание `consumer-check` после него ставит пакеты и вызывает `npm audit signatures` без токена; самой публикации в репозитории не было (ручная часть - в SRS, «Ещё нет»)
