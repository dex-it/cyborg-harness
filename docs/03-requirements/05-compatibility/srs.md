# SRS фичи 05 - совместимость, версии и данные

## 1. SRS overview

Как обновление ядра и плагина не ломает соседей и не теряет данные: проверка `engines.cyborg` до запуска кода, версии API и контрактов, устаревание членов контракта, разделы `config` и `state` с миграциями и их сохранность, снимок публичного API. Закрывает BR-CH-002, BR-CH-008. Сценарии - [пользователь после обновления](../../02-use-cases/compatibility/UC-COMPATIBILITY-5001-user-after-upgrade.md), [плагин переживает обновление ядра](../../02-use-cases/compatibility/UC-COMPATIBILITY-5002-plugin-survives-core-upgrade.md). Устройство - [SAD](../../04-architecture/design/sad.md), 3.3 и 3.10; правила контрактов - `contracts/README.md`. Метод проверки называет тест ядра (`core/test`), тест playground (`playground/test`, `playground/src/main/*.test.ts`) или дымовой тест окна (`playground/scripts/smoke.mjs`, `npm run smoke`). Что не сделано - помечено «Ещё нет» или «Отложено», остаток - [дорожная карта](../../06-plans/roadmap.md). Раскладка норм по фичам - [03-requirements](../README.md).

Что лежит в соседних фичах. Воркспейс, замок, «Недавние», битый файл целиком, второй запуск - FR-CH-1014; граф и каскад отказа - FR-CH-1004; правка файла руками и угроза У-41 - FR-CH-1021; журнал и окно «Плагины Cyborg» - FR-CH-1010; выгрузка диагностики - NFR-CH-1005; восстановление документов и сессий (шаги 6-7 сценария «после обновления») - FR-CH-2005, FR-CH-2009; стирание секретов и `granted` при удалении плагина - FR-CH-2014 и фича 03. Здесь они берутся ссылкой на ID.

## 2. Требования

### FR-CH-1002 Проверка совместимости до запуска кода

- **Требование:** до запуска кода `engines.cyborg` плагина сверяется с версией API плагинов (`ctx` и элементы ядра). Несовместимый плагин не загружается: отказ графа с причиной «нужен API Cyborg <диапазон>, есть <версия>». Диапазон, нижняя граница которого выше версии API ядра (`^1.5` на ядре 1.3), отклоняется так же, как диапазон другой мажорной версии. Отказ каскадирует на тех, кто требует плагин через `requires`; потребитель через `optional` остаётся.
- **traced from:** BR-CH-002, BR-CH-006, BR-CH-008; `UC-COMPATIBILITY-5001`, шаг 2, расширение 2а; `UC-COMPATIBILITY-5002`, шаг 3, расширения 3а, 3б.
- **источник:** [SAD, 3.3](../../04-architecture/design/sad.md#33-версии-и-миграции); `core/src/graph.ts`, `core/src/semver.ts`.
- **verification:** испытание - `core/test/graph.test.ts` («отказ по engines каскадирует на зависимых, optional переживает»), `core/test/semver-manifest.test.ts` («диапазоны: каретка, тильда, префикс и звезда» - `^1.4` не принимает 1.3.9; «манифест под другой API…» - `^1.3` на 1.2.0).
- **класс:** Functions.

### FR-CH-1012 Версии API плагинов и контрактов

- **Требование:** API плагинов (`ctx` и элементы ядра) и контракты версионируются семантически. Элемент ядра не удаляется и не меняет атрибуты в пределах мажорной версии. Минорная версия контракта добавляет только необязательное; мажорная - новый тип в карте `Contracts`. Поставщик может давать две мажорные версии контракта сразу, каждый потребитель получает ту, что просил. Мажорная версия в `get` и `all` должна лежать в диапазоне манифеста потребителя, иначе `NotDeclared`. Член с `@deprecated` живёт минимум до следующей мажорной версии (пометка - в манифесте поставщика, `provides.<контракт>.deprecated`); запись его вызовов - FR-CH-5005.
- **traced from:** BR-CH-001, BR-CH-002, BR-CH-008; `UC-COMPATIBILITY-5002`, шаг 4, расширение 4г.
- **источник:** [SAD, 3.3](../../04-architecture/design/sad.md#33-версии-и-миграции); `contracts/README.md`.
- **verification:** испытание - `core/test/graph.test.ts` («поставщик с двумя мажорными версиями обслуживает старого и нового потребителя», «несовместимая мажорная версия поставщика - как отсутствие»), `core/test/registry.test.ts` («потребитель получает свою мажорную версию…», «мажорная версия в get и all должна лежать в диапазоне манифеста»), `core/test/contracts-types.ts` (`npm run typecheck`). Стабильность `ctx` и элементов ядра в пределах мажорной версии автоматически не проверяется - FR-CH-5003.
- **класс:** Functions.

### FR-CH-2008 Разделы `config` и `state`

- **Требование:** плагин видит только свой раздел `config` (`ctx.config`) и `state` (`ctx.state`); чужой раздел хост не пишет. `config` - слои пользователя и воркспейса, воркспейс перекрывает; `state` лежит в каталоге приложения по ключу воркспейса. Манифест объявляет версию и схему раздела. Ядро проверяет раздел по схеме - подмножеству JSON Schema, где ключ вне подмножества - ошибка схемы, - до активации и при правке файла извне. Версия раздела ниже версии плагина - ядро до активации вызывает `migrate` и записывает итог (сбой `migrate` - FR-CH-5007); выше - плагин не активируется, данные не трогаются, причина в журнале; раздел не по схеме - отказ только этому плагину. Правка файла извне доходит до `ctx.config.onChange`; не прошедшая проверку оставляет прежнее значение. Значений секретов в `config` и `state` нет, только ссылка `$secret`. Документ воркспейса без поля `cyborg` переводит хук приложения `migrate` при открытии; ядро записывает итог один раз и оставляет копию `.v1.bak` (поля вне списка переноса - FR-CH-5009).
- **traced from:** BR-CH-002; `UC-COMPATIBILITY-5001`, шаги 4-5, расширения 1а, 4а, 5а.
- **источник:** [SAD, 3.3](../../04-architecture/design/sad.md#33-версии-и-миграции), [SAD, 3.10](../../04-architecture/design/sad.md#310-главный-конфиг-и-состояние); `core/src/config.ts`, `core/src/json-schema.ts`.
- **verification:** испытание - `core/test/config.test.ts`, `core/test/json-schema.test.ts`, `core/test/loader.test.ts` («откат версии плагина…», «миграция config идёт в хосте…», «схема раздела из манифеста…»), `core/test/workspace.test.ts` («перенос старого формата хуком приложения…», «правка файла извне доходит до ctx.config.onChange…»), `playground/src/main/legacy-workspace.test.ts` («перенос {projects, lastProjectId}…»), `core/test/trust.test.ts` («provide и section.write…»), `electron/test/plugins.test.ts` («схема раздела: файл из каталога плагина…»).
- **класс:** Functions.

- **Требование:** версия API плагинов определена в одном месте; ядро, приложение и проверка плагина вне репозитория берут её оттуда, второго литерала версии в исходниках нет.
- **traced from:** BR-CH-008; `UC-COMPATIBILITY-5002`, шаг 3.
- **источник:** задача T-03 (#51, PR #72); `core/src/api-version.ts` (`PLUGIN_API_VERSION`).
- **verification:** испытание - `core/test/api-version.test.ts` («мажор PLUGIN_API_VERSION равен мажору @cyborg-harness/contracts»); осмотр - литерал версии только в `core/src/api-version.ts`. Ещё нет: теста, который ищет второй литерал версии API в исходниках. Связь версии API с версиями пакетов - вопрос 5.
- **класс:** Maintainability.

- **класс:** Compatibility.

### FR-CH-5003 Снимок публичного API

- **Требование:** публичный API - `PluginContext`, `UiContext`, `PluginPermissions`, поля манифеста, теги `cy-*`, коды `CoreErrorCode`, карта `Contracts` - зафиксирован снимком в репозитории. Удаление члена, смена его атрибутов и новое обязательное поле в пределах мажорной версии роняют сборку; добавление необязательного члена проходит после дополнения снимка.
- **traced from:** BR-CH-008; `UC-COMPATIBILITY-5002`, расширение 4а.
- **источник:** задачи T-06 (#12), K-21 (#62: эталон снимка - API 1.0 на момент заморозки); [ADR-CH-0002, «Расхождения с текущим кодом»](../../04-architecture/adr/ADR-CH-0002-manifest-and-compatibility.md#расхождения-с-текущим-кодом), п. 3; MOE BR-CH-008.
- **verification:** частично - снимок деклараций пакета контрактов (P-01, PR #102): `contracts/api-snapshot.txt` и `npm run check:contracts` в CI, тесты `contracts/test/api.test.ts` («правка карты Contracts или PluginContext без новой версии даёт ошибку, с новой версией и снимком - нет»), `contracts/test/check-api.test.ts`. Проверка ловит любую правку деклараций без повышения версии пакета, но не различает удаление члена и добавление необязательного. Род изменения и поверхность вне пакета - `core/test/api-snapshot.test.ts` (T-06) и эталон `core/test/api-snapshot/<версия API>.txt`: члены `PluginContext`, `UiContext`, `PluginPermissions` и остальных типов `contracts/plugin.ts`, `view.ts`, `os.ts`, `elements.ts`, поля манифеста (`PluginManifest`, `TOP_LEVEL`), команды окна, теги `cy-*` и их атрибуты; удаление, переименование, смена типа и новый обязательный член у типа, который строит плагин, - ломающее (нужен новый мажор), добавление - минор; процедура - [README пакета контрактов](../../../contracts/README.md#снимок-api-плагина-t-06). Ещё нет: карты `Contracts` в роде изменения (её держит снимок пакета и ревью, ADR-CH-0002, п. 4); тест различает три линии по суффиксу пакета: `-dev` - красный до обновления эталона, мажор не требует; `-rc.N` (кандидат, K-21) - правка требует следующего кандидата; без суффикса - ломающее требует нового мажора. Эталон 1.0 принят K-21 2026-11-11 кандидатом `1.0.0-rc.1` (состав эталона - вопрос 6; в него вошли вклады в меню, свойства и события `cy-*`); согласованность версий API, пакета и `engines.cyborg` встроенных плагинов - `core/test/api-version.test.ts`. Ещё нет: финального `1.0.0` (У-42 открыта, PL-08 не слит).
- **класс:** Compatibility.

Пометку ядро берёт из манифеста поставщика, `provides.<контракт>.deprecated`. Автор видит запись в окне «Плагины Cyborg» (FR-CH-1010) и в выгруженной диагностике (NFR-CH-1005).

- **источник:** [SAD, 3.3](../../04-architecture/design/sad.md#33-версии-и-миграции), «Устаревание»; [ADR-CH-0002](../../04-architecture/adr/ADR-CH-0002-manifest-and-compatibility.md), п. 5; задача K-06 (#41, PR #107); D-00, строка 10 (решено 2026-11-08, вопрос 1); `core/src/call-check.ts`, `core/src/journal.ts`; MOE BR-CH-008: у каждого члена с `@deprecated` есть запись о вызывающих.
- **verification:** испытание - `core/test/via-contract.test.ts` («@deprecated: …»), `core/test/journal.test.ts` («журнал: вызовы устаревшего члена за окно - первая запись сразу, повторы одной записью с repeats…», «журнал: записей deprecated-call не больше предела…»), `core/test/status.test.ts` («вызов устаревшего члена: словами…»), `core/test/semver-manifest.test.ts` («манифест: deprecated у provides…»). ### FR-CH-5007 Сбой миграции раздела

### FR-CH-5008 Поставщик контракта не на просимой мажорной версии

- **Требование:** поставщик, не дающий мажорную версию контракта, которую просит потребитель, для этого потребителя - как отсутствие: потребитель через `requires` не загружается, причина в журнале называет контракт и диапазон; потребитель через `optional` работает без поставщика.

- **источник:** [SAD, 3.3](../../04-architecture/design/sad.md#33-версии-и-миграции), «Переход между мажорными версиями»; `core/src/graph.ts`. Граф и каскад - FR-CH-1004.
- **verification:** испытание - `core/test/graph.test.ts` («несовместимая мажорная версия поставщика - как отсутствие» - `requires`; «отказ по engines каскадирует на зависимых, optional переживает» - то же состояние `missing` для `optional`). Ещё нет: отдельного теста `optional` при чужой мажорной версии.
- **класс:** Functions.

### FR-CH-5010 Удаление плагина стирает его разделы

- **Требование:** удаление плагина стирает его раздел `state` в открытом воркспейсе; плагин с тем же `id`, появившийся после удаления, начинает `state` с `defaults`. Разделы `config` в слоях пользователя и воркспейса остаются: это файлы, которые правит человек, - ядро называет их в итоге удаления (`left`) и в журнале. Выключение плагина его разделы не стирает.
- **traced from:** BR-CH-002, BR-CH-005; угроза У-18.
- **источник:** [модель угроз, У-18](../../04-architecture/design/threat-model.md#52-плагин-против-плагина) (частично); задача K-10 (#47, PR #109); [SAD 3.7, «Удаление плагина»](../../04-architecture/design/sad.md#удаление-плагина), решения 1 и 2; `core/src/config.ts` (`SectionStore.remove`). Секреты и `granted` при удалении - FR-CH-2014 и фича 03.
- **verification:** испытание - `core/test/uninstall.test.ts` («uninstall: файлы, секреты, granted, память видов, документы и state плагина стёрты; config остаётся…», «uninstall: новый плагин с тем же id ничего не наследует…», «uninstall: активный плагин - отказ…»), `core/test/config.test.ts` (`SectionStore.remove`). Ещё нет: `state` в других воркспейсах - вопрос 8.
- **класс:** Security.

### NFR-CH-1006 Совместимость API

- **Требование:** ломающих изменений публичного API ядра и контрактов `@cyborg-harness/contracts` в минорных выпусках - 0. Плагин, собранный под API 1.x, загружается и проходит свои тесты на ядре 1.y при y не меньше x: плагинов прошлых минорных выпусков, не прошедших свои тесты на текущем ядре, - 0. Замер: CI на каждом выпуске 1.y против снимка (FR-CH-5003) и набора плагинов прошлого минорного выпуска (FR-CH-5004); неуспех - расхождение снимка без повышения мажорной версии либо упавший тест плагина. Версия API записана в одном месте (FR-CH-5001).
- **traced from:** BR-CH-008.
- **источник:** [SAD, 3.3](../../04-architecture/design/sad.md#33-версии-и-миграции); FR-CH-1012; MOE BR-CH-008.
- **verification:** испытание - `core/test/semver-manifest.test.ts` (`engines.cyborg`), `core/test/graph.test.ts` (две мажорные версии поставщика). Снимок API плагина в CI - T-06 (FR-CH-5003). Ещё нет: плагин прошлого минорного выпуска на текущем ядре (FR-CH-5004).
- **класс:** Compatibility.

### NFR-CH-5001 Сохранность разделов

- **Требование:** разделов `config` и `state`, потерянных или перезаписанных без решения человека, - 0 при каждом исходе: миграция раздела, откат версии плагина, сбой `migrate`, отказ по схеме, правка файла извне, битый файл. Раздел плагина, которого исход не касается, после запуска такой же, как до него. Замер: содержимое файлов слоёв и `state` до запуска и после, один запуск плюс повторный; неуспех - раздел исчез или изменился, хотя не мигрировался (FR-CH-2008) и не записан самим плагином.

- **verification:** испытание - `core/test/loader.test.ts` («откат версии плагина: раздел config новее манифеста - … данные целы»), `core/test/workspace.test.ts` («битый файл пользователя не роняет открытие: … файл не перезаписан»), `core/test/config.test.ts` («хранилище: мигрированный слой записывается сразу, чужие разделы не трогаются»), `electron/test/plugins.test.ts` («старт: … раздел plugins не теряется»). Ещё нет: теста на сбой `migrate` (FR-CH-5007).

## 3. Открытые вопросы

Решения за владельца не принимаются; после каждого вопроса - предложение составителя.

1. **Откуда ядру знать об `@deprecated` при выполнении.** Пометка живёт в типах, ядро их не видит. Варианты: (а) аннотация в манифесте поставщика рядом с `guard`; (б) генерация из типов `@cyborg-harness/contracts`; (в) отдельная машинерия. Держат: D-00, строка 10 (аннотация прав на членах контракта), [SAD, раздел 8, вопрос 6](../../04-architecture/design/sad.md#8-открытые-вопросы), сценарий `UC-COMPATIBILITY-5002` (6а, вопрос 1). Решено 2026-11-08 (D-00, строка 10) и влито с K-06 (PR #107): (а) - `provides.<контракт>.deprecated: ["член"]` рядом с `guard`; типы пакета ядро не видит, расхождение пометки с `@deprecated` в типах ловит автор поставщика.
2. **Как пишутся повторные вызовы устаревшего члена.** Варианты: каждый вызов; одна запись на пару «член, вызывающий» со счётчиком и временем последнего; одна запись за запуск. Держит сценарий `UC-COMPATIBILITY-5002` (5а, вопрос 2). Решено с K-06 (PR #107): первая запись сразу, повторы за окно 5 с - одной записью с `repeats`, записей `deprecated-call` не больше 1000, отказы они не вытесняют ([SAD, 3.3](../../04-architecture/design/sad.md#33-версии-и-миграции)).
3. **Нижняя граница `engines.cyborg`.** BR-CH-008 обещает «не ниже x», руководство учит `^1`, и такой диапазон пускает плагин, собранный под 1.5, на ядро 1.3. Ядро нижнюю границу проверяет (FR-CH-1002); объявить её может только автор. Допустимый синтаксис ядра - `^1.5`; запись `>=1.5 <2` не разбирается (`isValidRange('>=1')` ложно). Держит сценарий `UC-COMPATIBILITY-5002` (3б, вопрос 3). Предложение: руководство и сборка автора (фича 07) ставят нижней границей минорную версию, под которую собран плагин (`^1.5`).
4. **Видит ли тест-кит автора устаревшие вызовы.** Держит сценарий `UC-COMPATIBILITY-5002` (7а, вопрос 4); норма лежит в фиче 07. Решено 2026-11-10 (принято по поручению владельца): тест-кит показывает те же записи, что окно. [FR-CH-7004](../07-author-kit/srs.md#fr-ch-7004-тест-кит) уже даёт автору ожидание записей журнала ядра, а `deprecated-call` пишется в тот же журнал (`core/src/call-check.ts`), поэтому отдельной машинерии не нужно. Критерий - ST-5003/6.
5. **Связь версии API с версиями пакетов.** Варианты: (а) версия API равна версии `@cyborg-harness/contracts`; (б) независимы, связь только в журнале изменений. Руководство ([версии](../../guide/features/versions.md)) говорит «связана», код этого не держит. Держат: T-03, P-01. Решено с P-01 (PR #102): мажор API плагина равен мажору пакета `@cyborg-harness/contracts` (`core/test/api-version.test.ts`), что повышает какую версию - [README пакета](../../../contracts/README.md#что-повышает-какую-версию).
6. **Состав эталона снимка 1.0 (K-21).** Эталон нельзя было принять, пока открыты строки D-00 1, 8 (меню K-08, PR #157; отмена K-09, PR #122) и 9. Решено 2026-11-11 (принято по поручению владельца, K-21): строки 1 и 8 подтверждены по принятым формам, по строке 9 в 1.0 поля правила `process` нет (оно добавится необязательным ключом, минор); строки 2 и 10 решены раньше. Варианты: заморозить после закрытия всех; заморозить сейчас и расширять только дополнением. Снимок деклараций пакета уже есть (P-01). Предложение: T-06 различает род изменения поверх этого снимка, запрет на удаление и смену атрибутов включает заморозка K-21. Принято по поручению владельца 2026-11-10 и сделано в T-06: состав эталона - все экспортируемые типы четырёх файлов `contracts/` (кроме карты `Contracts`), поля манифеста, команды окна, теги и атрибуты `cy-*`; пока у пакета контрактов суффикс `-dev`, тест просит обновить эталон, без суффикса (K-21) включается правило мажорной версии. Эталон 1.0 - файл `core/test/api-snapshot/1.0.0.txt` на момент заморозки.
7. **Из чего набор плагинов «прошлого минорного выпуска» (FR-CH-5004).** Варианты: встроенные плагины и их тесты на теге прошлого выпуска; плюс шаблон плагина (фича 07). Предложение: встроенные плагины на теге прошлого минорного выпуска.
8. **Область стирания при удалении плагина (FR-CH-5010).** Варианты: (а) только слой пользователя и открытый воркспейс; (б) ещё `state` всех воркспейсов каталога приложения; (в) ещё файлы `config` других воркспейсов. Держат: У-18, K-10 (без D-00). Решено с K-10 (PR #109) иначе, чем предлагалось: стирается только открытый воркспейс, а `config` остаётся и в слое пользователя - это файлы человека; другие воркспейсы ядро называет в `left`, их обход по «Недавним» - [вопрос 18 SAD](../../04-architecture/design/sad.md#8-открытые-вопросы). Открыто: стирать ли `state` других воркспейсов; предложение прежнее - (б), иначе плагин с тем же `id` в другом воркспейсе унаследует память.
9. **Копия повреждённого файла `<файл>.corrupt-<время>`.** Варианты: делать (как в Cyborg, FR-1026); не делать - файл не перезаписывается и так (FR-CH-1014). Держат: K-18 (в), [спорный пункт 17](../../04-architecture/design/sad2-disputed-points.md); приёмка K-18 - тест или явная запись «не делаем». Предложение: не делать, пока ядро не заменяет битый файл.
10. **Кто переносит ключи `localStorage` Cyborg в `state`.** Варианты: приложение один раз при первом запуске; ядро; вид плагина. Держит PL-06; SAD 3.10 допускает чужие поля только в переводе старого формата. Предложение: приложение, ядро ключей не знает. Решено 2026-11-11 в PL-06 (принято по поручению владельца): плагин приложения (`playground/plugins/legacy-prefs`), старое окно отдаёт ключи, вид забирает своё при открытии; ядро не менялось. Владельцу подтвердить.
