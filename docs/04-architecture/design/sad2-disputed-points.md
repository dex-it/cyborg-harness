## A. Расхождения с текстом автора

### 1. Кто держит pty

- **SAD2 (автор):** `node-pty` в главном процессе, ядро держит процесс и буфер ([3.6](sad.md#36-ресурсы-дольше-плагина-pty)).
- **Проверка:** в VS Code терминал живёт в отдельном процессе (`ptyHost`) с heartbeat и перезапуском; `node-pty` в `utilityProcess` загружается; путь «хост - `<iframe>`» не дороже пути через главный процесс (45 мкс на круг, около 1,9 ГБ/с). Зависание или падение нативного модуля в главном процессе замораживает окно и убивает все сессии.
- **Предложение:** pty-хост - отдельный `utilityProcess` ядра ([ADR-CH-0012](../adr/ADR-CH-0012-pty-host.md)). Цена: ещё один вид процесса и сторож за ним.
- **Что нужно:** согласие автора; прогон `claude` в pty-хосте (спайк, раздел 7 ресёрча).
- **Решение:** принято; сделано в K-01 (2026-11-08): pty-хост - `utilityProcess` ядра со сторожем, вывод к виду по `MessagePort` ([SAD, 3.6](sad.md#36-ресурсы-дольше-плагина-pty)).

### 2. Origin `<iframe>` плагина

- **SAD2 (автор):** `cyborg-plugin://<id>/` на каждый плагин, физическая изоляция DOM; общий origin для встроенных - запасной путь, если памяти много (SAD-8/11).
- **Проверка:** кадр со своим origin - отдельный процесс рендера, 17 МБ против 3 МБ при общем origin; в базовой части 6-12 кадров, то есть 100-200 МБ разницы. Кадр с `sandbox` без `allow-same-origin` изолирует DOM по цене общего origin, но лишает хранилищ origin и опознания вида по origin: Monaco и xterm под ним не работают ([пилот PL-05](../../05-verification/spike-monaco-xterm.md)).
- **Предложение:** встроенные плагины делят `cyborg-plugin://builtin/`, сторонние получают свой origin ([ADR-CH-0007](../adr/ADR-CH-0007-plugin-ui.md)). Изоляция DOM между своими плагинами - статическая проверка, не граница.
- **Возражение, которое стоит услышать:** дисциплина «не трогать чужой DOM» без границы со временем размывается. Ответ: между встроенными плагинами одной команды граница безопасности не нужна, а ошибки ловит статическая проверка.
- **Решение:** иначе - origin по группе рендера `cyborg-plugin://<группа>/`. Группы составляются по смыслу: автор плагина рекомендует группу (`ui.group`), владелец переопределяет (`plugins.uiGroups`). Сторонний в группе всегда один, из любого слоя (на этапе 1 общую группу ему не дают, FR-CH-3020), и его origin - `cyborg-plugin://solo_<id>`; владелец задаёт группы в файле пользователя. Внутри группы - статическая проверка, граница доверия моста - группа ([SAD2, 3.8](sad.md#38-изоляция-рендера)). Сделано в K-04 (2026-11-09): плагин внутри группы мост берёт из пути адреса кадра `cyborg-plugin://<группа>/<плагин>/`; память десяти видов - [замер](../../05-verification/spike-render-groups.md); вариант `sandbox` без `allow-same-origin` не годится ([PL-05](../../05-verification/spike-monaco-xterm.md)). K-05 (2026-11-10, принято по поручению владельца 2026-11-10): CSP вида закрыта, инлайн-стили по `ui.inlineStyles`, но CSP по плагину внутри группы границей не является - вид читает документ соседа через `parent.frames`, граница доверия остаётся группой ([SAD, 3.8](sad.md#38-изоляция-рендера), задача #150).

### 3. Что даёт второй этап изоляции

- **SAD2 (автор):** `Compartment` (`ses`) в хостах даёт гарантию «ничего сверх объявленного»; запасной путь - процесс на плагин без `Compartment`; флаг `--permission` в `utilityProcess` как второй слой - вопрос.
- **Проверка:** `utilityProcess` флаг принимает и **не применяет**; процесс Electron как Node его применяет, но сеть и окружение не закрыты. `ses` работает и дёшев (+3,5 МБ, около 0,1 мкс на вызов), но общая виртуальная машина пробивается: Figma ушла с такой песочницы после нескольких побегов; сканер `ses` отвергает часть бандлов (zod, marked).
- **Предложение:** граница - процесс на плагин с `--permission` (12 МБ на плагин), `Compartment` вторым слоем, сеть и окружение держит шлюз ([ADR-CH-0003](../adr/ADR-CH-0003-trust-and-isolation.md)).
- **Что нужно:** согласие автора; решение о поводе для второго этапа (пункт 14).
- **Решение:** принято после перепроверки 2026-11-05 (Linux, Electron 45.0.0, Node 24.22): `utilityProcess` флаг не применяет, режим Electron как Node применяет (`fs`, `child_process`, `worker_threads` закрыты), сеть и окружение открыты. Повод для второго этапа - по-прежнему пункт 14.

### 4. Модель процессов и окон

- **SAD2 (автор):** «Один воркспейс - одно окно; второй экземпляр приложения передаёт путь первому и завершается».
- **Проверка:** в коде нет `requestSingleInstanceLock`; сегодня отдельный процесс на воркспейс с общим `userData`, повторное открытие отказывает (FR-1029, FR-1033). Фраза допускает два прочтения: «одно приложение, одно окно» (тогда второй воркспейс не открыть) или «процесс на воркспейс» (тогда передавать путь некому); с кодом и FR-1029 согласуется только второе.
- **Предложение:** оставить процесс на воркспейс (паритет); передача фокуса окну владельца - улучшение после паритета.
- **Если автор имел в виду одно приложение с несколькими окнами:** это отдельное решение, оно меняет FR-1029, FR-1033, модель `userData` и замок; в [ресёрче-2](../../research/sad2-validation.md#6-решения-и-открытые-вопросы-sad2-после-проверки) это новый вопрос 13, в раздел 8 SAD он не перенесён: решение записано в SAD, 3.1.
- **Решение (K-20, #61, D-00 строка 5; принято по поручению владельца 2026-11-09 по «Предложению» строки):** процесс на воркспейс с общим `userData`, паритет FR-1029 Cyborg (вариант Б). Один конфиг - один экземпляр, строго (замок `<файл>.lock`): второй запуск на тот же файл просит владельца поднять окно через сокет и завершается; разные воркспейсы - разные процессы, «Открыть в новом окне» - ещё один процесс. `requestSingleInstanceLock` для этого не годится (его замок общий для `userData`), поэтому заменён контролем по воркспейсу; общие файлы `userData` пишутся под замками, проверка P9 - smoke с двумя процессами ([SAD, 3.1](sad.md#31-воркспейс-как-главная-сессия)). FR-1029 сохраняется; FR-1033 меняется только в улучшении: повторное открытие того же воркспейса поднимает окно владельца, а не отказывает (ai-cyborg не открывался, формулировку уточнить в плане миграции P-11). Обратимо: вернуть `singleInstance` адаптера вместо `workspaceInstance`.

### 5. Перехват системных клавиш

- **SAD2 (автор):** `before-input-event` в главном процессе, одинаково из любого `<iframe>` ([3.9](sad.md#39-системные-клавиши-и-события)).
- **Проверка:** с фокусом внутри `<iframe>` синтетические нажатия до `before-input-event` не доходят, ни подтвердить, ни опровергнуть обещание без настоящей клавиатуры нельзя. Хоткеи кнопок задаёт пользователь и они условные (не в поле ввода, не при диалоге, только видимая сессия) - статические `keybindings` манифеста их не выражают. `Cmd/Ctrl+Shift+N` и `Cmd/Ctrl+0` сегодня живут только в слушателе окна.
- **Предложение:** сочетания остаются акселераторами меню (работают на уровне ОС до страницы), `before-input-event` - дополнение после спайка; динамическая регистрация `ctx.keys.register` с условием `when`.
- **Что нужно:** спайк с живой клавиатурой.
- **Итог:** на Linux настоящим вводом X11 подтверждено, что `before-input-event` гасит сочетание и при фокусе во фрейме ([спайк](../../05-verification/spike-iframe-ui.md)). macOS не проверена; до проверки сочетания остаются и акселераторами меню ([SAD2, 3.9](sad.md#39-системные-клавиши-и-события)).

### 6. Что показывать после `attach`: хвост или снимок

- **SAD2 (автор):** сырой кольцевой буфер, после `attach` `resize`, TUI перерисуется по `SIGWINCH`.
- **Проверка:** VS Code восстанавливает экран снимком (headless-xterm) вместе с размерами; в обсуждении для Zed предложено то же. Для `claude` это не проверялось: может оказаться, что хвост с `resize` достаточен.
- **Предложение:** начать с решения автора (хвост + `resize`), снимок оставить как запасной вариант, если спайк покажет сломанную перерисовку.
- **Итог:** [спайк](../../05-verification/spike-pty-restore.md) показал сломанное восстановление. Пока сессия короче хвоста, хвост с `resize` совпадает с эталоном. Когда длиннее, из хвоста выпадают включения альтернативного экрана, bracketed paste, мыши и фокуса, а `claude` по `SIGWINCH` их не повторяет. Снимок совпал во всех сценариях и стоит 1,7 МБ на сессию. Решено (D-00, строка 11, 2026-11-08): хвост + `resize`, как предлагал автор; снимок - запасной вариант, отдельной задачей, если длинные сессии `claude` покажут сломанный экран ([SAD, 3.6](sad.md#36-ресурсы-дольше-плагина-pty); вопрос 14 закрыт). Предел хвоста записан в SAD и в ADR-CH-0012.

## B. Чего в SAD2 нет

### 7. Восстановление сессий и non-goal корпуса

- **SAD2 (автор):** `sessions` хранит `{agent, resumeId, cwd, projectId, title, order}` и поднимает сессии через `resume` ([5.3](sad.md#53-восстановление-сессий)).
- **Корпус:** автоматическое восстановление сессий - non-goal (`docs/01-product/brd.md`); FR-1015 и FR-2014 запрещают хранить привязку задачи или MR к сессии на диске, это закреплено тестом `static-guards`.
- **Позиции:** (а) оставить non-goal, держать только живые pty при перезагрузке окна; (б) снять non-goal, восстанавливать вкладки и `resume`, привязку задачи теряем.
- **Предложение:** выполнить пункт (а) в первой версии (pty-хост даёт «живые сессии при перезагрузке окна»), восстановление после перезапуска приложения - отдельным решением владельца.
- **Решает:** владелец.
- **Снято 2026-11-06** при слиянии с master: документы перевода Cyborg (фича 03-migration, parity-plan) убраны, non-goal основного корпуса для харнесса не действует. Восстановление сессий - поведение `sessions` ([SAD, 5.3](sad.md#53-восстановление-сессий)), в playground сделан ручной подъём.

### 8. Владелец git

- **SAD2 (автор):** владелец не назван; в схеме «базовой части» есть `git-status` как поставщик отметок дерева.
- **Проверка:** шесть каналов `git:*`, потребители `files`, `viewer` (diff через `headContent`), `search`, `trackers`, `command-buttons` (подстановка `{branch}`); у `viewer` нет права на процессы; `git:switch` отказывает, если репозиторий занят сессией.
- **Варианты:** (а) плагин `git` с контрактом `cyborg.git`; (б) git в ядре; (в) каждый плагин вызывает git сам, каждому нужно право `process`.
- **Предложение:** (а). Нужны ещё `gitRemotes` (для `trackers`) и `gitFiles` (для `fs:files` и `search`), зависимость `git` - `sessions` для `switch` решается через опциональный контракт.
- **Решение:** (а) по правилу 11: общий ресурс держит плагин-владелец с контрактом. `cyborg.git` дополнен `remotes` и `files`; отметки дерева поставляет `git`. Отказ `switch` при занятом репозитории - открыт до P1.

### 9. Граница `trackers`

- **SAD2 (автор):** плагин `trackers`, в SAD старого состава - шесть плагинов.
- **Проверка:** общий `TrackersService`, составная карточка «Статус», одна секция `project-settings`, одна привязка задачи к сессии.
- **Предложение:** один плагин `trackers` с тремя видами (Задачи, MR/PR, Статус); разбивать, когда появится второй независимый трекер.
- **Решение:** принято - следствие правила 11 (общий ресурс трекеров держит один плагин-владелец).

### 10. Вклады плагинов в меню, условные сочетания

- **SAD2 (автор):** меню - забота ядра, вкладов плагинов нет.
- **Проверка:** `project:selected` включает пункты «Свойства проекта», «Поиск», «Расширения»; `notifications:toggle` держит галочку; FR-5006 и FR-10007 запрещают убирать пункты.
- **Варианты:** (а) `contributes.menus` в манифесте с `enabled`/`checked` из контракта владельца; (б) меню статично в ядре, плагины только исполняют команды (теряем состояния пунктов).
- **Предложение:** (а). Вместе с динамическими сочетаниями закрывает известный дефект D-27.
- **Решение:** (а): меню - вид ядра, `contributes.menus` - вклад в него по правилу 11; сочетания - `ctx.keys.register` с условием `when`. Сигнатуры - в P1 (SAD-8/15).
- **Итог по сочетаниям (2026-11-08, K-07):** форма `ctx.keys.register({ key, command, args?, when? })`, `when` - закрытый список флагов `repeat`, `dialog`, `visible`, `input`; единый реестр с акселераторами меню и командами окна закрывает D-27 на стороне ядра ([SAD, 3.9](sad.md#39-системные-клавиши-и-события)). Меню (`contributes.menus`) - K-08 (ниже).
- **Итог по меню (2026-11-10, K-08; принято по поручению владельца):** форма пункта `{ id, menu, title, command, order?, accelerator?, enabled?, checked? }`, `menu` из закрытого списка `workspace`, `view`, `tools`, `window`, источник `enabled`/`checked` - `{ contract, major, member }` булева члена контракта, который плагин получает или отдаёт; пункт неработающего плагина остаётся в снимке недоступным; акселераторы идут в единый реестр сочетаний. Предложение таблицы D-00 («выгруженный владелец - пункт недоступен, а не пропадает») принято как есть. Подробности - [SAD, 3.9](sad.md#вклады-в-меню-окна); владельцу подтвердить до заморозки API (K-21).
- **Отмена запросов (часть вопроса 15):** реализовано 2026-11-08 (D-00, строка 8, задача K-09), форма на подтверждении владельца до заморозки API (T-06): `AbortSignal` последним аргументом вызова, сообщение `cancel` в протоколе, код `Cancelled`; подробности - [SAD, 4, п. 12](sad.md#4-взаимодействие-плагинов).

### 11. Промпты, `prompts.json` и цикл `command-buttons` - `trackers`

- **SAD2 (автор):** `prompts.json` у `command-buttons` (SAD2, раздел 5.5; в SAD не перенесён).
- **Проверка:** все пять шаблонов (`mr.review`, `mr.rework`, `mr.ci`, `task.start`, `jira.start`) относятся к стартам из трекеров, а подстановки `{pr}`, `{task}` кнопок берутся из `trackers`. Граф с циклом не загрузится ([FR-CH-1004](../../03-requirements/01-plugin-host/srs.md)).
- **Варианты:** (а) шаблоны старта лежат у `trackers`, у `command-buttons` только кнопки; (б) отдельный маленький плагин `prompts` с контрактом, которым пользуются оба.
- **Предложение:** (б); подстановки `{pr}` и `{task}` приходят из контекста сессии, который заполняет `trackers`. Форма контракта - в P1. Заодно решается владелец фрагмента изоляции сессии (FR-9001): сегодня его нет ни у одного плагина SAD2.
- **Решение:** иначе - (а), отдельного плагина `prompts` нет. Шаблоны стартов у `trackers`; `{task}` и `{pr}` `command-buttons` читает из меток сессии (пункт 13), поэтому цикла нет. Контракт фрагментов промпта объявляет `sessions` как владелец вида, `trackers` - поставщик. Владелец инструкции изоляции (FR-9001) остаётся не назван.

### 12. Полоса кнопок под терминалом

- **SAD2 (автор):** слоты сняты, на панель инструментов переходят четыре кнопки; «чужой UI в свой не встраивается».
- **Проверка:** кнопки-команды (FR-12001, FR-12008) показываются под терминалом, а терминал живёт в `<iframe>` другого плагина.
- **Варианты:** (а) род области «подвал документа» в ядре; (б) кнопки на панели инструментов (меняется вид); (в) `command-buttons` отдаёт данные контрактом, `sessions` рисует полосу сам.
- **Предложение:** (в): совпадает с принципом «задача, а не виджет», вид не меняется.
- **Решение:** (в): полосу объявляет и рисует `sessions` как владелец вида, `command-buttons` - вкладчик.

### 13. Привязка задачи и MR к сессии

- **SAD2 (автор):** в `cyborg.sessions` такого члена нет.
- **Проверка:** сегодня поля сессии в окне (`s.task`, `s.mr`, `s.jira`); от них зависят заголовок, возврат к строке панели (FR-1031) и подстановки.
- **Предложение:** `cyborg.sessions` даёт незахранимый «мешок меток» сессии (в памяти), туда пишет `trackers`; на диск он не попадает, что соответствует FR-1015 и FR-2014.
- **Решение:** принято: метки сессии в `cyborg.sessions` с ключом по плагину, только в памяти; пишет `trackers`, читает `command-buttons`.

## C. Решения владельца

### 14. Сторонние плагины и второй агент

- **SAD2 (автор):** второй этап включается по поводу (автор вне команды или каталог плагинов).
- **Проверка:** без повода второй этап не окупается; первый этап с дисциплиной (асинхронные контракты, `structuredClone`, импорт только `@cyborg-harness/contracts`) сохраняет возможность перехода и стоит дёшево. Аналоги (Obsidian, Chrome) показывают, что подпись и источник важны не меньше окна согласия.
- **Предложение:** второй этап не планировать до повода; второй агент - P5 по запросу, как условие стабилизации `cyborg.agent`. Нужен ответ владельца: нужны ли сторонние плагины вообще и какой второй агент проверит контракт.
- **Решение исполнителя (сторонние плагины), ждёт подтверждения владельца:** 2026-11-08, D-00 строки 13 и 14 ([K-17](https://github.com/dex-it/cyborg-harness/issues/55)): сторонние плагины как продуктовая цель v1 не нужны, второй этап без повода не планируется; на этапе 1 каталог плагинов пользователя остаётся режимом разработки собственных плагинов - выключен по умолчанию, включается флагом запуска `--user-plugins`, загруженный оттуда плагин помечен в окне и записан в журнал ([SAD, 6.1](sad.md#61-этап-1-ядро-без-изоляции-доступа), вопрос 19). Какой второй агент проверит контракт `cyborg.agent` - открыто.

### 15. Трекеры: CLI или HTTP API

- **SAD2 (автор):** узкий класс плагинов (только `net`, свой токен) на примере `jira`.
- **Проверка:** сегодня все трекеры через CLI (`gh`, `glab`, `jira`), токенов в приложении нет; узкий класс возможен лишь после перехода на HTTP API - это новое требование и новая работа с секретами.
- **Предложение:** для паритета оставить CLI с правом `process`; HTTP-плагин (например, Jira) - отдельный плагин позже, первый кандидат в узкий класс.

### 16. Бюджеты и база замеров

- **SAD2 (автор):** бюджеты числами - открытый вопрос SAD-8/9.
- **Проверка:** базы старта и памяти нет (`scripts/measure.mjs` - файл Cyborg - замеряет только панель задач и MR); задержки моста измерены (около 50 мкс).
- **Предложение:** бюджет «вызов через шлюз не более 1 мс на p99», «вывод терминала не более 16 мс»; перед переносом расширить `measure` стартом и памятью; бюджет «не хуже 10%» (ADR-CH-0006, снят) без базы не проверяется.
- **Решение:** числа приняты владельцем 2026-11-07 - вызов через шлюз `ctx.os` не более 1 мс на p99 на вызов до 64 КиБ, событие `fs.watch` не позже 5 мс на p99 после окна склейки 50 мс, вывод терминала не более 16 мс; сверка - медиана трёх прогонов `npm run spike:gateway` ([замер шлюза](../../05-verification/spike-gateway.md)). Против чего мерить старт и память - открыто.

## D. Мелочи, которые надо закрыть до фиксации контрактов

### 17. Список

- **Область `path:open`.** `openablePath` пускает любой существующий неисполняемый путь (файлы из вывода сессии), а в SAD2 области `workspace`, `plugin-data`, `granted`. Предложение: явная область для `shell` с этим правилом, иначе теряются FR-10012 и FR-10013. **Решение:** область `any` права `shell` - любой существующий путь, кроме программ и скриптов; читать и писать она не даёт, защищённые пути и чужие каталоги закрыты. Решена вместе с цепочкой `fs.write` + `shell.openPath` (K-16): там, где плагин пишет сам, открывается только документ ([SAD, 3.7](sad.md#37-безопасность-данных-и-контроль-плагинов)). Проверка: `core/test/os.test.ts` («shell any…», ветка K-16).
- **`config:reveal`.** Открывает файл воркспейса целиком, а он по SAD2 защищённый путь. Предложение: команда ядра «показать файл воркспейса». **Решение:** команда ядра `cyborg.workspace.reveal` - среда показывает файл в файловом менеджере (`shell.showItemInFolder`). Зовёт её приложение или сочетание человека; плагину она отвечает `PermissionDenied`, файл для плагинов остаётся защищённым путём ([SAD, 3.10](sad.md#310-главный-конфиг-и-состояние)). Проверка: `core/test/os.test.ts` («команда ядра cyborg.workspace.reveal…»), `core/test/window.test.ts` («команды окна…», «манифест: id, в пространстве которого лежат команды окна, занят»). Остальные пользовательские JSON Cyborg переезжают в `plugin-data` своих плагинов, им команда не нужна (сверить в PL-06).
- **Копия повреждённого файла.** FR-1026 требует `<файл>.corrupt-<время>`; SAD2 говорит только об отказе раздела по схеме. Предложение: поведение сохраняется, владелец - ядро. **Решение:** принято. Ядро битый файл не перезаписывает, но человек правит его руками и может затереть исходник, поэтому при открытии рядом ложится `<файл>.corrupt-<время>` с исходными байтами; та же порча второй копии не даёт, имя копии - в жалобе ([SAD, 3.10](sad.md#310-главный-конфиг-и-состояние)). Проверка: `core/test/workspace.test.ts` («битый файл воркспейса: рядом копия .corrupt-<время>…»).
- **`experimental_` и реестр аудита.** SAD2 о них молчит, а ADR-CH-0002 и ADR-CH-0005 их отвергли (альтернатива «Префикс `experimental_`…»), реестр аудита D-10 снят ([журнал решений](../../03-requirements/01-plugin-host/decision-log.md)). **Решение:** не делаем. Свободу ломать нестабильное даёт мажорная версия контракта, переход - две мажорные версии у поставщика и `@deprecated` ([SAD, 3.3](sad.md#33-версии-и-миграции)); снятие префикса при стабилизации само ломало бы потребителей. Код префикса не использует.
- **Пороги сторожа.** Стартовые значения (5 с, 15 с, 3 перезапуска за 5 минут, 3 зависания) без прецедента в изученных системах; проверяются тестом до каркаса.
