# ADR-CH-0018 Процесс Node для сторонних плагинов, фьюзы сборки и защищённая конфигурация агента

> Решения составителя по задаче этапа В1 ([#248](https://github.com/dex-it/cyborg-harness/issues/248), TR-20, TR-31, TR-25, TR-07 из [плана исследования доверия](../../research/trust-and-isolation/06-work-plan.md)); принято по поручению владельца 2026-11-13 по рекомендациям [раздела 7](../../research/trust-and-isolation/07-open-questions.md) (вопросы 2 и 7) и результатам [спайка](../../05-verification/spike-node-host.md). Дополняет [ADR-CH-0003](ADR-CH-0003-trust-and-isolation.md); ADR-CH-0017 (происхождение плагинов, этап Б) на него не опирается.

## Decision Drivers

- В `utilityProcess` запреты Node (`--permission`) принимаются, но не действуют ([опыт Б](../../research/trust-and-isolation/08-sources-and-measurements.md)); сторонний плагин должен жить в процессе Node, где они действуют.
- Фьюз `RunAsNode` даёт любому процессу пользователя запустить подписанный бинарник приложения как Node с личностью приложения (ключ `safeStorage` в Keychain, права TCC): это обход защиты секретов.
- Запуск процесса Node должен укладываться в бюджеты шлюза (1 мс на p99 до 64 КиБ, NFR-CH-1001) и не ломать протокол ядра: структурное клонирование, пинг сторожа.
- Ядро ничего не знает об агенте, но шлюз должен уметь закрывать файлы по имени; что именно закрывать, решает адаптер или приложение (У-46: запись в конфигурацию агента - команда с правами пользователя мимо `process`).

## Decision

1. **Конфигурация агента закрыта для плагинов шлюзом `ctx.os` (TR-25, вариант (а) вопроса 15 SRS).** Запись в `CLAUDE.md`, `CLAUDE.local.md`, `.claude/settings*.json`, `.mcp.json`, `~/.claude.json` и в `.claude/{hooks,commands,agents,skills,output-styles}` - `PermissionDenied` и запись `denied` при любом праве; чтение закрыто для файлов с ключами и переменными окружения (настройки, `.mcp.json`, `~/.claude.json`), текст `CLAUDE.md` читать можно. Проверяются и имя, которым назван путь (ссылка `CLAUDE.md` на обычный файл), и настоящий путь; имена без учёта регистра (macOS). Ядро ничего не знает об агенте (проверка чистоты ядра, ST-1009/1): оно исполняет общие правила `OsEnvironment.protectedFiles` (имя файла в любом месте дерева, `under: 'home'`, `tree`, `closed: 'write' | 'all'`, соседи `<имя>.*`), а перечень Claude Code - значение по умолчанию адаптера (`electron/src/agent-files.ts`, `electronOs`), которое приложение заменяет или снимает. Норма - FR-CH-3027, угроза У-46 закрыта. Альтернатива (б), слово «полный доступ через программу» на право `fs.write`, отвергнута: слова не мешают записи.
2. **`RunAsNode` в сборке приложения выключен** (TR-07), вместе с `EnableNodeOptionsEnvironmentVariable` и `EnableNodeCliInspectArguments`; `OnlyLoadAppFromAsar` и `EnableCookieEncryption` включены; `EnableEmbeddedAsarIntegrityValidation` включён на macOS и Windows. Чек-лист - `electron/README.md`, проверка - `npm run pack:delivery` (фьюзы читаются из бинарника упакованного приложения, поведение каждого проверено против исходного Electron как контроля).
3. **Хост стороннего плагина - процесс Node с `--permission` и пустым `env`, запускаемый `forkHosts` (TR-20).** `forkHosts` получает необязательные `execPath`, `execArgv`, `env`, `serialization` (по умолчанию всё прежнее). Бинарник - отдельный Node, не Electron в режиме Node: при выключенном `RunAsNode` `child_process.fork` бинарника Electron запускает полное приложение (`process.type === 'browser'`), а не Node. Отдельный бинарник подписывается своей личностью и не наследует доступ к ключу приложения.
4. **Канал отдельного Node - `json`, пока нет кодека типов; `advanced` с ним не работает.** V8 в Electron 45.2.3 - 15.6, в Node 24.x - 13.6: хост на отдельном Node выходит с кодом 1 на первом сообщении (V8 не читает сериализацию из более нового V8), и наоборот. Канал `json` работает, но теряет `Map`, `Set`, `Date`, `BigInt`, `Uint8Array`, `Error`, `RegExp`, а функцию в ответе не отвергает, а молча превращает в `{}`. TR-21 начинает с кодека типов поверх `json` (тегированные значения для тех же типов, что проверяет `core/test/fork-permission.test.ts`) и запрета функций на стороне записи; хост стороннего плагина на отдельном Node не запускается, пока этого нет. Запасной вариант разработки - бинарник Electron в режиме Node (`advanced` работает, `RunAsNode` нужен включённым): только для стенда, не для выпуска.
5. **Плагин исполняется из проверенных байтов, повторного открытия файла нет (TR-20, п. 4).** Хосту под `--permission` разрешено читать только свой вход; ядро читает пакет один раз, проверяет и отдаёт байты каналом; хост исполняет их через `module.registerHooks` (граф модулей из памяти, относительные импорты и `node:*` работают; адреса `file:` под каталогом плагина, как выбрал этап Б, или своя схема) или `data:` URL для одного файла. Под `--permission` хук должен быть **и `resolve`, и `load`**: одного `load` мало, обычный разбор адреса проверяет файл и падает с `ERR_ACCESS_DENIED`; хук этапа Б (`core/src/verified-sources.ts`) получит `resolve` в TR-21. Повторный `import(путь)` под `--permission` - `ERR_ACCESS_DENIED`. Оговорка: `registerHooks` в Node 24 - «активная разработка» (стабильность 1.1), canary на каждый релиз Node (план, 6.6, п. 2) обязателен.
6. **Плагин привязывается к кадру вида при создании документа (TR-31).** Идентификатор - `WebFrameMain.frameTreeNodeId` (фиксирован при создании кадра, не используется повторно); привязку ведёт `guardNavigation`. `history.pushState` на путь соседа личность вида не меняет (У-19, частично закрыта; граница доверия внутри группы рендера остаётся группой).

## Consequences

- Positive: запреты Node для стороннего плагина действуют и проверены на настоящих процессах; ключ приложения не открыт режимом Node; вид не подменяет личность адресом; конфигурация агента не пишется плагином.
- Negative: отдельный бинарник Node (около 122 МБ на macOS arm64 и 123 МБ на Linux arm64) в поставке со своей подписью и нотаризацией; кодек типов для канала `json` - работа TR-21 с ограничением совместимости (значения вне перечня кодека не пройдут границу); `registerHooks` пока нестабилен.
- Risks: `--permission` не закрывает сеть (до Node 26, см. TR-22); версия V8 Node и Electron может сойтись в будущем (тогда `advanced` вернётся без изменений протокола, проверка - `npm run spike:node-host`); привязка к кадру не защищает от чтения соседа по группе (по-прежнему граница доверия).

## Alternatives Considered

- **Оставить `RunAsNode` включённым и запускать сторонние хосты бинарником Electron.** Работает с `advanced` и не требует лишних 122 МБ, но отдаёт режим Node с личностью приложения любому процессу пользователя. Отвергнуто.
- **Канал `advanced` с отдельным Node и подбором версии Node под V8 Electron.** Не подберёшь: V8 Electron идёт от Chromium и всегда новее V8 стандартного Node. Отвергнуто.
- **Собственный канал поверх сокета со своим кадрированием.** Закрывает ту же проблему, но тащит транспорт и сторож в ядро; сначала кодек типов на `json`.
- **Загрузка плагина `vm.SourceTextModule`.** Работает, но требует флага `--experimental-vm-modules` и не умеет графа модулей без ручной связки. Запасной вариант.
