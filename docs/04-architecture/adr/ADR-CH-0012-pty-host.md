# ADR-CH-0012 pty держит ядро в отдельном pty-хосте; вывод к виду идёт мимо хоста плагина

> Принят 2026-11-08 (D-00, строка 21: принять до старта K-01); принято по поручению владельца 2026-11-09 (владелец делегировал решение по K-01). Записывает решение [SAD, 3.6](../design/sad.md#36-ресурсы-дольше-плагина-pty), проверенное [ресёрчем-2](../../research/sad2-validation.md). Редакция 2026-11-06: хосты плагинов и сторож, которые первая редакция этого ADR тоже описывала, записаны в [ADR-CH-0003](ADR-CH-0003-trust-and-isolation.md), пп. 2-4; здесь остался только pty.

## Decision Drivers

- Процесс агента должен пережить перезапуск плагина, хоста и окна.
- Зависание или падение нативного `node-pty` не должно замораживать окно.
- Ядро не знает, что в pty агент: для него это программа из права плагина ([ADR-CH-0004](ADR-CH-0004-agent-provider-contract.md)).

## Context

Ресурс ОС, который переживает владельца, по критерию компактности держит ядро: плагин не гарантирует, что процесс переживёт его перезапуск ([ADR-CH-0001](ADR-CH-0001-core-and-plugins.md), п. 2). В VS Code терминал живёт в отдельном `ptyHost` по той же причине, что и здесь: нативный модуль в главном процессе замораживает окно ([ресёрч-2, 4.1](../../research/sad2-validation.md#41-vs-code)). `node-pty` в `utilityProcess` загружается (проверено).

## Decision

1. **Плагин решает, что запустить, ядро держит процесс.** `ctx.os.pty.spawn` по праву `pty`; `persist` - pty переживает падение хоста и ждёт `attach` вернувшегося плагина; `list` и `attach` видят только pty своего плагина, чужой - `NotFound`. Проверка: `core/test/pty.test.ts` («pty.spawn: программа, окружение и cwd по праву…», «pty: чужие не видны и не трогаются…», «падение хоста: pty с persist живёт и копит вывод…»).
2. **Экран для `attach` держит pty-хост, и при живом владельце тоже, - кольцевым хвостом вывода и шагом размера.** Размер хвоста - настройка ядра (256 К символов), после `attach` pty-хост шлёт `resize` с шагом размера, и TUI перерисовывается (D-00, строка 11, 2026-11-08: «хвост + `resize`, снимок запасным»). Предел, который показал [спайк](../../05-verification/spike-pty-restore.md): когда сессия длиннее хвоста, из него выпадают включения режимов (альтернативный экран, bracketed paste, мышь, фокус), которые `claude` делает один раз. Снимок состояния терминала (headless-xterm в pty-хосте) совпал с эталоном во всех сценариях и остаётся запасным вариантом, отдельной задачей. Проверка: `core/test/pty.test.ts` («pty завершился без владельца: list показывает выход, attach отдаёт хвост…»), `core/test/stress-pty.test.ts` («кольцевой буфер…»).
3. **Выключение плагина с живыми pty спрашивает человека.** Оставленные pty ждут без срока, пока плагин выключен; падение хоста и неудачная активация плагина их не трогают. Ядро отдаёт их приложению списком (`kernel.keptPty()`, изменения - `onKeptPty`), и человек завершает любой (`kernel.endKeptPty`): процесс, который ждёт без срока, должен быть виден. Удаление плагина, закрытие воркспейса и выход из приложения процессы завершают. Проверка: `core/test/pty.test.ts` («выключение: preview называет живые pty; keepPty…», «оставленный: ждёт без срока, пока плагин выключен…»), `core/test/stress-pty.test.ts` («оставленный: release и detach его не трогают…»), дымовой тест («выключение спрашивает о pty…»).
4. **Держит pty не главный процесс, а pty-хост** - отдельный `utilityProcess` ядра, не плагин и не общий хост плагинов. Сторож ([ADR-CH-0003](ADR-CH-0003-trust-and-isolation.md), п. 4) следит и за ним; перезапуск pty-хоста теряет процессы pty, плагины получают это как завершение (`{ code: -1 }`). Права, владельцы, билеты `share()`, льготный срок и список оставленных остаются в главном процессе (`PtyTable`), процессы, хвост, склейка вывода и зрители - в pty-хосте (`PtyHost`). Проверка: `core/test/pty-host.test.ts` («pty-хост упал: владельцы получают onExit…», «pty-хост завис: сторож убивает его по порогу…», «сторож не поднимает pty-хост, который падает снова и снова…»), дымовой тест останавливает pty-хост через `SIGSTOP`.
5. **Вывод к виду идёт мимо хоста плагина.** Главная часть выдаёт своему виду одноразовый билет `pty.share()`, вид открывает его через `ctx.terminal.open`; поток идёт из pty-хоста во фрейм по `MessagePort` (около 1,9 ГБ/с, круг 45 мкс), главный процесс только раздаёт концы порта. Хост плагина может зависнуть - терминал работает. Ввод и размер принимаются только от фрейма, которому главный процесс отдал порт, и проверяются в pty-хосте (размер 1..1000, предел ввода). Проверка: `core/test/pty.test.ts` («share: билет одноразовый и только для своего UI…», «share: просроченный билет не открывается»), `core/test/pty-host.test.ts` («вид: размер и ввод проверяет pty-хост…»), `electron/test/view-terminals.test.ts` («терминалы вида: порт уходит фрейму и pty-хосту, данные через главный процесс не идут…»), `electron/test/terminal-ports.test.ts`, дымовой тест останавливает хост `echo` через `SIGSTOP` и печатает в его вид, потом гонит поток 4 МиБ ([замер](../../05-verification/spike-pty-stream.md)).
6. **Pty без владельца завершается по льготному времени, как бы ни был написан плагин.** После падения хоста срок идёт сразу; активация плагина начинает его заново для всех его pty без `attach`, оставленных человеком (п. 3) тоже. Плагин, который не взял процесс за срок - не вернулся, не сделал `attach` или забыл про него, - процесс теряет, журнал пишет `pty-expired`. Значение - настройка ядра, по умолчанию 60 с. Оставленный человеком ждёт без срока, только пока плагин выключен: выбор человека сильнее срока, но процесс без владельца не живёт дольше срока после возврата плагина. Проверка: `core/test/stress-pty.test.ts` («сирота: pty с persist без attach завершается по сроку…»), `core/test/pty.test.ts` («сирота: плагин вернулся после падения хоста, но не взял pty за срок…», «оставленный: … вернувшийся плагин без attach теряет его по сроку»).

## Consequences

- Positive: процессы агентов переживают перезапуск хоста, плагина и окна; зависание `node-pty` не трогает окно; путь вывода к виду не дороже пути через главный процесс.
- Negative: ещё один вид процесса ядра и протокол к нему; перезапуск pty-хоста теряет все процессы pty; хвост вместо снимка не возвращает режимы терминала в сессии длиннее хвоста ([спайк](../../05-verification/spike-pty-restore.md)).
- Risks: сессия `claude` длиннее хвоста может остаться без мыши и bracketed paste после `attach` (запасной вариант - снимок, отдельная задача); `node-pty` в `utilityProcess` проверен на macOS и Linux, на Windows - нет.

## Alternatives Considered

- **pty в главном процессе.** Pros: проще, без протокола. Cons: зависание нативного модуля замораживает окно; падение главного процесса теряет все сессии. Why rejected: прямой путь из pty-хоста к виду не медленнее.
- **pty в плагине `sessions` или агента.** Cons: перезапуск владельца убивает процесс. Why rejected: не проходит критерий компактности ([ADR-CH-0001](ADR-CH-0001-core-and-plugins.md), п. 2).
- **Вывод через хост плагина.** Cons: зависший хост останавливает терминал. Why rejected: билет и порт дают тот же контроль доступа без хоста на пути.
- **Снимок состояния терминала вместо хвоста.** Pros: совпал с эталоном во всех сценариях спайка, режимы не теряются. Cons: эмулятор на каждый pty (1,7 МБ, 16 мс CPU на мегабайт вывода) и npm-зависимость, которую пришлось бы вести через интерфейс бэкенда. Why not now: D-00, строка 11 принимает хвост + `resize` и оставляет снимок запасным; вводится отдельной задачей, если длинные сессии покажут сломанный экран.

## Расхождения с текущим кодом

- Пункт 2: снимка нет по решению D-00 (строка 11): `PtyHost` отдаёт кольцевой хвост (`Tail`) и делает шаг размера; снимок - запасной вариант отдельной задачей.
- Перезапуск pty-хоста теряет не только процессы, но и хвосты: `attach` потерянного pty отдаёт выход `{ code: -1 }` и пустой хвост.
- `pty` на Windows не проверялся: Windows вне первой версии (D-00, строка 7).
