# ADR-CH-0017 Происхождение плагинов: подпись пакета, хранилище доверия, откат и отзыв

> Решение составителя по задаче TR-10..TR-14 этапа Б исследования доверия ([#247](https://github.com/dex-it/cyborg-harness/issues/247), исследование [#243](https://github.com/dex-it/cyborg-harness/issues/243), [раздел 5.4](../../research/trust-and-isolation/05-decision.md#54-слой-происхождение-плагинов)); решения по вопросам 4, 5, 12 и 14 раздела 7 исследования приняты по поручению владельца 2026-11-13 по рекомендациям исследования. Ждёт приёмки владельцем. Закрывает находку 5 («пакет плагина не подписан, сверка поставки не отказывает») и угрозы У-39 (подмена кода установленного плагина) частично, У-42 мерой «перечень пакетов». Изоляцию процесса (этап В, TR-20 и далее) не затрагивает.

## Decision Drivers

- Ядро исполняет JS из каталога на диске, а проверка поставки (`delivery.json`) лежала рядом с файлами, не была подписана, шла один раз при старте и только сообщала: тот, кто мог переписать файлы, переписывал и список.
- Подмену того же пользователя предотвратить нельзя (тот же uid), но можно сделать её **необходимо подписанной**: у атакующего нет секретного ключа издателя, и он не может ни подменить файл, ни вернуть старую версию с известной дырой.
- Проверка бесполезна, если файл читается дважды: между проверкой и `import()` его подменяют (TOCTOU).
- Ядро без npm-зависимостей ([ADR-CH-0001](ADR-CH-0001-core-and-plugins.md)): подписи только на `node:crypto`.
- Подпись не должна «окирпичить» приложение: потерянный ключ или ошибка выпуска не вправе остановить встроенные плагины.

## Context

До решения: `delivery.json` - sha256 файлов встроенных плагинов, `verifyDelivery` при старте писал расхождение в лог и `problems`, плагины поднимались ([SAD 6.1](../design/sad.md#61-этап-1-ядро-без-изоляции-доступа), `electron/src/plugins.ts`); у каталога пользователя и у `pack` проверки не было совсем. Хост делал `import(entry)` по пути (`core/src/host-entry.ts`, `electron/src/host-entry.ts`). Корень доверия по [5.9 исследования](../../research/trust-and-isolation/05-decision.md#59-что-остаётся-незащищённым-и-почему) - приложение: подмену самого приложения и списка его ключей процессом пользователя подпись не закрывает.

## Decision

1. **Формат подписанного пакета (TR-10).** В корне пакета лежит `integrity.json`: `format`, `id`, `version`, `keyId`, `notAfter` (срок, ISO 8601 UTC), `files` (путь через `/` -> sha256 каждого файла пакета, кроме самого `integrity.json`) и `signature` (Ed25519, base64). Подпись стоит над канонической записью: метка области `cyborg-plugin-integrity/v1`, затем JSON с полями в фиксированном порядке и файлами по алфавиту. Разбор строгий: лишнее поле - ошибка, потому что подпись покрывает только известные. Ключи - `ed25519:<base64 32 байт>` (открытый) и `ed25519-secret:<base64 32 байт>` (закрытый), `keyId` - первые 128 бит sha256 открытого ключа. Только `node:crypto` (Ed25519, SHA-256, `timingSafeEqual` для сравнения хешей). Доверие не берётся из `manifest.json` плагина. Проверка: `core/test/integrity.test.ts`.
2. **Команды `cyborg-plugin keygen`, `sign`, `verify`, `revoke`.** `sign` ставит подпись на собранный каталог (после `build`, до `pack`); состав файлов тот же, что у `pack`. `verify` читает каталог или архив `.tgz` в память целиком (архив не распаковывается), и лишний файл, изменённый байт, чужой ключ и истёкший срок - отказ; он проверяет так же, как ядро. `pack` кладёт `integrity.json` в архив обычным файлом и отказывает, если подпись устарела после правки файла (без ключа он сверяет хеши и состав, не подпись); воспроизводимость архива (время 0, владелец 0, права 0644, порядок по алфавиту) прежняя. Закрытый ключ создаётся с правами 0600, существующие файлы не затираются. Проверка: `tools/cyborg-plugin/test/sign.test.ts`.
3. **Хранилище доверия `<userData>/trust.json` (TR-11).** Слой пользователя, не воркспейса ([ADR-CH-0015](ADR-CH-0015-workspace-trust.md), п. 6). Содержит: ключи издателей (`publishers`), наибольшую виденную версию по `id` (`versions`, только растёт), отозванные ключи и хеши (`revoked`) и состояние применённого списка отзыва. Файл пишется атомарно (временный файл рядом, 0600; каталог 0700), перед записью перечитывается, чтобы два окна одного `userData` не затирали правки друг друга. Повреждённый файл не заменяется пустым: хранилище закрывается на запись, проверка пакетов отказывает с причиной. Ключ издателя поставки в файле не хранится: он зашит в приложение (`TrustOptions.releaseKeys`), и им же принимаются пакеты каталога пользователя (запасной офлайн-ключ перечисляется там же вторым элементом). Проверка: `core/test/trust-store.test.ts`.
4. **Проверка перед запуском и исполнение проверенных байтов (TR-11).** Перед каждой активацией загрузчик (`activation.ts`, `LoadOptions.provenance`) зовёт проверку: читает каталог плагина **один раз** в память (`readPackageTree`, скрытые файлы тоже, ссылки не раскрываются и в подписанный пакет не входят), проверяет эти байты (ключ -> не отозван -> подпись -> срок -> совпадение `id` и версии с `manifest.json` -> версия не ниже виденной -> файлы: ссылки, изменённые, пропавшие, лишние -> отозванные хеши) и отдаёт хосту **те же байты** (`VerifiedPackage`, base64, чтобы они одинаково доехали по structuredClone и JSON). Манифест, который прочёл поиск плагинов, должен совпасть с подписанным `manifest.json`: иначе права ядра взяты из другого файла, чем проверенный. Поставка (встроенные) проверяется по подписанному `delivery.json` (п. 7), каталог пользователя - по `integrity.json` и ключам издателей. После успешной проверки версия запоминается. Отказ: запись журнала `integrity-failed` (`code`, `reason` словами, `mode`, `keyId`), в окне «Плагины Cyborg» - состояние «остановлен» с причиной словами и «Включить снова» (проверка повторится). Проверка: `core/test/provenance.test.ts`, `electron/test/provenance.test.ts`.
5. **Способ загрузки из проверенных байтов (TR-11, критерий 5).** Хост ставит хук загрузки модулей `module.registerHooks` (Node 24, в том же потоке): для адреса файла под каталогом плагина `load` возвращает проверенные байты вместо чтения с диска; адрес остаётся `file:`, поэтому `import.meta.url` и относительные импорты работают; файл под каталогом, которого нет среди проверенных, не загружается. Отвергнуто: `import()` из `data:` (ломает `import.meta.url` и относительные импорты бандла со вспомогательными модулями), копия во временный каталог (открыта процессу того же пользователя: подмена копии - то же окно гонки), `vm.SourceTextModule` (под флагом, не публичный). Замеры и ограничения: [provenance-loading.md](../../05-verification/provenance-loading.md); проверено на macOS (Node 24.20), на Linux (Node 24.22, Docker, ядро 7.2) и в рантайме Electron 45. Проверка: `core/test/provenance.test.ts` («подмена файла между проверкой и запуском…» на настоящем процессе с контролем: без проверенных байтов та же подмена исполняется), `playground/test/host-electron-verified.test.ts`.
6. **Откат и отзыв.** Версия ниже виденной - `rollback`, даже при верной подписи; сбросить её может только человек (`TrustStore.forgetVersion`). Отзыв: ключ издателя или хеш (файла либо выпуска пакета - sha256 канонической записи); список ведёт человек (`revokeKey`, `revokeHash`) либо приходит подписанным (`cyborg-plugin revoke` -> `userData/revocations.json`, применяется при каждом старте): подпись ключа поставки или издателя с правом `canRevoke`, номер `serial` растёт, у списка есть срок свежести (позже него он не принимается). Записи только добавляются; устаревший применённый список не снимает отзыв, но пишет предупреждение «получите свежий». Проверка: `core/test/trust-store.test.ts`, `electron/test/provenance.test.ts`.
7. **Подпись `delivery.json` (TR-12).** Поле `signature` (`keyId`, `notAfter`, `value`) в том же файле; `format` остаётся 1, старые читатели хеши читают как раньше. `cyborg-plugin delivery --sign-key <файл> [--days N | --expires дата]` ставит подпись ключом выпуска; `verifyDeliverySignature` и `verifyDelivery(…, { releaseKeys })` проверяют её, при старте приложение со `trust` сверяет подпись и файлы поставки. Расхождение пишется в журнал записью `delivery-failed` (строка на расхождение) и в `problems`; плагин поставки проверяется по подписанным хешам перед запуском так же, как пакет пользователя (п. 4). **Режим «предупреждать» - по умолчанию для поставки** (запись есть, плагины запущены), «отказывать» включается настройкой `TrustOptions.modes.bundled` отдельным решением после пилотов (вопрос 5 исследования); для каталога пользователя по умолчанию «отказывать». Режим стенда (`builtinMode: 'stand'`, исходники без сумм) поставку не проверяет. Выключатель человека - `modes: off` в настройках приложения: подпись не «окирпичивает» установку.
8. **Происхождение выпусков наших пакетов (TR-13).** Настоящая публикация (`release.yml`, задание `publish`, только по тегу и при `RELEASE_PUBLISH=true`) идёт как `npm publish --provenance`: задание получает единственное в файле право `id-token: write`; сухой прогон флага не получает. После публикации задание `consumer-check` ставит выпущенные пакеты в чистый каталог и выполняет `npm audit signatures` (подписи реестра и аттестации); оно идёт при `RELEASE_PACKAGES_PUBLIC=true`, потому что закрытый пакет без токена не установить. Выключатель `RELEASE_PROVENANCE=false` оставлен на случай, если npm не принимает аттестацию (документация npm не называет, поддерживается ли происхождение для пакета `access: restricted`). Sigstore проверкой в ядре **не берём**: нужны сторонние библиотеки.
9. **Перечень пакетов бандла (TR-14, У-42).** `cyborg-plugin build` и `delivery` печатают пакеты npm (имя, версия, байт вклада), код которых попал в `index.mjs` (по метафайлу сборщика), и возвращают их в отчёте (`BuildReport.packages`). Это перечень для ревью поставки и `npm audit --omit=dev` по lock-файлу (задание `audit` в CI уже есть), а не проверка содержимого.
10. **Публичный API.** Форма `ctx`, `ctx.os`, манифеста и контрактов не меняется: снимки `core/test/api-snapshot/1.0.0.txt` и `contracts/api-snapshot.txt` те же (проверено), кандидат `1.0.0-rc.N` не заводится. Добавлены: два вида записей журнала (`integrity-failed`, `delivery-failed`) в публичном типе `JournalEntry` пакета ядра (он вне снимка контрактов; прецедент - `third-party`, K-17), входы `@cyborg-harness/core/integrity`, `TrustStore`, `createProvenance`, `LoadOptions.provenance`, `StartOptions.trust` адаптера и команды инструмента автора. Приложение, которое различает виды записей журнала исчерпывающе (`switch`), обязано добавить две ветки: так сделаны `describeEntry`, `entryLevel`, `pluginStatuses`.

## Consequences

- Positive: подмена файла плагина, лишний файл, чужой ключ, истёкший срок, откат на подписанную старую версию и отозванный ключ дают отказ до исполнения кода; исполняется то, что проверено; встроенные плагины проверяются тем же механизмом по подписанному списку; отказ виден человеку словами; режим «предупреждать» страхует выпуск.
- Negative: каждая активация читает и хеширует весь каталог плагина (стенд: десятки КБ; пилот с Monaco - десятки МБ) и передаёт хосту код модулей (JS и JSON) base64-строкой (+33% размера, одна копия в памяти хоста на время жизни плагина); срок подписи заставляет перевыпускать пакеты (по умолчанию 365 дней); пакет, распакованный с лишним файлом (`.DS_Store` и т. п.), отвергается как «лишний файл»; хук `registerHooks` в Node 24 помечен «активная разработка» - canary на каждый релиз Electron и Node (тесты выше идут в CI на macOS и Linux).
- Risks: потерян или украден ключ выпуска (мера: запасной офлайн-ключ в `releaseKeys`, `revoke`, режим «предупреждать», выключатель); атакующий, подменивший приложение или список ключей, подпись обходит (корень доверия - приложение, вне охвата); подпись не говорит о безопасности содержимого подписанного плагина; на втором этапе (процесс на плагин, TR-21) способ загрузки в процесс Node под `--permission` надо проверить отдельно (вопрос TR-20).

## Alternatives Considered

- **Sigstore (Fulcio, Rekor) вместо своего формата.** Pros: нет долгоживущего ключа. Cons: проверка сертификатов и журнала Rekor требует сторонних библиотек, а ядро без зависимостей. Why rejected: [5.12 исследования](../../research/trust-and-isolation/05-decision.md#512-отвергнутые-альтернативы); для наших выпусков Sigstore используется через `npm --provenance` на стороне потребителя пакетов.
- **Подпись только манифеста плагина (`manifest.json`).** Cons: автор пишет в него что угодно, а подпись файлов кода не покрывает. Why rejected: доверие не берётся из манифеста плагина.
- **Копия проверенных байт во временный каталог ядра и `import` оттуда.** Cons: процесс того же пользователя подменяет и копию. Why rejected: окно гонки остаётся.
- **`data:`-URL для бандла из одного файла.** Cons: `import.meta.url` становится `data:`, относительные и динамические импорты не работают. Why rejected: см. п. 5.
- **Режим «отказывать» у поставки с первого дня.** Cons: ошибка выпуска или потерянный ключ останавливают приложение. Why rejected: риск «окирпичивания» ([6.7 исследования](../../research/trust-and-isolation/06-work-plan.md#67-риски-и-откат)).
- **Срок подписи не вводить.** Cons: украденная подпись действует вечно. Why rejected: исследование требует срока, а отзыв без срока свежести списка не отличить от устаревшего.

## Расхождения с текущим кодом

- Окно согласия, установка из выбранного источника и повторное согласие при расширении прав (FR-CH-3023, FR-CH-3024, TR-23) не сделаны: пакет проверяется, когда лежит в каталоге; кто и как его туда положил, ядро не решает.
- Стенд (`playground`) включает проверку только флагами `--release-key=`, `--delivery-signatures=`, `--plugin-signatures=` (без них прежнее поведение); в `DEFAULT_CONFIG` ключа выпуска нет, его создаёт и хранит владелец.
- Проверка `registerHooks` в процессе Node под `--permission` и в `utilityProcess` на Linux не выполнялась ([provenance-loading.md](../../05-verification/provenance-loading.md)).
- Происхождение выпусков (`--provenance`, `npm audit signatures`) в этом репозитории не запускалось: публикации не было, и без решения владельца о видимости пакетов её не будет.
