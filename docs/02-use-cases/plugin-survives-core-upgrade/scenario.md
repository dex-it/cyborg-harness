# Плагин переживает обновление ядра

- **Актор:** автор плагина; пользователь, обновляющий приложение. В расширениях участвует разработчик ядра.
- **Цель:** плагин, собранный под API 1.x, работает на любом ядре 1.y не ниже x без пересборки; устаревший член заметен до удаления; ломающее изменение не доходит до пользователя в минорном выпуске.
- **Предусловия:** плагин собран под API 1.x, его `engines.cyborg` принимает эту версию; поставщики контрактов, которые он берёт, на мажорных версиях, которые он просил.
- **Требования:** BR-CH-008 ([BRD](../../01-product/brd.md)). Нормы - [FR-CH-1012](../../03-requirements/05-compatibility/srs.md#fr-ch-1012-версии-api-плагинов-и-контрактов), [FR-CH-1002](../../03-requirements/05-compatibility/srs.md#fr-ch-1002-проверка-совместимости-до-запуска-кода), [NFR-CH-1006](../../03-requirements/05-compatibility/srs.md#nfr-ch-1006-совместимость-api). Устройство - SAD [3.3](../../04-architecture/design/sad.md#33-версии-и-миграции); план - [дорожная карта, раздел 6](../../06-plans/roadmap.md#6-совместимость-и-версии). Данные плагина (`config`, `state`) при обновлении - сценарий [пользователь после обновления](../user-after-upgrade/scenario.md); здесь только API.
- **Состояние:** проверка `engines`, две мажорные версии контракта у поставщика и одно место версии API (T-03) работают. Ещё нет: журнала вызовов `@deprecated` (K-06, ждёт решения владельца по D-00, строка 10), снимка API в CI (T-06), прогона плагина прошлого минорного выпуска на текущем ядре ([NFR-CH-1006](../../03-requirements/05-compatibility/srs.md#nfr-ch-1006-совместимость-api), «Ещё нет»).

## Основной ход

1. Автор выпускает плагин, собранный под API 1.x; в манифесте `engines.cyborg` принимает эту версию.
2. Пользователь обновляет приложение; в нём ядро 1.y, y не меньше x. Плагин не пересобирается.
3. Ядро до запуска кода сверяет `engines.cyborg` плагина с версией API плагинов; плагин проходит.
4. Ядро разрешает граф и активирует плагин. Члены `ctx`, элементы ядра и контракты в пределах мажорной версии не удалены и не сменили атрибуты, поэтому плагин работает, как до обновления.
5. Плагин вызывает член контракта, который поставщик пометил `@deprecated`. Вызов выполняется, как раньше.
6. Ядро пишет в журнал вызов устаревшего члена и называет вызывающий плагин.
7. Автор находит запись в журнале плагина в окне «Плагины Cyborg» или в выгруженной диагностике ([причина сбоя по трассе](../diagnose-failure-by-trace/scenario.md)) и видит, какие устаревшие члены плагин вызывает.
8. Автор заменяет вызов на преемника и выпускает новую версию плагина до следующей мажорной версии API.
9. Выходит ядро 2.0 без устаревшего члена. Пользователь обновил плагин под 2.0, ядро загружает его, и вызова удалённого члена в нём нет.

## Расширения

- **3а. Ядро сменило мажорную версию, а `engines.cyborg` плагина принимает только 1.** Плагин не загружается, код не выполнялся; в журнале и в «Плагины Cyborg» причина «нужен API Cyborg <диапазон>, есть <версия>». Потребители через `requires` не загружаются каскадом, через `optional` остаются. Остальные плагины работают. Автор выпускает версию под новую мажорную (шаги 8-9).
- **3б. Плагин собран под более новый минорный API, чем ядро: диапазон начинается с 1.5, ядро 1.3.** Тот же отказ с той же причиной. Диапазон шире (`^1`) такой отказ не даёт; что делает плагин, когда вызывает член, которого в старом ядре нет, норма не говорит (вопрос 3).
- **4а. Разработчик ядра удаляет член, меняет его атрибуты или добавляет обязательное поле в минорном выпуске.** Снимок API в CI расходится с зафиксированным, сборка падает. Изменение либо возвращается, либо выходит мажорной версией; новый член минорный выпуск добавляет, снимок дополняется. Выпуск с ломающим изменением не уходит.
- **4б. Изменение прошло снимок, но сменило поведение члена.** Плагин прошлого минорного выпуска проходит свои тесты на текущем ядре в CI; упавший тест даёт тот же исход, что в 4а.
- **4в. Ломающее изменение всё же дошло до пользователя.** Плагин падает в вызове; отказывает только он, окно и соседи работают, причина в журнале. Дальше - сценарий [плагин падает, приложение работает](../plugin-failure-isolated/scenario.md). Это нарушение меры BR-CH-008, его разбирают как дефект выпуска.
- **4г. Поставщик контракта сменил мажорную версию, а плагин просит старую.** Поставщик, дающий обе версии, обслуживает плагин. Не даёт - потребитель через `requires` не загружается с причиной, через `optional` работает без поставщика ([пользователь после обновления, 3а](../user-after-upgrade/scenario.md)).
- **5а. Устаревший член вызывается много раз.** Как пишутся повторные вызовы: каждый, склейкой или один раз за запуск, норма не говорит (вопрос 2). Возврат к шагу 7.
- **6а. Ядро не знает, что член устарел.** Пометка `@deprecated` живёт в объявлении типов и при выполнении не видна; откуда ядро берёт её во время работы, не решено (вопрос 1). Пока не решено, запись по шагу 6 не пишется, и обещание об устаревании не выполняется.
- **7а. Автор не видит журнал пользователя.** Он получает запись из выгруженной диагностики пользователя или из своего прогона; видит ли её тест-кит автора, не решено (вопрос 4). Возврат к шагу 8.
- **8а. Автор не успел выпустить версию под 2.0.** На ядре 2.0 действует 3а.

## Постусловия

Плагин либо работает на ядре той же мажорной версии без пересборки, либо не загружается с причиной словами до запуска кода; остальные плагины работают при любом исходе. Устаревшие вызовы видны вызывающим.

## Открытые вопросы

Норма молчит; сценарий не решает их за владельца. После каждого - предложение.

1. **Откуда ядру знать об `@deprecated` при выполнении (6а).** K-06 ждёт D-00, строка 10 (аннотации на членах контракта). Предлагаю решать вместе: одна аннотация на члене контракта, из которой берутся и право, и признак устаревания; иначе две машинерии на один предмет.
2. **Повторные вызовы (5а).** Мера BR-CH-008 требует «запись о вызывающих». Предлагаю одну запись на пару «член, вызывающий» со счётчиком и временем последнего вызова: так журнал не вытесняет шумным плагином чужие записи, как уже сделано для `denied`.
3. **Нижняя граница `engines.cyborg` (3б).** BR-CH-008 обещает работу на ядре «не ниже x», а руководство для автора ([сборка и упаковка](../../guide/authors/packaging.md)) учит писать `^1`. Такой диапазон пускает плагин, собранный под 1.5, на ядро 1.3, и он падает на отсутствующем члене. Предлагаю в руководстве и в сборке автора ставить нижней границей минорную версию, под которую собран плагин.
4. **Видит ли автор устаревшие вызовы до пользователя (7а).** Предлагаю тест-киту показывать те же записи журнала, что и окно: автор узнаёт о них на своих тестах, а не от пользователя.
