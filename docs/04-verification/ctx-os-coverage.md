# Достаточность `ctx.os` для базовых плагинов Cyborg

Задача [K-12](https://github.com/dex-it/cyborg-harness/issues/59). Вопрос: хватает ли `ctx.os` (`fs`, `process`, `net`) базовым плагинам Cyborg - `files`, `viewer`, `git`, `search`, `trackers`, `claude-extensions`, - чтобы перенести их функции, не давая лишних прав. Ответ нужен до заморозки API ([K-21](https://github.com/dex-it/cyborg-harness/issues/62)): всё добавленное после снимка станет ломающим изменением.

Дата сверки: 2026-11-08.

## Откуда взяты вызовы

- Код ai-cyborg, ветка `master`, коммит `e112be0`, каталог `src/main` (только чтение). Из него выписаны все обращения к `node:fs`, `node:child_process`, `fetch` и `shell`, `dialog`, `Notification` Electron: `grep` по `fs.`, `execFile(`, `spawn(`, `fetch(`, `watch(`, `shell.`. Строки ниже - `файл:строка` этого коммита.
- Основа - [«Cyborg сегодня», разд. 4](../research/cyborg-today.md#4-функции-и-их-код): какая функция в каких модулях живёт.
- Ревью команды ai-cyborg таблицы **не проходило**: список вызовов снят с их кода, а не получен от них. Строки, где есть сомнение в том, как команда понимает вызов, помечены в разделе 4.

Обозначения итога: **есть** - покрыто без правок ядра; **закрыто (K-12)** - исправлено в этой задаче, код и тест названы в разделе 3; **плагин** - решает сам плагин поверх `ctx.os`; **этап 2** - не нужно сейчас, пересматривается при изоляции доступа; **не нужно** - Cyborg этого не делает; **вне K-12** - решает другая задача эпика.

## 2. Пробелы, найденные в коде ядра: решения

Критерий отбора в ядро - [SAD, разд. 2](../03-architecture/design/sad.md#2-что-есть-ядро): задача нужна всем плагинам и плагин не решит её сам, не нарушив гарантию ядра. Права, которые выдаются плагину, не растут: нового права в манифесте задача не вводит.

### 2.1. `process.run`

| Пробел | Решение | Основание |
|---|---|---|
| Многобайтный символ на границе куска трубы портится: `chunk.toString('utf8')` в `#run`. Вывод `'a' + 'я' × 300000` возвращался длиной 300010 с 18 символами U+FFFD | **В ядро, сделано.** `StringDecoder` на каждый поток. Тест: `core/test/os-lifetime.test.ts` | Ошибка ядра: плагин поправить её не может, байты кусков ему недоступны |
| Предел `MAX_OUTPUT` 16 МиБ считался в символах и молча обрезал; трекерам Cyborg нужен буфер 64 МиБ и ошибка при переполнении | **В ядро, сделано.** Предел в байтах на `stdout` и `stderr` отдельно. `ProcessOptions.maxOutputBytes` (целое от 1 до 64 МиБ, по умолчанию 16 МиБ), `ProcessResult.truncated`; сверх предела программа получает `SIGTERM`, а если глушит его - `SIGKILL` через 2 с (то же для `timeoutMs`), в ответе прочитанное по границу символа. Значения - `processOutput` и `processOutputMax` в `LIMITS`. Тесты: `core/test/os.test.ts` | Выбран признак, а не ошибка, потому что вызывающим нужно разное: трекеры считают переполнение ошибкой («ответ больше 64 МБ»), поиск берёт совпадения из прочитанного. Признак с сохранённым выводом даёт оба. Остановка программы - как у `execFile` при `maxBuffer`; без неё бесконечный вывод жил бы до тайм-аута. 64 МиБ - буфер трекеров Cyborg, потолок не больше |
| Окружение в правиле перечислялось точными именами, а `GIT_CONFIG_KEY_<n>` и `GIT_CONFIG_VALUE_<n>` имеют переменный n | **В ядро, сделано.** Маска `ПРЕФИКС_*` в `env` правила `process`, `pty`, `launch`: звёздочка только в конце после подчёркивания, хвост - только десятичные цифры (`GIT_CONFIG_KEY_X` и `GIT_SSH_COMMAND` под `GIT_CONFIG_KEY_*` и `GIT_*` не проходят). Правило Cyborg: `["GIT_CONFIG_COUNT", "GIT_CONFIG_KEY_*", "GIT_CONFIG_VALUE_*"]`. Решение записано в [SAD, 3.7](../03-architecture/design/sad.md#37-безопасность-данных-и-контроль-плагинов). Тесты: `core/test/security-gateway.test.ts` (`ruleRefusal`), `core/test/os.test.ts` | `-c` в аргументах не годится: Cyborg выбрал `GIT_CONFIG_*` именно потому, что «в отличие от -c, имя ключа берётся как есть» (комментарий `git.ts:30-35`), а `-c имя=значение` делит по первому `=`. Маска расширяет только то, что манифест назвал вслух, и показывается словами; право `env.get` масок не принимает |
| Отсутствие программы - безымянный `Remote` с текстом ОС | **В ядро, сделано.** `ENOENT` при запуске - `NotFound` | Cyborg различает «не установлен» и остальные отказы (`missing`); по тексту ОС плагин различал бы это хрупко |
| Таймаут не отличим от иного завершения по сигналу | **Плагин.** Заданный `timeoutMs` и `signal: 'SIGTERM'` без `truncated` - таймаут | Своего признака в `ProcessResult` не заводим: он расширил бы то, что замораживает K-21, ради различения, которое плагину доступно |

### 2.2. `fs`: члены, которых нет

| Член | Нужно Cyborg? | Решение | Причина |
|---|---|---|---|
| Двоичное чтение и запись | Нет: просмотрщик показывает текст, NUL-проверка идёт по декодированному тексту, двоичные файлы Cyborg не пишет и не отдаёт | **Не нужно** | Кроме `fs`, двоичные данные в `ctx.os` вообще нет, это отдельное изменение формы API; пересмотреть, если появится плагин с картинками (этап 2) |
| `rename` | Только внутри `writeJsonAtomic` (`jsonfile.ts`) и замка воркспейса (`workspaces.ts`, файлы ядра) | **Не нужно**: атомарность даёт сам `writeText` | Отдельный `rename` потребовал бы проверки двух путей, защиты корней областей и защищённых соседей ради случая, который закрыт |
| `copy` | Нет вызовов | **Не нужно** | В коде Cyborg `copyFile` нет |
| `append` | Нет: журналы пишут хуки `claude`, а не Cyborg | **Не нужно** | Внешний процесс пишет файл сам |
| Проверка существования без исключения | Да (`exists`, `isDir` в `git.ts`, `extensions-read.ts`) | **Плагин**: `stat` и `catch`; код ошибки - `NotFound` (закрыто в K-12) | Отдельный `exists` дублировал бы `stat` |
| `lstat` | Один вызов (`git-search.ts:188`), чтобы пропустить ссылку | **Не нужно**: `list` отдаёт вид `link`; `stat` разворачивает ссылку, но ссылка наружу области отказана шлюзом, ссылка внутрь области безопасна | Шлюз проверяет настоящий путь, то есть то, ради чего Cyborg пропускает ссылки |
| `writeText` не атомарна (`O_TRUNC`) | Да: Cyborg пишет всё через временный файл и `rename` (`projects`, `hubs`, кэш использования) | **В ядро, сделано.** Временный файл `<файл>.<hex>.tmp` рядом и `rename`; режим существующего файла сохраняется; каталог, ссылка, FIFO - `Invalid`. Без `fsync` (не входит в бюджет шлюза 1 мс на p99): защита от падения процесса, не питания. Временный файл создаётся, только если на его имя есть право записи и каталог цели открыт для создания; иначе запись на месте (`O_TRUNC`). Файл без права записи (0444) не заменяется: `EACCES`, как на `O_TRUNC`. Тест: `core/test/os.test.ts` | Плагин не может сам сделать атомарную замену без `rename`, а читатель с `O_TRUNC` видит пустой файл. Не добавляет члена и права |
| Настоящий путь (`realpath`) | Да (`extensions.ts`, `allowed-paths.ts`, `open-path.ts`) | **В ядро, сделано**: `fs.realpath`. Тест: `core/test/os.test.ts` | Плагин не раскроет ссылки сам, а сверка каталогов по имени без этого неверна |
| Режим создаваемых файлов (`0600`, каталог `0700`) | Для файла событий сессий (`events-store.ts`) | **Этап 2** | Не относится к шести плагинам; решается вместе с каталогом данных `agent-claude-code` (при первом настоящем переносе `sessions`) |
| Предел `readText` | Да: JSON до 8 МиБ, просмотр до 5 МиБ | **Сделано**: 8 МиБ по умолчанию, просмотрщик держит 5 МиБ сам по `stat` | Закрывает «значение согласовать с K-12» в [SAD, 3.7](../03-architecture/design/sad.md#37-безопасность-данных-и-контроль-плагинов) |

### 2.3. Что оставлено как есть

- `fs.readText` читает файл целиком до предела 8 МиБ, предел держит само чтение (K-14).
- `fs.list` отдаёт `link`, а `fs.stat` разворачивает ссылку: этого хватает, `lstat` не нужен.
- Нет `process.run` с потоком вывода и отменой - [K-09](https://github.com/dex-it/cyborg-harness/issues/46); пределов числа процессов и размера ввода - K-14 (сделано); цепочки `fs.write` + `shell` - K-16.

### 2.4. Двоичный `stdout` и окружение пользователя

- Cyborg читает вывод `git` как `latin1` только чтобы заметить имя не в UTF-8 (`git.ts:47-60`). В `ProcessResult.stdout` невалидный байт приходит как U+FFFD, и плагин отказывает тем же образом. Параметр `encoding` в `ProcessOptions` не заводим: он не даёт ничего, чего нельзя получить из U+FFFD, а расширяет заморозку API. Пересмотреть, если плагину понадобятся настоящие байты вывода.
- Окружение Cyborg передаёт программам целиком; шлюз - базу и названное. Это намеренное сужение, не пробел: токены `gh` и `glab` лежат в их конфигурации в `HOME`. Переменные, которые плагину нужны сверх базы, он перечисляет в `env` права и в `env` правила. Маски в праве `env` (`env.get`) нет: читать можно только названную переменную. Если список окажется длинным (`GH_*`, `GITLAB_*`, `JIRA_*`, прокси), вопрос пересматривается в K-21.

### 2.5. `net.fetch`

Ядро не менялось: ветку правит [PR #99](https://github.com/dex-it/cyborg-harness/pull/99) (K-25).

### 2.6. Каталоги вне заранее названных путей

`CLAUDE_CONFIG_DIR` может указывать куда угодно. Права на весь диск плагину не дают (`/*` и `~/*` манифест не принимает), поэтому такой каталог плагин получает через `dialog.open` как область `granted`, а типовые `~/.claude/**` и `~/.claude.json` объявляет в манифесте.

## 5. Замер `fsync` и атомарной записи

Довод «`fsync` не вошёл бы в бюджет шлюза 1 мс на p99» (NFR-CH-1001) в первой редакции не был замерен, а `writeText` в [spike-gateway.md](spike-gateway.md) нет. Замер воспроизводится из репозитория: `npm run spike:fsync` (`playground/scripts/spike-fsync.mjs`; `-- --dir=<каталог>` задаёт ФС, `--json` отдаёт ряды). Скрипт без шлюза, канала хоста и Electron: 300 записей по 64 КиБ UTF-8 в один и тот же файл, четыре серии подряд; последовательность та же, что в `writeAtomic`: `open` с `O_EXCL`, запись, `chmod` существующего режима, `rename`; вариант «с `fsync`» добавляет `fsync` файла перед `rename`. Диапазон - по четырём сериям.

| Стенд | Вариант | p50, мс | p99, мс |
|---|---|---|---|
| macOS 27.2, APFS, Node 24.20 | без `fsync` (как в ядре) | 0,41-0,44 | 0,75-2,05 |
| | с `fsync` файла перед `rename` | 4,94-6,31 | 6,13-21,19 |
| Linux в контейнере (OrbStack, overlayfs, Node 24.22, 10 ядер) | без `fsync` | 0,27-0,39 | 1,01-4,8 |
| | с `fsync` | 2,34-2,78 | 3,36-15,55 |
| Linux ext4 (повтор рецензента по той же методике, [ревью #106](https://github.com/dex-it/cyborg-harness/pull/106)) | без `fsync` | 0,30 | 1,04-2,50 |
| | с `fsync` | 0,85 | 134 |

Вывод держится по p99, а не по p50: с `fsync` p99 выше бюджета 1 мс на всех трёх стендах (6-21 мс на macOS, 3-16 мс на overlayfs, 134 мс на ext4 рецензента), без него - около бюджета. Фраза «на порядок выше уже на p50» верна для macOS (в 11-15 раз); на Linux `fsync` на p50 дороже в 3-10 раз, и p50 с ним выше бюджета на overlayfs (2,3-2,8 мс), но ниже на ext4 рецензента (0,85 мс). Без `fsync` одна запись держится около бюджета на p99 без учёта шлюза и канала хоста (проверки шлюза у `fs.readText` стоят 0,08-0,10 мс на p50, [замер](spike-gateway.md)): запись 64 КиБ из плагина в бюджет 1 мс на p99 может не уложиться, но это цена самой записи на диск, а не шлюза. Пропускная способность `fs.writeText` через шлюз в `spike-gateway.mjs` не входит. Windows и сетевые тома не мерялись; числа между стендами не сравнимы (разные диски и ФС), сравнивать можно варианты внутри стенда.
