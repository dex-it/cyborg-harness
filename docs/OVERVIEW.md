# Cyborg Harness: обзор

Cyborg Harness - ядро плагинов для рабочего места, где человек ведёт несколько сессий агентов. Ядро не знает предметной области: агент, сессии, дерево файлов, просмотрщик, проекты и трекеры - равные плагины. Поставка приложения - это список встроенных плагинов и больше ничего. Этот репозиторий - разработка харнеса; перевод приложения Cyborg на харнес - забота репозитория [ai-cyborg](https://github.com/dex-it/ai-cyborg).

Статус документов - `review`: решения составителя ждут приёмки владельцем. Истина - [SAD](04-architecture/design/sad.md) и код.

## 1. Из чего состоит репозиторий

| Каталог | Что в нём |
|---|---|
| `core/` | ядро без зависимостей и без Electron: воркспейс, загрузчик и граф контрактов, хосты со сторожем, RPC, шлюз `ctx.os`, pty, слой окна, документы, клавиши; тесты - `core/test` на Node 24 |
| `core/elements/` | элементы ядра `cy-*` для видов плагинов |
| `core/examples/` | демо-плагины и сценарии ядра в консоли (`npm run demo`) |
| `contracts/` | пакет объявлений `@cyborg-harness/contracts`: API плагина и карта контрактов имя -> мажорная версия -> тип, без логики; правила - [contracts/README.md](../contracts/README.md) |
| `playground/` | Electron-приложение, где ядро видно вживую: хосты в `utilityProcess`, виды во фреймах `cyborg-plugin://<группа>/<плагин>/`, дымовой тест и замеры |
| `playground/plugins/` | плагины стенда: базовые `sessions`, `agent-claude-code`, `agent-shell`, `session-isolation`, `session-notifications`, `next-actions`, `pin-lock` и демо `echo`, `chat`, `alice`, `bob`, `flaky`, `later` |
| `docs/` | эта документация, вход - [README.md](README.md) |

## 2. Архитектура

Ядро - хост плагинов с [десятью целями](04-architecture/design/sad.md#3-цели-ядра). Оно открывает воркспейс (один воркспейс - один процесс - одно окно; процессов с общим `userData` может быть несколько), читает манифесты и разрешает граф контрактов до запуска кода, держит главные части плагинов в хостах `utilityProcess` под присмотром сторожа, держит pty дольше плагина, пропускает доступ к ОС только через шлюз `ctx.os` по правам из манифеста, рисует каркас окна по манифестам и даёт каждому виду плагина свой `<iframe>`, перехватывает системные сочетания и хранит `config` и `state` по разделам. В ядро задача попадает, только если она нужна всем плагинам или окну без плагинов и плагин не решит её сам, не нарушив гарантию остальным ([критерий компактности](04-architecture/design/sad.md#2-что-есть-ядро)). Поэтому в ядре нет агента, сессий, шины событий и реестра сервисов, а агент - обычный плагин, поставщик контракта `cyborg.agent`.

Плагины знают друг друга только через контракты, объявленные в манифесте (`provides`, `requires`, `optional`, `consumes`), команды по имени и типы данных при перетаскивании ([раздел 4](04-architecture/design/sad.md#4-взаимодействие-плагинов)). API контракта асинхронный и только с данными, поэтому вызов выглядит одинаково в одном хосте и между хостами. Строится всё в [два этапа](04-architecture/design/sad.md#6-этапы): первый даёт все цели ядра, кроме гарантии доступа, - изоляцию сбоев и рендера для всех плагинов, видимые и проверяемые шлюзом права и дисциплину, которую держат тесты; второй - `Compartment` в хостах, окна согласия и установку сторонних плагинов, когда для этого появится повод. Как это легло на код, расписано в [SAD](04-architecture/design/sad.md) пометками «Сделано» у каждой цели.
